# 功能点文档：说明这个角色负责的系统功能

`role-card.md` 里列出这个角色**负责的系统功能点**；文档建好后，每项链接到 `features/<feature-id>.md`。一个功能点一份文档。功能点是用户或外部系统能触发并看到结果的行为，例如“保存工单草稿”；“负责 Pipeline”“写测试”“维护接口”是角色工作，不是功能点。尚未写文档的计划功能标“待补文档”，不用失效链接。

## 一份文档写什么

1. **做什么。**谁在什么情况下使用，成功后得到什么。开头用一句大白话说清楚。
2. **怎么开始、输入输出是什么。**写按钮、命令或请求入口；列出会改变流程的关键输入，以及成功和失败分别输出什么。注明主要接口（网络接口写方法和 URL，内部接口写公开入口）。
3. **完整流程和分支。**按实际发生顺序写关键步骤。判断条件写成“如果……则……；否则……”，说明成功、失败、取消和重试分别去哪里，哪些数据会保存、发送或保持原样。一个功能点有多条流程时逐条写，不能只写“调用服务处理”。
4. **到哪里核对。**给当前源码入口、相关数据与接口、项目理解中的 `role_id` 和流程 ID，以及相关的日期文档链接。实际做过的验证写一两句；未实现或未核实的地方直接标明。

例子：

```markdown
# 保存工单草稿

负责角色：工单。状态：已实现。

客服暂时不提交工单时，可以保存已填内容，之后接着编辑。

## 从哪里开始

客服在编辑页点击“保存并退出”。输入是当前工单内容和工单 ID；页面通过 `POST /api/tickets/{id}/draft` 提交。成功时输出已保存草稿和成功提示；失败时输出错误提示，页面仍保留原输入。

## 怎么运行

1. 页面先检查必填内容。缺少必要内容时，留在编辑页并提示，草稿不保存。
2. 内容通过检查后，向服务端发送保存请求。
3. 保存成功时，更新草稿并返回列表；保存失败时，保留页面输入并显示原因，客服可以重试。

## 从哪里核对

- 项目理解：角色 `ticket`，流程 `save-draft`；数据 `ticket-draft`；接口 `save-draft-api`。
- 源码入口：`src/interface/ticket-editor.js`。
- 新增记录：`docs/feature/2026-09-27_feature_save-draft.md`。
- 验证：已检查保存成功和失败分支的测试。
```

例子只示范写法，不能复制成真实项目事实。已有项目先核对代码、测试和接口，再逐个补文档；没有证据的功能或分支写“待核实”。新项目可以先写“计划中”的草稿，客户确认对应方案并授权实现后才改业务代码；实现后核对真实行为并更新状态。

## 跟其他文档怎么分工

- `role-card.md` 的功能点列表回答“这个角色负责系统的哪些功能”。它只列名字、状态和文档链接，不重复完整流程。
- `boundary.md` 回答“这个角色允许改哪些文件”。功能点归属不能扩大文件权限。
- `functional-description.md` 解释角色范围内的整体架构和关键代码位置，不再把每个功能的完整流程塞在一页。
- `features/` 解释各功能**当前**怎样运行；`docs/feature/`、`docs/change/`、`docs/fix/` 记录**某次**增改修及原因，按日期保留历史。
- `project-context/context.sqlite3` 存可查询的流程图、数据字段与接口字段。功能点文档用 `role_id` 和主题 ID 指向相关记录，功能行为变化时一起核对。不要根据旧 SQLite 或文档猜新代码行为。

一个功能点只指定一个主要负责角色。跨角色的步骤在同一份功能点文档写清由谁处理；其他角色链接这份文档，不复制。若还没决定主要负责角色，先把归属问题交给项目角色和客户，不用两个角色同时维护不同版本。
