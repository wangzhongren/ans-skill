# 修改功能文档：说清前后差别

写给已经熟悉旧行为、需要适应新行为的人。读完后，他应该知道**以前怎样、现在怎样、为什么改、自己要不要调整**。

重点写：

1. **先指出改在哪里。**写明用户在哪个页面、按钮、命令或接口遇到变化；再链接实际准备修改的文件、函数或契约。还没查到代码位置就标“待确认”，继续只读调查，不编造路径。动代码前要把实际位置补进文档。若有多个改动点，逐项写“位置 → 改动”，不要只扔一串文件名。
2. **用一个触发场景比较前后。**例如“以前启动同步器后每 10 秒上传；现在只有用户运行同步命令才上传”。说清原来的结果和新的结果。
3. **用短句划清范围。**这次只改哪些行为？哪些流程、数据和用法不改？旧命令、接口或配置是否还可用；确有迁移时给出步骤。
4. **说明怎样确认。**指出最重要的回归场景和结果；详细日志、候选哈希等留在任务记录或链接的测试报告。

不要重写整份功能说明。已有稳定用法继续链接原文档；这里只讲改变的部分。若改动还没部署，要明确“代码已改，线上尚未更新”。

动代码前先把“以前怎样、准备改成怎样、不改什么”写成草稿给客户看。客户确认并授意按它修改后才动代码；完成后再核对“修改后”是否真的如此，没做到的地方不要留在文档里当成既成事实。

涉及具体功能时，在正文链接本角色 `../feature/<feature-id>.md`，并在该功能末尾的演变历史中链接回本记录。跨角色事项链接实际参与的功能文件。计划与实施状态如实标注；功能当前流程只在实现后按实际结果更新。
