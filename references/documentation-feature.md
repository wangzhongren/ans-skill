# 功能文档：让人知道现在怎么用

使用角色自己的 `docs/feature/<feature-id>.md`，一功能一份稳定文档，不加日期前缀，不再另建 `features/` 或日期版新增记录。格式和演变历史见[功能点文档](feature-point.md)。

写给第一次使用这个功能的人，也写给之后接手的开发者。读完后，他应该能回答**功能解决什么事、从哪里开始、输入什么、会得到什么**。

重点写：

1. **一句话说明用途。**谁会用、用来完成什么，不用“新增某某能力”代替实际用途。
2. **完整流程。**从哪个按钮、命令或请求开始，输入什么，经过哪些关键判断，系统在哪一步保存或发送数据，最后到哪里结束。用 Mermaid 流程图和短句按发生顺序说明；实际存在的成功、失败、取消、重试等分支都要有去向。功能跨层时说明真实的关键交接和数据变化，不强迫简单功能凑齐五层，也不抄一串内部辅助函数。
3. **给一个可照做的例子。**页面功能写实际操作；CLI/API 功能给最短命令或请求。说明每条结果分支中用户看到什么、哪些数据保存或没保存。
4. **从哪里继续看。**给主要入口、相关设计或接口文档的链接；末尾用一两句说明做过什么验证，详细测试记录留在任务报告。

这不是代码改动清单。若用户只关心怎么使用，不应先读完十个文件名才能找到答案。字段表仅在字段本身是使用门槛时列出；完整契约链接到接口说明。

动代码前可以先写“计划让用户怎样使用”，标为草稿，交客户确认。客户授意按它实现后再动代码；实现和测试完成后，把预期步骤改成真实可用的步骤，不让草稿一直冒充产品说明。

例如：“打开工单 → 填写内容 → 点‘保存退出’ → 保存成功则提示并回列表；保存失败则留在详情页、保留输入，客服可以重试。”这比“完成工单草稿模块开发”有用。

文档末尾的演变历史链接本角色 design、change、fix 中的日期文档，历史文档也反向链接本功能。已有功能的计划变更先写在历史方案里，不能提前覆盖当前流程；实现后再一起更新文字、图和历史状态。
