# 项目文档：先让人看懂

文档写给以后使用、修改或排查这个功能的人。**正文先解释事情，元数据只负责查找和生成时间线。**写作时想一想：读者没有参与这次聊天，他打开文档后最想知道什么？先回答那个问题，再放代码位置和验证链接。不要把任务报告、提交清单或审计字段原样抄成文档。

## 先选对文档

| 这次做什么 | 放在哪里 | 读者最想知道 |
| --- | --- | --- |
| 还在决定怎么实现 | `design/` | 为什么这样设计，关键过程怎样走？ |
| 新增可使用的功能 | `feature/` | 从触发到成功或失败，完整流程怎么走？ |
| 改变原有行为 | `change/` | 具体哪里改了，前后有什么不同？ |
| 修复不符合预期的行为 | `fix/` | 什么情况下出错，原因和修复是什么？ |

每一种有自己的写法，只读当前任务需要的一篇：[设计](documentation-design.md)、[新增](documentation-feature.md)、[修改](documentation-change.md)、[修复](documentation-fix.md)。简单修复不必为了凑流程另写设计文档；一个改动也不必在四个目录各写一遍。跨类型确有不同读者时，分别写重点并互相链接，不复制相同段落。

另有一类**不带日期的当前功能点文档**：每个角色在 `role-card.md` 列出自己负责的系统功能点，每个功能点在该角色的 `features/<feature-id>.md` 单独说明当前用途、完整流程和结果。它回答“现在怎样运行”；上面的四类带日期文档回答“这次为什么设计、新增、修改或修复”。写法见[功能点文档](feature-point.md)。功能点归属不等于文件修改权限。

涉及业务代码或测试时，先写相应类型的**草稿文档**，让客户看到准备改的行为和范围。客户确认这份文档并授意照它实施后，才改代码；实现完成再把草稿更新成实际行为。设计文档先说明拟采用的方案；新增、修改、修复文档先写已知场景与预期结果。**未实施、未测试、未部署**是三个不同状态，用普通话说清楚，不能把计划写成结果。

## 必须做的改动和建议选装分开写

方案里的新增或修改先分清两类：**完成客户需求、修复已查明问题或满足已有契约所必需的改动**，以及 **AI 建议顺便增加的选装**。选装包括针对尚未出现的小概率问题、额外的失败兜底、旧版本兼容或为以后扩展提前加的逻辑。不能只写“提高健壮性”就把这些当成必做，也不能把满足当前需求必需的检查或已知失败处理说成选装；必要性要能对应需求、实际问题或已有约定。

有选装时，在同一份文档里给每项一个编号，写清：**加什么、为哪种情况准备、有什么实际依据、不加会怎样、会多出什么代码或维护负担**。发生概率不知道就说不知道，不编造数字，不用“万一出问题”代替依据。没有选装就不凑这一节。

选装首次提出时默认勾选为推荐，旁边必须标 **待客户确认**。客户取消或拒绝后，保留未选状态；更新方案时不重新勾选或反复推销同一项。例如：

```markdown
这次必须做：让指定目录的文档能上传，并能查到已经上传的旧版本。

- [x] O1：同步前先列出将上传的文件（默认推荐，待客户确认）。
  好处：用户能先检查有没有漏文件。不加也能正常手动同步。
  代价：多一个预览命令，需要维护它的输出和测试。
```

**勾选不是批准。**客户确认的实施范围明确包含某项编号或所展示的勾选组合后，才实现这些选装；同一版本、同一组选装已有批准就不重复问。客户只同意必要部分、没有回复，或界面保留默认勾选，都不能当成选装批准。未批准的选装不写进代码或测试；执行中发现新的选装，先补到方案和聊天总结里，再由客户选择。可以一次确认一组选装，不要求每项反复单独问。

## 放在谁的目录

```text
项目根目录/docs/
  design/  feature/  change/  fix/     # 影响多个角色或整个项目
角色卡/<角色>/docs/
  design/  feature/  change/  fix/     # 只属于该角色
```

目录在有内容时再建。跨角色文档放在主要负责人有权写入的位置，并让其他角色链接它。项目当前的流程、数据、接口和定义仍存于 `project-context/context.sqlite3`；那里是**现在是什么**的结构化索引。`features/` 也描述当前行为，适合人直接阅读，用角色 ID 和流程 ID 链到 SQLite；功能行为改变后两处一起核对。带日期的 Markdown 说明**当时为什么和怎样改变**。源码与正式接口契约仍是行为依据，不因为写了文档就自动获得改代码权限。

文件名使用 `YYYY-MM-DD_<type>_<topic>.md`，例如 `2026-09-27_fix_save-draft-close.md`。日期用项目当地实际创建日，topic 写具体事情，不用 `update`、`misc`、`final`。继续修改同一件事时更新原文件并保留原文件名；另一次独立改变才建新文档。不要为了整理旧记录而编造旧日期。

## 正文怎么写

1. **开头用大白话。**写“保存失败时别关页面”，别写“页面会先等待保存结果”或“优化保存能力”。
2. **中间划清范围。**用短句说“这次只改什么”“什么不改”。再按读者的问题说明操作、输入、结果和失败情况；必要时放一个小例子或流程图。
3. **把原因和结果连起来。**解释为什么选这种做法、改后会怎样；事实未核实时明确标为待核实，不填套话。
4. **结尾直接说状态。**做了就说做了什么、怎么测的；没做就说“还没做”，没测就说“没测”。不要用“尚未实施或测试”绕一圈。详细命令、日志、哈希和任务证据留在任务记录，必要时给链接。

标题和小节按内容组织，不强制每份文档都有“背景、目标、范围、风险、方案、验收”六段。没有迁移就不写迁移节；没有经过比较的备选方案就不写方案对比。少用“赋能、治理闭环、能力建设、完成优化”这类看不出具体行为的词。

## 日期和时间线元数据

每份新文档开头保留一小段 YAML，便于按类型、日期和关联记录检索；**它不是正文模板**：

```yaml
---
id: save-draft-close-fix
type: fix
title: 保存失败时保留工单详情页
created: "2026-09-27"
updated: "2026-09-27"
timezone: Asia/Shanghai
status: draft
related: []
events:
  - date: "2026-09-27"
    kind: created
    summary: 记录保存失败却关闭页面的问题
---
```

`id` 在项目内唯一且不随改名变化；`type` 与目录一致；`created` 与文件名日期一致，`updated` 是实际修改日期。`status` 用 `draft`、`designed`、`implemented-unverified`、`verified` 或 `blocked`；只有真的检查通过才写 `verified`。`related` 放确实相关的文档 ID，没有就写 `[]`。`events` 只记创建、设计定稿、实施、验证、阻塞、恢复或证据失效等**真实节点**；普通措辞调整只改 `updated`，不用编造新事件。旧文档缺日期或证据时如实保留，不倒填历史。

时间线需要时，从根目录或角色目录下这四类文档的元数据生成 `docs/timeline.md`；它是浏览入口，不另写一套事实。生成前检查日期、ID、关联链接和事件是否自洽，不能从 `updated` 猜验收或部署日期。时间线、任务状态和文档正文各管一件事，正文仍以人能读懂为先。

## 交付前看一遍

确认文件放在有权限的目录、名称和链接能打开，内容讲的是**最终实际行为**，而不是过时方案。新功能与修复写明用户会看到什么；修改写明前后差别；设计区分计划和实现。若测试没跑或线上没更新，直说。不要在文档中放 Key、客户隐私或完整原始日志。

## 写完后，在聊天页面说清楚

文档保存后，不要只回复“已写入”，也不要把原文的标题、字段名和接口名直接摘抄到聊天里。附文档链接，再做一次**大白话缩写**：让没读原文、刚学编程的人也能听懂。通常用 `1. 2. 3. 4.` 中必要的几条，每条一两句，说明**现在有什么问题、准备怎么改、改完怎样用、现在做没做和测没测**。需要客户知道的限制和未核实事项不能为了缩短而删掉。

有选装时，聊天总结也要分别说“必须改什么”和“推荐加什么”，保留选装编号、默认勾选和待确认状态，用一句大白话说明好处与代价。不能只在长文档里藏着选装，也不能把“推荐”缩写成“已经决定要做”。请子代理缩写时，把这个要求一起交给它；主代理检查摘要没有漏掉选装及其确认状态。

优先自己写这段说明。自己写后仍难懂，或原文信息多、容易漏重点时，可以在现有授权和调度规则允许、且工具可用的情况下，请一个只读子代理做缩写；主代理核对后再发给客户。子代理只帮助表达，不能改方案、补承诺、确认客户授权或动业务代码。没有可用子代理也要交付清楚的短说明，不因此停住。

摘要子代理优先选当前工具支持的低成本模型，显式指定模型和低思考强度，不默认沿用主代理的高成本配置。只给它待缩写文档和表达要求，不继承整段聊天历史。当前 `spawn_agent` 支持时，可使用 `model: "gpt-6-luna"`、`reasoning_effort: "low"`、`fork_turns: "none"`；其他环境按实际可用型号选择，不把这个示例当成通用模型名单。指定型号不可用时，由主代理直接缩写，不为了摘要自动换成更贵的模型。

流程分支、前后差别或几个方案难以用短句讲清时，可以在当前聊天加一张小图或表；图表帮助理解，不代替文档，也不必每次都做。

交付**设计方案**时，再问一句：“这个方案有什么地方想进一步了解吗？”这是邀请客户提问，**不是确认方案或授权改代码**。要改业务代码或测试，须等客户确认这份文档并明确授意照它实施；只有提问、沉默或含糊的回复都不算确认。若同一份文档和实施范围已经在本次或之前的对话中获确认，不重复询问。等待时继续可独立完成的只读调查和文档工作。其他三类文档按实际内容说明，不机械地每篇都问同一句。
