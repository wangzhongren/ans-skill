# 设计文档：解释为什么这样做

写给接下来要实现或修改这部分代码的人。读完后，他应该知道**要解决什么问题、方案怎么运转、为什么选它**。设计可以尚未实现；用“计划”“拟采用”说明状态，不把想法写成已经上线的行为。

重点写：

1. **场景和目标。**谁在什么情况下遇到问题，完成后应该看到什么。用一个具体例子开头。
2. **主要过程和数据。**请求从哪里进、经过哪些关键步骤、数据怎样变化；有判断或失败分支时画一张小图或写清条件。
3. **关键选择。**哪些方案会影响维护者的判断？说清选当前做法的理由和代价。只解释真的比较过的选择，不为了凑“方案对比”编造备选。
4. **怎样知道设计可行。**列出实现后最该验证的成功、失败和边界情况；设计阶段写“待验证”，不写“测试通过”。

设计跨角色时，说明谁提供能力、谁调用、接口需要什么字段；只有涉及五层职责时才写对应层。无需把每个目录和每个类都抄进文档。正式接口细节可以链接到同一份契约，不维护第二份会过期的定义。

例如，写“工单草稿保存成功后才关闭详情页；保存失败时保留输入，让客服重试”，比写“建立可靠的草稿持久化能力”更能让人看懂设计。源码位置或示意代码只在帮助解释关键过程时加入。

交付时在聊天页面给文档链接和简短说明；分支较多时附一张小流程图。例如：“方案是先存草稿，存上了才退出；没存上就留在原页。目前只写了设计，代码还没做、没测。你对这个方案有什么想问的？”这句话让客户提问，不表示已经确认。客户确认文档并明确授意按它修改后才动业务代码；已有的同版确认和授权不必重复索取。

涉及具体功能时，在正文链接本角色 `../feature/<feature-id>.md`，并在该功能末尾的演变历史中链接回本记录。跨角色事项链接实际参与的功能文件。计划与实施状态如实标注；功能当前流程只在实现后按实际结果更新。
