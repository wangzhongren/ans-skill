# 固定测试角色

每个项目由 ANS Governance 创建并维护一份固定测试角色卡和边界，交用户确认。它是项目角色，不是新的内置角色，也不要求一直运行一个 Agent。已有专门测试角色定义就复用；测试执行上下文始终绑定测试角色。没有子代理时，在独立上下文里按授权顺序承接测试；无法创建独立上下文就报告待办，不在原上下文切换角色。

角色卡开头采用[长期维护者的工作立场](role-card.md#working-stance-for-every-role)：理解真实用户要完成什么，以及项目以后会怎样继续变化。以实际使用效果判断交付，帮助团队看清问题和影响，让后续修改有可靠的依据。

## 负责什么

1. **跨角色联调。**检查角色之间的数据、接口、错误处理和调用顺序是否符合已确认的设计。
2. **完整流程测试。**从真实入口检查用户能否完成操作，覆盖实际存在的判断分支、成功结果和失败处理。
3. **回归测试。**共享组件或功能修改后，检查受影响的原有功能，复测已修复的问题。
4. **给出明确结论。**记录测了什么、实际结果、对应版本、没测什么和仍存在的问题。测试通过只说明这些场景通过，不代替客户的业务确认。

## 与其他角色的分工

| 角色 | 测试责任 |
| --- | --- |
| 开发角色 | 编写并运行自己负责代码的单元测试和必要的层内契约测试；每层完成时先验证 |
| 项目管理角色 | 编写并运行 `common/shared/` 的对应测试；统一安排联调、修复顺序和验收 |
| 装配角色 | 配置构建和测试运行环境，完成接线与启动冒烟测试 |
| 固定测试角色 | 独立检查跨角色接口、完整功能流程和受影响功能的回归结果 |

不能因为有固定测试角色，就把开发阶段的测试全部推到最后。测试角色可以提前根据已确认的设计准备用例；依赖尚未实现时，不能把替身测试写成联调通过。

## 文件边界与必读资料

治理角色在测试角色的 Section 1 中授予专属测试目录，例如 `test/<测试角色ID>/`，包含联调、完整流程、回归用例及相应的测试夹具和测试辅助代码。沿用项目现有测试位置和语言规则；需要共置的测试列明具体文件。另授予角色的功能导航、测试方案、问题记录和测试报告的实际路径，沿用已有 `docs/`，不创建架构 JSON。

测试角色可读取本次任务相关的源码、功能文档、已确认方案、共享组件清单和其他角色的测试结果。开始前加载自己的角色卡、边界、[测试要求](testing.md)、[文档规则](documentation.md)及当前任务涉及的层约束。新增或修改测试代码同样遵守先交方案、确认后实施的要求；已确认的同版任务方案可以同时包含测试范围，不重复索要同一授权。

不能修改业务源码、`common/shared/`、其他角色的私有框架或单元测试，也不能修改构建配置、角色卡或权限来让测试通过。需要调整运行环境时，交项目管理角色安排装配角色处理。测试辅助代码不能被生产代码引用。

## 从发现问题到验收

1. 项目管理角色提供已确认方案、功能范围、当前代码版本和相关角色，安排测试任务。
2. 测试角色检查输入、步骤、分支、预期结果与实际结果；保留能复现问题的最小案例。
3. 有问题时，向项目管理角色报告复现步骤、预期与实际差别、影响范围和版本，不擅自切换角色修代码。
4. 项目管理角色判断是实现错误、设计缺口还是需求变化。实现错误交代码所属角色修复；设计或需求变化先更新文档并按现有确认规则处理。必要时暂停受影响任务。
5. 修改所属角色先运行自己的测试；固定测试角色再复测问题及受影响流程。依赖版本改变后，旧结果不能继续作为通过依据。
6. 项目管理角色汇总各角色结果，按已确认的验收条件交付。测试失败、无法运行和未测试必须分别说明，不能算通过。

固定测试角色不一定拥有用户可操作的系统功能；功能清单可以写“无直接负责的业务功能”。功能导航可以写明没有直接负责的业务功能；测试设计和报告链接受测角色的功能文档，不复制它们的流程图。
