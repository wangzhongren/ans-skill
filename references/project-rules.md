# 项目工程法案

项目工程法案把一个具体项目已确认的工程做法集中写给所有角色。项目管理角色在自己的角色目录下维护唯一的 `docs/project-rules.md`；其他角色从项目管理角色卡或正式文档引用同一实际路径，不在各自目录另建法案。它补充通用技能对本项目的约束，不替代项目目标与实施方案、架构说明、功能文档或任务记录。

## 何时适用

开始新项目或发现工程约束需要集中说明时，项目管理角色结合实际运行环境、架构、正式约定和受影响角色意见整理法案。法案路径必须在项目管理角色已接受的边界中；文档本身不扩大任何角色的读写权限。草稿、建议、待核实内容与已确认并生效的规则要明确区分。没有项目证据或确认的做法只能写成建议，不能因为技能示例而自动成为项目要求。

初始化时先建立并确认项目管理角色及其边界，再由该角色调查和整理法案。没有法案不阻止角色建立、项目启动或有授权的工作；相关约束缺失时如实说明，并按已有通用规则和确认过的项目约定工作。

## 写清每条规则

每条规则都说明：

1. **范围**：适用的目录、模块、运行位置或操作。
2. **要求**：必须、允许或禁止什么。
3. **正确办法**：在本项目中应如何实现。
4. **检查方式**：怎样从代码、运行行为或已有测试核对。

每条规则使用稳定编号或名称，便于角色引用；理由按需补充。例如线程规则要指出哪些入口运行在主线程、什么工作需要移交、结果如何返回，以及可实际执行的检查。示例仅展示写法；例如 GUI 主线程规则只有在项目确实采用该运行模型且要求已经确认后才生效。

下面的 `THREAD-01` 展示四个字段怎样落到工程做法。它只适用于项目确认采用 GUI 主线程模型并确认这项约束之后；不表示所有项目都禁止在主线程工作：

```markdown
### THREAD-01：保持 GUI 响应

范围：页面事件、渲染循环和主线程回调。
要求：这些位置不得同步等待网络或大文件 I/O，也不得执行会阻塞界面的重计算。
实现：I/O 使用项目约定的异步接口；重计算交给 Worker、后台线程或任务进程，完成后按项目约定回主线程更新界面。单纯给函数加 `async` 不会把重计算移到后台。
检查：检查调用位置，并运行相应交互和计算场景，确认操作响应及结果更新符合预期。
```

可覆盖线程与执行、代码组织和文件位置、模块依赖与公开入口、数据和共享状态、资源生命周期、错误处理与排查、验证方式等项目实际需要的主题。只写会改变角色决策的具体约束；不要复制整份通用技能或写“代码要规范”“保证高性能”等无法检查的口号。

## 执行与冲突

项目管理在方案评审时核对相关法案，执行角色在实现时阅读与本次工作有关的条目，测试角色按实际检查方式验证。没有可用检查依据时明确记为待补，不声称已自动检查或通过。报告中引用规则编号、涉及位置、证据和影响。

发现旧代码与已生效规则冲突时，局部记录实际冲突及影响并交项目管理安排；不要借机迁移或重构无关代码，也不要私自放宽规则以通过检查。项目管理按已有评审和确认流程修订法案，说明状态、依据和受影响角色。重要变更通知受影响角色；工程约束的变化链接对应的日期设计或变更记录。

法案约束工程实现方式；项目方案说明目标和实施路线。两者相互核对但不合并，也不因此新建 `project-plan.md`。
