# 内置角色：ANS 团队组建

**ANS 团队组建（原 ANS Governance）**是独立的内置角色，专责招聘、角色卡和文件边界：把“需要谁来做”变成可核对的职责与权限定义。它承接原治理职责，只有这一个所有者，不再保留第二个重叠治理岗位。原 Governance 固定上下文可继续这一职责演进；这不允许它变成统筹、项目管理或验收。

该内置角色不需要先创建自己的项目卡。统筹、项目管理、测试和验收等项目角色仍要由它建立各自卡与边界。它不是组长，也不是项目管理附带功能，不接管派发或验收。

## 什么时候需要团队组建

新项目先建立角色；已有项目新增能力、人员不足、职责冲突、拆分或合并模块时，统筹整理缺口交团队组建。团队组建先查已有角色能否承接，只有确有独立职责才提出新角色。一次小修复不需要重建团队，也不要求所有角色参加会议。

提案说明：业务职责、与现有角色的区别、唯一所有者、精确且不重叠的写入范围、分类用的组别、交接输入输出、验证办法，以及新增上下文的收益和成本。角色数量按已确认角色定义计数；同一角色开多个上下文不算增员。

先查用户已有同意或已确认配置是否覆盖这次具体角色和边界变化。已有授权足够就继续；不足才请求差额授权。组别、普通角色任务授权或工具返回成功都不表示可以增员或扩权。

## 团队组建创建什么

团队组建在自己的获准范围内创建或维护角色卡、`boundary.md`、同名 YAML 副本及根 `changelog.md` 治理变更记录。治理职责定义写在角色卡中；角色自己的 `functional-description.md` 后续由该owner在其获准范围维护真实职责、交接和代码/文档位置，不由治理接管工作文档。角色卡写职责，边界第 1 节列真实可改路径。角色模板存在不代表该角色已在项目中成立，更不授予整个仓库写权。

新项目建立彼此独立的具体角色：

| 角色 | 建立后的工作 |
| --- | --- |
| 统筹 | 默认接待请求，调查影响，安排逐角色授权、范围预留和进度记录 |
| 策划 | 后续新需求的问题、用户目标、完整产品流程、输入输出、范围与选项方案 |
| 项目管理 | 承接产品方案，负责技术架构、实现设计/技术评审、跨角色契约和 `common/shared/` 及其测试 |
| 独立验收 | 先说明怎样才算完成，再检查当前证据，判通过、返工或证据不足 |
| 业务、装配和测试 | 分别实施自己的能力、构建接线或真实测试 |

各项目角色都需要自己的卡和边界。团队组建只定义团队，不接管日常派发、全局任务记录或验收。团队组建可以为自己的角色定义结论提供依据；项目交付是否完成由独立验收判断，用户确认仍按原有约定执行。

## 交接前核对工作文档

团队组建准备完整 `roleDefinitions` 登记内容和角色权限定义，不写执行配置；已接受的统筹在自身获准范围将内容落入候选执行配置。登记内容为：真实card/boundary、精确requiredWorkDocuments及有非空职责依据的apiSpec/apiSpecReason。角色根取实际卡与边界的共同父目录，不拼roleId；包括不执行的统筹、策划、PM和验收等全部项目角色，不混入隔离样例。原owner核对职责适用性；统筹和验收对照实际角色清单核对完整性。工具只验证所登记资料，不能自动证明未登记角色不存在。

默认明确授予自身feature-map、memo、functional-description；实际导出、shared或装配接口要求api-spec，无此接口可有据声明不适用。无业务功能或代码就如实写明，不编造功能或无用层。requiredWorkDocuments仅列要检查许可的精确文件，不授权、不另建配置、不替代Section 1，也不预列所有未来日期文档。

新项目先接受统筹定义，由独立固定统筹上下文仅做候选配置准备；只读预检齐全后再交接/派发其余实际工作。已有项目由原统筹在其边界内写候选配置。团队组建提供完整登记内容和权限，不因预检需要取得配置写权。新建/调整角色按此顺序运行[任务操作指南的只读preflight-role](task-operations.md)，读取实际Section 1核对缺项、保护及全部权限重叠。没有任务/凭证要求，不创建runtime、锁、日志或状态。缺工作内容可以报告尚不存在，不能据此把完整许可误判缺权；治理只交定义，原owner接手写内容。缺权先由治理在已有授权内修正并重查，不以完成摘要替代真实结果；成功不代表客户批准、派发或验收。根changelog与card/boundary/YAML继续治理独占，执行历史落owner自身docs。

## 交接与旧项目迁移

角色定义获确认后，交给绑定统筹的新上下文。每个参与者在独立上下文绑定自己的固定角色；团队组建上下文保持这一固定身份。交接传角色、边界、授权、需求、依赖和交付要求，不传完整团队组建对话来让同一上下文改身份。

旧项目不会因更新技能而自动把 PM 改成统筹。团队组建先列出现有职责、已有卡和边界、未完成任务及记录、配置中角色绑定和缺失角色；提出迁移方案，获得对应授权后，由团队组建修改定义、已接受的统筹在自身边界内修改配置。保留历史归属，核对并停止旧写入者后，才在新的固定角色上下文接续。不能只改名称、重算哈希或沿用旧凭据来冒充完成迁移。
