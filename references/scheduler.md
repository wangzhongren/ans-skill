# 统筹调度：角色工作流、授权和派发

**统筹调度（简称调度）** 是技能内置的管理角色，任何项目一开始就可以使用，不需要项目角色卡；默认写权是 `docs/scheduling/`，项目可以通过已接受的治理文档收窄或覆盖。它负责管理每个角色的工作流、逐角色授权和范围预留、派发、任务记录与阶段放行。客户请求由[沟通角色](communication-role.md)接待；调度只在客户确认意图（**闸门 0：意图确认**）和方案（**闸门 1：方案确认**）后判断团队。策划完成（产品方案、架构设计、共有契约与完成标准）并经沟通取得客户方案确认后，沟通把客户的确认版本交给调度，调度按方案和架构判断团队并写团队计划（角色不变时也写明参与角色、各自范围和写集；需要变动时附角色调整方案），团队计划先交沟通向客户确认角色指派（**闸门 2：角色指派确认**）；客户同意后，需要新招/拆分/合并/改边界的才交[人事](team-formation.md)按已确认计划建卡。角色不变也要在闸门 2 确认参与角色、各自范围和写集；人事按计划写卡（如需）后，按客户实施指令建立各角色的任务工作流并安排开发。调度不直接找客户，也不自行判断客户是否同意。策划负责[产品方案、架构设计与共有契约](planning-role.md)；如统筹判断实现确实需要技术架构工作角色，按计划交人事建卡，该角色才负责实现设计与技术契约。测试负责真实执行，[独立验收](acceptance-role.md)判是否完成。调度不兼做这些角色，也不直接与客户对话。

## 运行架构与上下文

客户窗口只加载沟通角色，不切换为统筹或任何其他角色。统筹由沟通启动独立子代理上下文，只接收自己的角色、边界、授权、任务输入和交付要求；本上下文不切换为沟通、策划、人事、验收或工作角色。统筹是工作角色的唯一调度口，负责授权、预留、启动和收证据，不接受沟通直接给工作角色派活、授权或启动。交接时，沟通把客户确认的方案、闸门 2 的角色指派和客户实施指令交统筹，统筹再派发工作角色。验收由沟通启动独立上下文，统筹把当前候选和证据交验收，验收结论回到沟通和统筹。子代理上下文只拿自己的角色、边界、授权、输入和交付要求，不继承完整对话。完整权力矩阵见[角色权力矩阵](authority-matrix.md)。

## 创建与入口

内置管理角色立即可用，不需要先建卡：新项目由沟通接单、写盘需求并取得闸门 0 意图确认，策划形成产品方案和架构并取得闸门 1 方案确认，之后调度接手判断团队并写团队计划。团队计划（角色不变时也写明参与角色、各自范围和写集；需要变动时附角色调整方案）写入 `docs/scheduling/` 后，先交沟通取得闸门 2 角色指派确认（角色不变也要确认参与角色、各自范围和写集）；需要开发、测试、项目管理等工作角色或新增/拆分/合并/改边界时，再交人事按已确认计划建立或修改。人事按计划写卡（如需）后，按客户实施指令按方案派发开发。调度在自己的 `docs/scheduling/` 范围内准备任务记录和候选执行配置（如项目使用 `task_ops`）；人事不写配置，也不因预检需要取得配置写权。已有项目由原调度准备候选配置。客户沟通始终由[沟通角色](communication-role.md)承接；调度从沟通接收经闸门 1 确认的方案和架构、经闸门 2 确认的角色指派以及客户实施授权，不自行向客户确认或扩大授权。定义齐备不表示全部角色一直运行，更不表示每个小任务都要开会。已有项目先显式迁移角色、配置和未完任务；不能把旧上下文改称调度后继续使用。

内置调度默认在 `docs/scheduling/` 工作，不需要项目角色卡。旧项目在显式迁移前可以继续使用已有的调度角色卡和边界；新项目不必为调度建卡。若项目保留调度角色卡，卡记录必读资料、实际工具、并发限制和交接办法；边界第 1 节写真实路径。模板存在不等于获得写权。

## 团队判断与人事计划

客户通过闸门 1 确认方案和架构后，调度才判断团队，结果只能是五种之一：**不变、改边界、拆分、新增或合并**；并形成团队计划（角色不变时也写明参与角色、各自范围和写集）。判断依据是客户确认的方案版本、架构、现有角色职责与任务量；未确认的草稿不得作为团队规划或人事写卡依据。调度不把这项判断交给人事，人事也不得自行提议或决定招聘。

调度只在自己的 `docs/scheduling/` 范围写团队计划；需要变动时附角色调整方案，至少列出：判断结果（不变、改边界、拆分、新增或合并）、能力缺口、要新建或修改哪些角色、职责目标、唯一所有者、精确写入边界与写集、依赖、人员/任务分配、验证办法、分类组别和授权依据。团队计划写盘后，调度先交沟通向客户确认角色指派（闸门 2）：哪些角色、谁做、各自范围和写集；客户同意后，该计划才成为人事写/改角色卡的唯一依据。没有客户确认的角色指派时，人事必须停下并报告缺失。人事只按计划执行，不得增加计划外角色或扩大计划中角色的权限；人事认为计划不可行或缺少必要信息时，只报告问题和需要的决定，不自行修改计划或先行建卡。调度在自己的范围修订计划后可重新交沟通确认。角色就绪后，人事按计划写卡（如需），调度再按客户实施指令和方案派发开发。角色指派实质变更重开闸门 2；方案实质变更重开闸门 1；意图或范围实质变化时，等沟通重开闸门 0 后再继续。

### 五维判断与决策表

调度按五个维度判断团队，并记录依据：

1. **责任独立性**：新工作是独立责任，还是现有角色职责的一部分？看是否有独立的变化原因、是否需要不同知识和契约。
2. **范围归属**：涉及文件/模块是否已有 owner？是否缺失或重叠？看 Section 1 覆盖图。
3. **契约影响**：是否新增或改变公开契约或共享抽象？谁做唯一 primary owner？
4. **证据独立性**：是否需要独立测试或验收？一个角色能否被独立核对？
5. **协调成本**：新增角色/上下文/交接的成本是否值得？看并行收益、沟通成本和风险。

判断结果按决策表落到团队计划：

| 情况 | 决定 |
| --- | --- |
| 现有角色能承接、范围已有 owner、无新契约 | 不变，派给现有角色 |
| 职责相同但需新增精确路径 | 修改边界 |
| 新的、持续存在的独立责任，现有角色无法承接 | 新增角色 |
| 现有角色过载/混杂，工作可拆分且写集不相交 | 拆分角色 |
| 两个角色范围重叠/职责重复 | 合并或重划边界，保证唯一 owner |
| 一次性/临时工作 | 不建角色，任务分配或顺序执行 |
| 新增共享抽象但无合适 owner | 指定唯一 primary owner，确有必要才新增角色 |
| 新角色协调成本大于收益 | 不变，顺序执行 |

一句话规则：能复用就不新增；职责相同只改边界；职责独立且持续才新增；过载且可分离才拆分；重叠就合并；临时工作不建角色。

团队计划必须记录：Section 1 覆盖图、工作量与范围预留、契约影响、证据影响、协调成本、考虑过的选项、选择理由、精确边界变更清单，以及客户对角色指派的确认状态（闸门 2，确认记录以 `docs/communication/` 为准）。

### 统筹定能力与边界，人事补角色卡

统筹是“能力缺口和边界的需求方”，不是角色卡作者。团队计划写能力缺口、职责目标、精确写入边界与写集、依赖、人员/任务分配；**不写角色卡的能力描述**，也不代写职责、必读资料、交接输入输出或执行原则。

人事是“能力描述的补全者 + 角色卡的落卡人”，不是招聘决策人。人事按客户确认的计划写卡时，必须补齐能力描述（这个角色能做什么、需要什么知识/技能、与现有角色的区别），并把职责、必读资料、交接输入输出、执行原则和精确边界落到角色卡、`boundary.md` / `boundary.yaml`，检查权限不重叠并更新 changelog；不能只把边界抄进 Section 1。计划缺少能力细节时，人事只报告统筹补充，不自行补计划或先建卡。

调度可读相关需求、源码、日志、角色定义、方案和证据，定位入口与责任，直接向每个受影响角色了解现有任务、剩余工作、依赖和阻碍。未知工作量标“待评估”，不编造工时或另建工作量数据库。后续新需求的产品方案和架构交策划形成；团队是否需要改边界、拆分、新增或合并由调度判断并写团队计划；团队计划经沟通取得闸门 2 角色指派确认后，需要人事写卡的再交人事；技术实现疑问交已建立的技术架构工作角色（如有），客户沟通和需要客户决策的事项交沟通角色。调度不直接找客户，也不自行判断客户是否同意。调度不修改业务代码、shared、他人报告、角色卡或边界；角色卡、边界和角色定义类参考由人事维护，任何角色都不写自己的角色定义。

项目法案缺失不阻止角色建立或已有授权工作。如已建立项目管理角色，由其在获准路径维护法案；未建立时不虚构法案路径。所有执行者读取相关已确认条目及自己的 memo。

## 管理每个角色的工作流

调度管理的是每个角色在一个任务里的工作流，不是角色的技术判断。工作流按技能定义的标准阶段实例化，不按项目重新发明：

| 阶段 | 入口条件 | 出口条件 |
| --- | --- | --- |
| 准备 | 角色、边界、授权和输入齐全 | 影响范围、依赖和验证办法已核对 |
| 方案 | 需要业务代码或测试改动 | 相关文档或提案已写，并按方案审核流程核对 |
| 授权 | 方案版本已评审并经闸门 1 确认，角色指派经闸门 2 确认，客户已下达实施指令 | 逐角色授权和范围预留已完成 |
| 实施 | 依赖阶段已放行，写入范围已预留 | 候选实现完成，自测通过 |
| 交证 | 当前候选和检查命令确定 | 原始证据、改动路径和遗留问题齐全 |
| 验收 | 独立验收已按客户确认的策划方案建立标准，变更包（候选哈希、改动路径、任务节点、证据链接、风险档位）齐全 | 验收按客户确认的同一策划方案版本和验收表给出通过、返工或证据不足 |
| 放行 | 验收结论匹配当前候选 | 记录完成并释放依赖 |

调度为每个任务节点记录“角色 + 阶段 + 可观察交付”，维护依赖和放行条件；逐角色授权、范围预留并检查写入冲突；缺入口条件不启动，缺出口条件不放行；安排返工和补证，保留每次尝试和执行者；使用 `task_ops` 写任务记录，不手工改状态。

调度不重新定义标准工作流；需要调整共享流程时按流程文档的维护归属处理，角色职责或边界变化由调度写入团队计划，经沟通取得闸门 2 角色指派确认后交人事。调度也不替角色做技术选型、设计判断或验收结论。

工作流有两个层次：端到端阶段（需求写盘 → 闸门 0 意图确认 → 策划方案与架构 → 闸门 1 方案确认 → 团队判断与团队计划 → 闸门 2 角色指派确认 → 按需人事写卡 → 客户实施授权 → 实施 → 验收 → 交付）由[沟通角色](communication-role.md)管理；其中团队判断、团队计划和派发由调度负责。本节是每个角色/任务内部的工作流。调度向沟通报告整体状态和需客户决策事项，由沟通取得并记录客户确认；调度不直接找客户。

## 边界与记录

调度默认在 `docs/scheduling/` 下写 `docs/scheduling/<task-id>.md`，由 `task_ops` 统一写入全局计划、步骤和事件；调查、会议等文档也只使用其已获准路径。默认范围以外的路径须经项目已接受的治理文档覆盖，不授权整库文档，也不赋予调度 shared 所有权。状态仍只经task_ops统一写入，即使位于自身docs也不能借普通文档writeFiles/writeSet直改机器状态。自身有限根工作文档或有界docs文件还须同时满足实际Section 1、审核配置精确writeFiles及当前节点writeSet，治理card/boundary/YAML/根changelog、他角色资料和.ans继续保护。

调度维护 `docs/scheduling/memo.md`（默认路径，位于 `docs/scheduling/` 既有写范围内，不扩大写权）。memo 只记录调度的续接线索和已核事实，不是任务状态（任务状态仍只经 `task_ops` 写入）、不是角色定义，也不写其他角色的文档；调度完成工作后更新自己的 memo，作为交付的一部分。项目通过已接受的治理文档覆盖默认路径时，memo 落在覆盖后的角色范围内。

调度维护全局计划、逐角色授权核对、范围预留、当前进度和依赖放行。调度直接向具体角色派发并接收原始结果；组别只作分类，不增加派发或汇报层级。执行者不能拿到调度、验收或其他执行者凭据。工作者在各自固定角色上下文执行。任务计划只能缩小已确认边界，不能新增权限。

云端角色消息和管理员决定是信息来源，不自动派发本地工作；仍需检查真实任务、角色边界、写入范围和有效用户授权。

## 用阶段任务表达依赖

按已确认边界、集成设计、公开契约和必要源码调查建立有向无环图，不要求全项目代码图谱。节点是“角色 + 阶段 + 可观察交付”，不是整个角色或每个源文件。

每个节点记录：

1. 稳定 ID、所有者、阶段、目标、角色卡/边界及其版本或哈希；
2. 精确写入集合、相关不变输入、预期输出和实际检查命令，均在既有授权内；
3. 前置节点和具体放行条件，注明所需合同版本或实现候选证据；
4. 经独立验收核对的完成条件与证据要求，区分合同设计、实现和集成。

合同准备好可以让多个角色独立准备；真实集成必须等相关实现及检查。装配的构建准备可早做，最终接线晚做；shared 实施归项目管理（如已建立），完整流程测试归测试。若真实先决条件成环，交项目管理理顺设计（如未建立，交策划调整架构），不能为了调度删依赖；所有权变化交调度判断并写入团队计划，经沟通取得闸门 2 角色指派确认后交人事执行。

## 调度循环

后续新需求按“沟通接待并写盘需求 → 闸门 0 客户确认意图 → 策划形成产品方案和架构 → 闸门 1 客户确认方案 → 调度判断团队并写团队计划（经闸门 2 客户确认角色指派后，需要人事写卡的再交人事）→ 沟通取得客户实施授权 → 调度派发开发”交接；已有有效同版同范围方案和授权直接复用，不为新增岗位重复补造历史。实施前核对[方案审核](proposal-review.md)：实际文档版本、架构设计意见、受影响所有者反馈、待修订项、独立验收标准以及客户对方案和角色指派的确认与实施指令。已有同版同范围授权继续有效；实质变动按意图、方案或角色指派重开对应闸门。草案可安排已授权的只读调查，不能当已批准实施方案。

1. **查授权和范围。**核对确切角色及任务授权、客户认可配置版本、闸门 1 方案确认、闸门 2 角色指派确认和实施指令、已选择选装、边界、唯一文件归属及依赖。默认勾选不是选装授权，团队共识、方案已写完或沉默也不是客户确认。未覆盖路径先由调度判断是否属于角色调整：需要时写入团队计划，经沟通取得闸门 2 确认后再交人事，不派发受影响节点。新建/调整角色接手前，按[任务操作](task-operations.md)运行无任务副作用的preflight-role，核对实际card/boundary根、完整登记和精确requiredWorkDocuments；缺权写入团队计划交人事处理，不代改。清单不授权，成功不代替客户确认或验收。启用登记的新任务init复用同源检查；旧配置不能自动获得角色文档写权。
2. **找可以开始的阶段。**依赖必须满足当前记录条件，输入齐备，没有活动写入者冲突；文档、生成文件、公共入口和配置也要检查碰撞。角色名不同不代表写入范围不同。
3. **逐角色预留再启动。**按[任务操作](task-operations.md)给具体 `roleId` 和范围做授权/预留，再使用可用且已授权的工具开独立上下文。只传该角色、边界、授权、任务输入和检查，不继承调度完整角色对话。调度只授权、预留和启动工作角色；策划、人事、统筹、验收由沟通启动独立子代理，调度不启动内置管理角色。可信启动端只在调度授权后启动工作角色。执行者不派发其他角色；工具不是代理启动器。
4. **接收真实证据。**核对任务/阶段/尝试、改动路径、最终候选版本、产物、实际检查结果和遗留问题。收到当前证据后，把**变更包**交独立验收：候选哈希、改动路径、任务节点、证据链接、风险档位（T0-T3），并附客户确认的策划方案版本；不要求验收每次全量重跑。验收按该确认版本和验收表判断通过、返工或证据不足，调度不能按自己的意见改结论。完成报告或进程成功退出都不能代替验收。
5. **按策划方案验收结论更新和放行。**只消费匹配当前候选、客户确认的策划方案版本和标准的有效结论；通过才记录相应完成并释放依赖。返工交原所有者，证据不足安排补证；调度不能自己改结论。最终装配与测试使用合并后的实际候选，各角色单独通过不表示组合通过。

按任务选择能可靠完成工作的最低成本可用模型；工具允许且用户未指定时明确设置。摘录、总结和简单检查通常可用低成本低思考；复杂实现或关键审核需要较强模型时说明具体原因。只传必需资料，遵守工具对模型覆盖和上下文继承的限制。

## 交验收的变更包

统筹交给验收的不是一句完成通知，而是**变更包**：候选哈希、改动路径、任务节点、证据链接、风险档位（T0-T3），并附客户确认的策划方案版本。风险档位按 [testing.md 的风险分档](testing.md#risk-based-verification-and-change-packages) 标注；统筹不得为省检查而压低档位。验收按变更包和验收表核对证据覆盖，复用仍有效的同候选、同输入/依赖、同命令证据，只补失效部分；统筹不能要求验收每次全量重跑，也不能代替验收改结论。

## 失败、恢复和完成

阶段状态沿用 `pending`、`ready`、`running`、`awaiting-verification`、`verified`、`failed`、`blocked`、`cancelled`。`ready` 取决于当前依赖；`verified` 是已记录的阶段结论，候选或证据随后可能过期；当前完成须看 `task_ops status` 的 `currentAcceptanceValid` 与 `taskComplete`，不能只看持久化状态。保留每次尝试、执行者、失败证据和变更原因。

- 失败阻止依赖它的阶段，独立且已授权工作可继续。业务或私有代码归原所有者修，shared 归项目管理修（如已建立），测试角色复测；调度安排顺序。重试须有已改变条件或具体返工计划。
- 合同、边界、源码或相关规则变化使受影响证据失效。安全暂停并核对运行者，再回到待做/返工，不能只改哈希让旧证据冒充当前结果。
- 恢复前核对真实执行者、当前源码/合同及证据，状态不明时不重复启动写入者。确认停止或完成后才释放预留。尊重停止和取消要求。
- 无并发工具时按相同授权、依赖和隔离要求顺序交给独立角色上下文。无法创建新上下文就保留待办，不在调度上下文切换角色。

必需阶段都获当前有效验收、组合检查通过且文档/记录齐备后才能报告完成。必需节点取消、阻塞、返工或证据不足都不能算完成。调度对其派发、角色工作流与记录准确负责，代码所有者对实现和自测负责，测试对真实测试负责，独立验收对完成判断负责；任何一方都不能取代用户授权。
