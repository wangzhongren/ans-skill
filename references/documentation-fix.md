# 修复文档：让人看懂问题和解法

写给遇到同样问题的人和将来排查这段代码的人。读完后，他应该知道**什么情况下会出错、错在哪里、现在如何处理、怎样确认没再发生**。

重点写：

1. **症状和触发条件。**用用户能观察到的现象开头，给最短的复现步骤或输入；区分实际结果和预期结果。
2. **根因。**沿实际调用链找到哪一步偏离预期。用一两句解释因果，不堆调查过程或整段日志；根因仍未确认时直接说明。
3. **修复后的行为。**描述改了哪条判断、数据流或错误处理，以及失败时会怎样；源码链接只给关键位置。
4. **回归验证。**写能防止问题再次出现的测试场景和实际结果。如果还需真实环境验收，明确留在哪里。

不用把每一次搜索、猜测和失败尝试写成流水账。保留后来的人真正能用来识别和解决问题的线索。

修代码前先记录已确认的症状、当前掌握的原因和准备怎样修，标为草稿交客户确认。原因还没查清就写“还没查清”，继续只读排查。客户确认文档并授意实施后再改代码；修完再补真实的回归结果。

例如：“保存接口返回失败时，详情页仍被关闭。原因是关闭页面的代码没有检查保存结果；现在仅在保存成功后关闭，失败时保留输入并显示错误。”比“定位并优化保存链路”更容易复查。
