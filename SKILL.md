# ANS Governed Construction

This skill helps AI change a project without touching unrelated files. Read enough to understand the problem, but edit only files the current task and active role allow. Explain results so a beginning programmer can tell what changed, what it does, and how it was checked.

The governing rule is:

> Read widely when needed; change only what you are allowed to change.

AI may propose a change. The user and the execution environment decide what may run and what may be accepted.

Every project role approaches its work as the long-term maintainer of its responsibility in a real, evolving project. Actual use, collaboration with existing components and future maintenance guide its judgment. Express this [working stance](references/role-card.md#working-stance-for-every-role) near the start of each role card. Existing scope and authorization still apply.

Customer requests enter through the **ANS Communication** built-in role — the single customer interface and end-to-end workflow owner. Communication records the request under `docs/communication/` and passes it through three separate customer gates; never merge or skip them:

1. **Gate 0 — intent confirmation.** Communication first writes down its understanding of the request and asks the customer to confirm it: goals, scope, priorities, non-goals, already-authorized boundaries and known constraints. Only after the customer explicitly confirms that understanding does the request go to **Planning**.
2. **Gate 1 — proposal confirmation.** Planning produces the product proposal, architecture design, shared business contracts and checkable acceptance criteria; the customer-confirmed version is the **implementation plan**. When the situation, root cause, impact or feasibility is still unclear, Planning also writes a **research plan**: the questions to answer, investigation scope and entry points, methods, required evidence and stop conditions. All implementation plans and research plans are written by Planning; the Scheduler writes only the team plan and task plan. Communication presents the proposal to the customer. Until the customer confirms it, no team planning or recruiting starts.
3. **Gate 2 — role-assignment confirmation.** The **Scheduler** judges the team — keep, adjust boundaries, split, add or merge — by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表), then completes the team plan: which roles, who does what, and each role's scope and write set. This assignment is required even when the roster stays unchanged, and any role-assignment or boundary change needs the customer's confirmation here. Communication presents the role assignment to the customer. Until the customer agrees, People Operations writes no role cards and the Scheduler dispatches no development.

After gate 2, People Operations writes or changes role cards and boundaries only as the confirmed team plan directs: the plan defines what capability is needed and what boundary it must have, and People Operations supplies the capability description and turns it into the card text. It never recruits on its own; the Scheduler then authorizes, reserves and dispatches the work. Communication is the only customer channel: the Scheduler and worker roles never contact the customer directly. Only explicit customer agreement passes a gate — default checkmarks, team consensus, a finished proposal and silence are not agreement. An intent change reopens gate 0, a material proposal change reopens gate 1, and a role-assignment change reopens gate 2. Same-object, same-version, same-scope confirmation remains reusable, but one gate's confirmation never substitutes for another. Never switch one context between roles. See [Role Binding and Handoff](#role-binding-and-handoff).

## Governing Invariants

Maintain these invariants throughout the task:

1. **Edit only allowed files.** A file must be in this task's write scope; ask for a scope change before editing anything else. For a built-in management role, its reference default scope is the baseline; a project may narrow or override it through accepted governance.
2. **Follow the layer rules.** Code may call only capabilities allowed by its layer and the agreed public interface.
3. **A patch is not yet a finished change.** Run the required structure checks and behavior tests first.
4. **Tests prove only what they actually ran.** Record the code version, environment, inputs, and rules used for the result.
5. **Protect frozen files.** Do not change them during an ordinary downstream fix; change them only when the task authorizes it.
6. **Retest callers after changing a dependency.** Earlier test results for affected code are no longer current.
7. **Do not make a failing change look successful.** Never delete tests, loosen assertions, widen permissions, or hide errors just to make it pass unless the user explicitly changes that rule.
8. **One context, one fixed role.** Once bound, a context cannot activate another role. Cross-role work requires a separate context; neither authorization nor unavailable subagent tools permits an in-place switch.

### Adjacent-Layer Calls, Controlled Infrastructure Access, and Shared Models

The default operational call direction is:

```text
Interface -> Pipeline -> Service -> Provider -> external infrastructure
Model: shared by all four operational layers
```

- Interface may call Pipeline only. Pipeline normally calls Service; it may directly call a narrow operation from the designated Provider public entry point only for infrastructure orchestration with no business validation, transformation, deduplication, policy, or platform-specific business decision. Service may call Provider only. Provider is the bottom operational layer and accesses its authorized infrastructure. Do not call upward, deep-import Provider implementations, or call peer components as a workaround. Private module collaboration within one component is allowed under the shared acyclic dependency rules.
- Controlled Pipeline-to-Provider operations are limited to connection/transport clients, storage, process lifecycle, logging, metrics, notifications, and bootstrap construction. They must be explicitly exported by Provider public, must not expose concrete implementations or lower-layer capability objects to Interface, and must not become a general service locator. If business meaning is present, add or reuse a meaningful Service instead of using this exception.
- Responsibility determines module ownership, existing capability determines reuse, and layer position determines the legal call path. Apply the decision table in [Shared architecture](references/architecture.md): invoke an existing capability, modify its existing responsibility, or create a separate owner for a new responsibility. Call boundaries do not require every feature to visit or add files in all layers.
- Enforce this direction for imports and runtime capability use, including injected objects, callbacks, factories, registries, dynamic imports, and re-exports. Passing a Provider into a Pipeline or Interface does not authorize those layers to invoke it; an allowed Pipeline call must target the declared Provider public infrastructure operation itself. Returning ordinary results or errors to a caller is not an upward call.
- Each layer exposes its own operations and manages only the immediately lower layer, except for the controlled Pipeline infrastructure access above. Do not re-export lower-layer APIs or hand lower-layer capability objects to higher-layer consumers. Keep creation and selection local: Interface starts Pipeline, Pipeline obtains Services through the Service public entry point, Services obtain Providers through the Provider public entry point, and an authorized Pipeline infrastructure call enters through that same Provider public boundary. No global wiring shortcut may bypass these boundaries.
- Model is globally shared and outside this operational call chain. Every layer may directly use Model schemas, types, value objects, and invariant validation. Model must not depend on or call Interface, Pipeline, Service, or Provider, and shared access does not authorize mutable global business state.
- `utils` remains a helper folder, not an operational layer. Its shared helpers must not depend on or invoke the operational layers or perform external effects on their behalf. Keep effectful helpers inside Provider. Neither Model nor `utils` may be used to hide a forbidden dependency.

See [references/architecture.md](references/architecture.md) for the full dependency decision table, three-part layer structure (`abstract/`/`public/`/`impl/`), enforcement edge cases (imports, callbacks, factories, dynamic imports, re-exports), creation locality rules, and Model sharing constraints.

## Role Cards & Module Boundary Documents

Role cards (角色卡) and module boundary documents (模块边界文档) together define **what the AI may read and what it may mutate**. For worker roles they are per-project artifacts, created autonomously by the AI when needed and candidates until human-accepted. The five built-in management roles do not need project cards; their reference documents carry their default scopes. Follow explicit user requirements first, then repository conventions, then language/toolchain conventions. Use OS locale only as a fallback for natural-language prose; never translate identifiers or change filenames solely because of locale.

The [authority matrix](references/authority-matrix.md) is a summary view maintained by People Operations. It shows the current division of authority across the built-in and worker roles, but it does not add, remove or change any permission. The authoritative sources remain this SKILL, each role's reference default scope and a worker role's `boundary.md` Section 1.

**Boundary documents** use Section 1 of `boundary.md` as the mutation whitelist; description and ownership details live in the companion `functional-description.md`. A same-name `boundary.yaml` is a synchronized copy, not an authority source. The five built-in management role references carry their default scopes and responsibilities together; worker roles use `boundary.md` Section 1 and companion descriptions. **Role cards** describe what the agent does, list must-read docs (including its boundary doc), state the execution principles, and link to `feature-map.md`, the role's single feature navigation. Each owned feature gets one current-behavior document with a flowchart and history links under the role's existing `docs/feature/`; do not confuse a system feature with a role duty or use feature ownership as mutation permission. See [references/module-boundary.md](references/module-boundary.md), [references/role-card.md](references/role-card.md), and [references/feature-point.md](references/feature-point.md).

**Files not listed in or covered by an accepted directory in Section 1 are read-only by default.** Each role may grow its private `common/<role-id>/` subtree within an approved task. When the scheduler's team plan establishes a project-management (technical-architecture) worker role, that role alone owns `common/shared/`. Uncovered files and ownership changes require a People Operations boundary update based on the scheduler's team plan (Governing Invariant #1). See [common-code ownership](references/shared-directories.md).

Planning owns the product proposal, implementation plan, research plan and architecture design in `docs/planning/`. When the scheduler's team plan establishes a project-management (technical-architecture) worker role, that role maintains the implementation-level architecture and role collaboration in its own `docs/architecture.md`. It also maintains one project-wide engineering rules document at `docs/project-rules.md` within accepted scope; every role reads that same actual file and keeps its own `memo.md` for concise private work clues. See [project rules](references/project-rules.md) and [role memos](references/role-memo.md). No project-specific rule is effective merely because it appears as a skill example. During bootstrap, People Operations establishes and accepts the worker role definitions the scheduler's written team plan needs, including project management only when implementation needs a technical-architecture role; the five built-in management roles need no definitions. Absence of a project rules file does not block initialization. Development roles maintain `feature-map.md` and one Markdown file per feature in their existing `docs/feature/`: purpose first, then a readable Mermaid flowchart and steps, followed by links to design/change/fix history. Historical documents link back to their features. Do not require architecture JSON, a separate role-root `features/`, content.json or a project-understanding database. Source and contracts remain behavior evidence. See [feature documents](references/feature-point.md).

Feature documents and dated design/change/fix history explain work to people; they are not copies of the task audit log. Feature files use stable names and are the current explanation, not a second dated feature record. Use [the shared documentation rules](references/documentation.md) plus only the guide for the type being written: [design](references/documentation-design.md), [feature](references/documentation-feature.md), [change](references/documentation-change.md), or [fix](references/documentation-fix.md). A feature document must trace the complete path and meaningful branches; a change document must name the user-visible entry and verified code location. If that location is unknown, keep investigating before implementing rather than inventing a path. Keep date metadata for navigation and link detailed test evidence instead of copying logs.

For work that would change application code or tests, prepare the relevant feature draft or dated design/change/fix proposal first and make the proposed behavior and scope reviewable. Summarize it in the chat with a link and, when helpful, a small diagram or table. Do not change application code or tests until the customer confirms that document and instructs implementation based on it. An existing confirmation and implementation instruction for that document/version remains valid across turns; do not ask again. This document-level confirmation is separate from the three workflow gates and never substitutes for the role-assignment confirmation (gate 2) before dispatch. Read-only investigation and document preparation may continue while a decision is pending. If the design changes materially, present the revised document before implementing the affected change.

For new product requirements, Communication first confirms its understanding of the intent with the customer (gate 0), then routes the request to [planning](references/planning-role.md); Planning delivers the product proposal, implementation plan, research plan (as needed), architecture design, shared business contracts and acceptance criteria; the customer-confirmed version is the implementation plan, and all implementation and research plans are written by Planning. Communication obtains the customer's proposal confirmation (gate 1). Only then does the scheduler judge the team by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表) and complete the team plan — which roles, who does what, each role's scope and write set — and Communication obtains the customer's role-assignment confirmation (gate 2) before People Operations writes any role cards or the scheduler dispatches development. Role-assignment and boundary changes are among the objects confirmed at gate 2. Only if the confirmed team plan includes a technical-architecture worker role does that role add implementation design and technical contracts under the confirmed architecture. Same-object, same-version, same-scope proposals and confirmations remain valid; adding a planner does not require duplicate historical proposals.

Before requesting customer implementation approval for application-code or test changes, the review step follows the scheduler's team plan. When a project-management (technical-architecture) worker role exists, it must [review the proposal](references/proposal-review.md), assess architecture and cross-role impact, seek affected owners' assessments where needed, and consider materially better alternatives. When no such role exists, the scheduler checks the proposal against the confirmed planning proposal and architecture and the affected owners' findings before dispatch; no role invents a reviewer. The reviewer returns needed revisions to the owner, then presents a concise approval brief linking the reviewed proposal/version, recommendation and reason, affected roles, risks/costs, unresolved issues, optional selections and exact approval scope. Do not merely forward the owner's text. Review recommendation, customer authorization and verified implementation remain distinct. Task-level implementation approval is not the role-assignment confirmation (gate 2); each gate confirms its own object and version, and neither replaces the other. Standalone owners use a separate authorized review context; no role switching is allowed. Reuse valid same-version approval and review evidence rather than repeating gates without changed findings.

Separate changes required by the task or existing contracts from optional hardening, compatibility or speculative additions. Show each optional item in both the document and its plain-language chat summary, with a stable item ID, reason, benefit and added cost. Options are checked by default as recommendations but remain pending; only implement the options explicitly covered by the customer's confirmed selection and implementation authorization. A default checkmark alone is not consent. Follow [the optional-change rules](references/documentation.md).

After writing a document, link it and restate its meaning in brief, plain language for a beginning programmer; do not just copy technical headings or identifiers. Explain the problem, proposed change, how the user will use it, and what is or is not done. When needed and authorized, a read-only subagent may help shorten the explanation; prefer a low-cost model with low reasoning effort and minimal context, then verify its summary against the document before sending. Follow [the documentation handoff guide](references/documentation.md). For a design proposal, invite the customer to ask what they want clarified; that invitation is not itself confirmation or permission to implement.

Explain each feature so a beginning programmer can answer: **What is the user trying to do? What changes on success? What happens on failure?** Its feature document records the trigger, complete flow, real conditions and debugging references. Its Markdown flowchart shows actual steps and decisions, including role handoffs and returned results; history links explain how it changed. Do not invent branches, bulk-fill explanations from button names or make missing information look complete. A resulting HTTP request belongs to the same feature's flow. See [Interface constraints](references/interface.md) and [the feature document guide](references/feature-point.md).

Every worker role needs explicit Section 1 coverage for its own `feature-map.md`, `memo.md` and `functional-description.md`; the five built-in management roles use their reference default scopes and keep their records there, including `memo.md` (Communication `docs/communication/memo.md`, Planning `docs/planning/memo.md`, Scheduler `docs/scheduling/memo.md`, Acceptance `docs/acceptance/memo.md`, People Operations `角色卡/招募/memo.md` as a governance memo). The memo is a private continuation note, not a role definition or task state, and it does not expand write authority. Worker roles without system features say so; collaboration roles describe actual responsibilities, handoff inputs/outputs and document locations without inventing code. `api-spec.md` applies to real exported/shared capabilities or assembly interfaces; otherwise record a reasoned `not-applicable` decision. Role cards, boundaries, synchronized YAML and root governance `changelog.md` remain People Operations-owned; owners keep implementation history in their own docs.

On the scheduler's written team plan, People Operations supplies worker role registration content and role permissions; the built-in scheduler writes the candidate configuration within its own `docs/scheduling/` scope. A new project needs no scheduler definition acceptance: use a separate fixed scheduler context for configuration preparation only, then preflight before handing off/dispatching the remaining actual work. Existing projects use their existing scheduler. People Operations gains no configuration write authority. Run the read-only `task_ops preflight-role` against actual definitions and the existing configuration's complete `roleDefinitions`. Its exact `requiredWorkDocuments` list checks expected permission coverage; it grants nothing. The root comes from the actual card/boundary parent, never the role ID. The check creates no task/runtime/lock/log. Missing permissions return to the scheduler, which records them in the team plan for People Operations to correct. Execution still requires the intersection of the role's permitted root work files or bounded docs, actual Section 1, approved exact `writeFiles` and node `writeSet`, excluding governance, peers and state. See [bootstrap](references/bootstrap-workflow.md) and [task operations](references/task-operations.md) for the approved contract and implementation status.

### Bootstrap

When the scheduler's written team plan needs worker roles and the project has no worker boundary documents, follow the [bootstrap workflow](references/bootstrap-workflow.md) under the ANS People Operations built-in role. The plan is People Operations' only basis for writing or changing definitions. The five built-in management roles need no bootstrap.

### People Operations Rules

- Every worker role card must reference its boundary Markdown document; its same-name YAML is only a synchronized copy. The five built-in management roles use their reference default scopes and need no card or boundary. Section 1 lists exact layer-source files and may grant the role's specific private `common/<role-id>/` subtree, project-owned `common/shared/`, and dedicated role-owned test directories. No blanket source/common root or overlapping ownership is allowed. Supporting and governance locations may use bounded directory entries; see [module-boundary.md](references/module-boundary.md).
- New or removed files inside an accepted directory do not require a per-file boundary rewrite; the task still records actual changes. New directory permissions, ownership changes and additions/removals of individually listed paths require People Operations to update Section 1 before execution. Ordinary edits to already permitted files do not require a boundary rewrite.
- Worker role cards grant context, not mutation authority. Only Section 1 of the referenced boundary document does; a built-in role's reference default scope is its baseline. Each card records `group` / `组别` as classification only. Roles are peers; there is no group-lead duty, group dispatch or intermediate reporting layer. The scheduler dispatches to and receives evidence from each role directly. See [People Operations](references/team-formation.md).
- Boundary documents and worker role cards obey the same evidence and acceptance gates as code changes.
- **Shared abstractions** (Model types, event buses, public entry points, cross-module contracts) must have exactly one **primary owner** role. Other roles may reference them as read-only dependencies. A primary owner change invalidates evidence for all referencing roles (Governing Invariant #6).
- **Role activation required:** Before creating or modifying any file, verify the current role. Built-in management roles operate from their reference default scopes without a project card or boundary. Worker roles require a loaded card and boundary Section 1. Scheduling records belong to the scheduler's `docs/scheduling/` default scope. Application code requires a worker role card and its boundary doc Section 1. Writing application code without an active worker role is a governance violation.

### Built-in Management Roles

The skill provides five built-in management roles. They are available immediately in any project, need no project role card, and carry narrow default write scopes for their own management artifacts. A project may narrow or override a default scope through accepted governance, but the default never grants application-code writes.

| Built-in role | Default write scope | Responsibility | Reference |
| --- | --- | --- | --- |
| Communication (沟通) | `docs/communication/` | Sole customer interface; owns the end-to-end workflow and customer gates; records requests; relays among the other four | [communication](references/communication-role.md) |
| Planning (策划) | `docs/planning/` | Turns a requirement into a product proposal, implementation plan and research plan (as needed), architecture design and shared business contracts; states checkable completion criteria as the acceptance baseline; all implementation plans and research plans are written by Planning | [planning](references/planning-role.md) |
| People Operations (人事) | `角色卡/` governance artifacts | Writes and changes worker role cards and boundaries only per the customer-confirmed team plan; the scheduler's plan defines the needed capability and boundary, and People Operations supplements the capability description and turns it into the card text; never recruits on its own and never writes application code | [People Operations](references/team-formation.md) |
| Scheduler (统筹调度) | `docs/scheduling/` | Judges the team from the customer-confirmed proposal and architecture (keep, adjust boundaries, split, add or merge) by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表), completes the role assignment, and manages each role's task workflow: stages, dependencies, authorization/reservation, dispatch, evidence and stage release; writes only the team plan and task plan, never the implementation plan or research plan, and arranges authorized read-only investigation per Planning's research plan | [scheduler](references/scheduler.md) |
| Independent Acceptance (验收) | `docs/acceptance/` | Writes completion criteria from the same confirmed planning proposal version before implementation; judges current evidence as pass, rework or insufficient evidence; cannot invent criteria | [acceptance](references/acceptance-role.md) |

Built-in roles are identities, not standing agents: a project does not need to keep all five running. They still obey one fixed role per context, customer authorization, and the task's document-first gates. The scheduler defines what capability the plan needs and what boundary it must have; People Operations supplies the capability description and writes it into the card rather than re-deciding the team. Their default scopes cover only their own records; reading is broader, and writing outside the scope still needs an accepted boundary.

**Worker roles** are project-specific: capability, assembly, test and, only when the scheduler judges implementation needs it, a project-management (technical-architecture) role. People Operations creates them only per the scheduler's written team plan. Each worker role has an accepted card and `boundary.md` Section 1; it writes application code or tests only within that boundary.

**ANS People Operations (ANS 人事; formerly Team Formation / recruiting, formerly ANS Governance)** is the built-in People Operations role. On the scheduler's written team plan, it forms worker roles and maintains governance artifacts — role cards, module boundary documents, and skill definitions. It never decides or proposes recruitment on its own, never writes application code, and does not dispatch execution or judge acceptance. Its reference boundary source is [references/built-in-boundary.md](references/built-in-boundary.md); its adjacent [YAML copy](references/built-in-boundary.yaml) is for structured readers only.

**After recruiting, People Operations creates no application code.** Implementation is a separate task under the worker role's card and boundary. Load its Section 1 before writing code.

### The Five-Role Operating Model

The five built-in roles form one customer-facing hub and four management roles around it; worker roles sit under the scheduler.

| Role | Responsibility |
| --- | --- |
| Communication (沟通) | Sole customer interface; owns the end-to-end workflow and customer gates; records requests; relays among the other four |
| Planning (策划) | Turns a requirement into a product proposal, implementation plan and research plan (as needed), architecture design and shared business contracts; states checkable completion criteria as the acceptance baseline; all implementation plans and research plans are written by Planning |
| People Operations (人事) | Writes and changes worker role cards and boundaries only per the customer-confirmed team plan; the plan defines the needed capability and boundary, and People Operations supplements the capability description; never recruits on its own |
| Scheduler (统筹调度) | Judges the team (keep, adjust boundaries, split, add or merge) after the customer confirms the proposal and architecture, using the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表); completes the role assignment (which roles, who does what, each role's scope and write set); manages each role's task workflow: stages, dependencies, authorization/reservation, dispatch, evidence collection and stage release; maintains task records; writes only the team plan and task plan, never the implementation plan or research plan, and arranges authorized read-only investigation per Planning's research plan |
| Independent Acceptance (验收) | Writes completion criteria from the same confirmed planning proposal version before implementation; judges current evidence as pass, rework or insufficient evidence; cannot invent criteria |

The customer talks only to Communication. Communication records the request, confirms its understanding of the intent with the customer (gate 0), and only then takes it to Planning. Planning produces the product proposal, implementation plan and research plan (as needed), architecture design and shared business contracts. Communication obtains the customer's confirmation of the proposal (gate 1). Only after that does the scheduler judge the team — keep, adjust boundaries, split, add or merge — by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表). The scheduler completes the team plan — which roles, who does what, each role's scope and write set — including the assignment when the roster stays unchanged; Communication obtains the customer's confirmation of the role assignment (gate 2). Role-assignment and boundary changes require confirmation at this gate. Only then does People Operations write or change the worker role cards the confirmed plan requires: the scheduler's plan defines what capability is needed and what boundary it must have, and People Operations supplements the capability description and turns it into the card text. The scheduler then manages each role's task workflow, dispatches workers, and collects evidence. Workers report to the scheduler, not to the customer. Acceptance writes criteria from the same confirmed planning version and judges current evidence; the scheduler releases stages and Communication reports to the customer.

Built-in roles have deliberately narrow default write scopes. Communication writes only `docs/communication/`; Planning only `docs/planning/`; the scheduler only `docs/scheduling/`; acceptance only `docs/acceptance/`; People Operations only worker role cards, boundaries and governance changelogs under `角色卡/`. None writes business code, another role's documents, task records belonging to another role, or role-definition files outside its scope. See the individual references for details.

For new product requirements, Communication confirms its understanding of the intent with the customer (gate 0) and starts the [Planning](references/planning-role.md) context, which describes the problem, user goals, full product flow/branches, inputs/outputs, scope and options, defines the shared business contracts among affected roles — promised inputs/outputs, shared terms, handoff conditions, success/failure semantics and behavior guarantees — and owns the architecture design: layering and modules, call/data flows, necessary interfaces, data models and error semantics, sharing and reuse, technical choices and verification points. The customer-confirmed planning proposal and architecture (gate 1) are the implementation plan and the acceptance baseline; when investigation is needed first, Planning writes the research plan, and the scheduler arranges authorized read-only investigation per that plan instead of writing its own. If implementation genuinely needs a separate technical-architecture worker role, the scheduler judges that need and writes it into the team plan; only after the customer confirms the role assignment (gate 2) does People Operations create the project-management role, which details implementation design and technical contracts under the confirmed architecture without rewriting planning decisions. Reuse valid existing proposals and same-object, same-version, same-scope confirmations instead of recreating them.

Workers implement and unit-test their own scope; assembly owns startup/wiring; the [fixed test role](references/test-role.md) runs cross-role, complete-flow and regression checks. The [independent acceptance role](references/acceptance-role.md) writes completion criteria from the same confirmed planning proposal version before implementation and judges the current result as **pass, rework, or insufficient evidence**; it cannot invent criteria. The scheduler embeds those criteria as gates in each role's workflow and consumes the conclusion to record/release stages and arrange repairs or missing evidence. Scheduling, architecture review, tests and acceptance are distinct facts; none substitutes for customer authorization.

Acceptance is risk-based, not a full rerun by default. The scheduler gives Independent Acceptance a change package for the current candidate: candidate hash/version, changed paths, task nodes, evidence links and risk tier (**T0** pure documentation with no governance or permission change, **T1** local implementation, **T2** cross-role/contract/shared, **T3** release, shared abstraction, governance or permission change). The single T0–T3 definition is in [testing](references/testing.md). Acceptance reviews the change record and the acceptance table in `docs/acceptance/`, reuses evidence still valid for unaffected paths, and adds only missing, invalidated or high-risk checks. Full regression is reserved for T3 changes or insufficient evidence. See [documentation](references/documentation.md).

Worker roles are created by People Operations only when the scheduler's written team plan requires them, each with an accepted card and boundary. Existing projects require an explicit [migration](references/team-formation.md#交接与旧项目迁移); never silently rebind an existing context, retire an existing project role card, or reuse old self-verification as independent acceptance.

### Default Project View: Markdown Architecture and Feature Flows

Start from Planning's customer-confirmed implementation plan (proposal plus architecture design) and any research plan under `docs/planning/`. When the customer-confirmed team plan established a project-management worker role, its `docs/architecture.md` expands the implementation-level structure, role responsibilities, public contracts and collaboration. Follow links to each role's `feature-map.md`, then to its `docs/feature/<feature-id>.md` for purpose, current flowchart, inputs/outputs and history. Each owner updates its own documents after changes; the scheduler coordinates owner updates and delivers links to the current architecture and affected features. No JSON maintenance or HTML-generation step is required.

The old [JSON architecture HTML](references/role-architecture-viewer.md), [Dashboard](references/dashboard.md), project-context queries and cloud tools are legacy opt-ins only. Do not generate missing JSON to satisfy an old viewer. Preserve existing data unless migration/deletion is authorized. If an HTML reading view is explicitly requested, it should read the Markdown documents without introducing a second authored representation; the existing JSON renderer does not provide that capability.

Cloud synchronization remains manual. One project Key stays in private project configuration; uploads and conflicts follow the user's decision. See [dashboard/README.md](dashboard/README.md).

The shared Dashboard may also host an opt-in [role channel](dashboard/README.md#role-channel): each role sends its own task messages and exact permission requests using the project's shared Key and declaring its active role ID. The server checks project scope but does not independently authenticate each role behind that shared Key. Only an administrator login records decisions. A Dashboard decision is not dispatch or mutation authority: continue to enforce customer consent or approved configuration through `task_ops` before any worker activation.

## Role Binding and Handoff

Each conversation or agent context binds to exactly one role before role work begins, and keeps that role for its entire lifetime. Binding survives new turns, task completion, resume and context compaction. Reading another role's card or reports for reference does not activate that role or grant its authority. Do not combine role identities or alternate them through prompts, task labels, or approval.

### Runtime Role Architecture

These are hard rules, not preferences:

1. **The customer window loads only Communication.** The customer-facing conversation stays in the Communication role and never switches to another role for its entire session.
2. **Communication starts the other management roles.** Planning, People Operations, Scheduler and Independent Acceptance are each started by Communication in a separate subagent context when their work is needed. Each handoff passes only the role, its boundary or built-in default scope, the authorization, task inputs and delivery requirements; never the Communication conversation for replay.
3. **The Scheduler is the only dispatch gateway for worker roles.** Development, test, assembly and project-management worker roles are dispatched only by the Scheduler. Communication never assigns work to, authorizes, or starts a worker role.
4. **No role switching.** Never switch roles inside one context, and never let Communication bypass the Scheduler to assign work to a worker role.

For another role, start a fresh independent context with only its assigned role, its accepted boundary or built-in default scope, task authorization, required inputs/contracts and deliverables. Do not fork or replay the coordinator's full role-bearing history as a way to change roles. A reused worker context may receive more work only for its original role and authorized scope. Communication starts the Planning, People Operations, Scheduler and Independent Acceptance contexts; the Scheduler alone dispatches worker roles after that exact role's authorization and scope reservation, and a trusted launcher may only carry out that already-authorized start. Workers return evidence directly to the Scheduler.

### Activation

1. **Load the target role definition.** For a worker role, load its card from `角色卡/<role>/role-card.md`. The role-directory root name follows the project language (`角色卡/` in Chinese projects, e.g. `role-cards/` in English ones); examples use the Chinese form. For one of the five built-in management roles, load its reference document and use its default write scope; no project card or boundary is needed.
2. **Load the mutation scope.** For a worker role, load `boundary.md` Section 1 — this becomes the only mutation authority. For a built-in management role, the reference default scope is the baseline.
3. **Verify authorization and binding:** Confirm the context is unbound or already bound to this same role. Obtain customer consent for the role assignment/task scope or match a preauthorized rule in the designated customer-approved project configuration, as specified in [project-role.md](references/project-role.md). State the role and confirm its loaded scope is the active whitelist. A different role requires a separate context even with customer consent. Writing application code without an active worker role card is a governance violation (Governing Invariant #1).

Activation is the initial binding, not a role switch. All five built-in management roles use their reference default scopes; only worker roles load a project card and boundary. A cross-role request transfers the task and evidence, never the sender's identity or write authority.

### When to Hand Off to a Separate Context

| Current role | Receiving role in a separate context | When |
|---|---|---|
| Customer / Communication | Planning | The customer has confirmed Communication's intent understanding (gate 0); a product proposal, implementation plan, research plan or architecture design is needed |
| Planning | Communication | The implementation plan (proposal plus architecture design), any research plan, shared business contracts and acceptance criteria are ready for the customer's proposal confirmation (gate 1) |
| Communication | Scheduler | The customer has confirmed the proposal (gate 1); the scheduler judges the team and completes the team plan/role assignment |
| Scheduler | Communication | The team plan and role assignment are ready for the customer's role-assignment confirmation (gate 2) |
| Communication | Scheduler | The customer has confirmed the role assignment (gate 2); dispatch may proceed |
| Communication | People Operations | The customer has confirmed the role assignment (gate 2); the confirmed team plan requires new or changed worker roles |
| People Operations | Scheduler | Worker role definitions are accepted and ready per the confirmed team plan |
| Scheduler | Capability / assembly / test / project-management worker role | An authorized and reserved stage is ready |
| Communication | Independent Acceptance | Criteria or current delivery needs judgment; Communication starts the context with the request and evidence |
| Any worker role | Scheduler | Task progress, blockers, evidence or scope requests |
| Any role | Communication | A customer decision, ambiguity or status needs the customer interface |
| Any role | Scheduler | A worker role, ownership or permission definition must change; the scheduler judges it and writes the team plan, then Communication starts the People Operations context after gate 2 |

Each receiver binds directly to its assigned role. People Operations never turns into Communication, and no role turns into another. Communication starts the Planning, People Operations, Scheduler and Independent Acceptance contexts; the Scheduler alone starts worker roles.

The five built-in roles are available immediately; no bootstrap sequence is needed to create them. Communication starts by confirming its intent understanding with the customer (gate 0) and only then starts Planning in a separate subagent context. Once Planning finishes and the customer has confirmed the proposal (gate 1), Communication starts or continues the Scheduler context, which judges the team and completes the team plan/role assignment; Communication obtains the customer's role-assignment confirmation (gate 2). Only when the confirmed plan requires new or changed worker roles does Communication start the People Operations context to write the cards. After those definitions are accepted, People Operations hands back to the Scheduler, which authorizes, reserves and dispatches worker roles. The Scheduler owns each role's task workflow, the project-wide plan, per-role authorization/reservation and global records; Communication owns the end-to-end workflow and the customer relationship; Independent Acceptance judges completion from the planning proposal version. The Scheduler authorizes, reserves and dispatches each worker role directly; workers receive only their own assignment credential. Independent Acceptance holds its separate credential. Existing accepted definitions can be reused. A standalone single-role task may omit scheduling records but still runs in a context bound to its authorized owner and still passes the applicable customer gates. Ordinary members do not dispatch peers, and no role may change its bound identity.

Without subagent tools or capacity, run separate role contexts sequentially and exchange scoped handoffs. If a separate context cannot be started, prepare the handoff, report the pending work, and continue only work belonging to the current role. The customer window stays in Communication; never take over the blocked role's work. Never use in-place role switching as a fallback.

Coordinated tasks use one Git-readable `docs/scheduling/<task-id>.md` record per task. `task_ops` writes its current step table and verifiable event history; each task's prior multi-file JSON records are legacy read-only data. The one approved `.ans/project.json` still defines executable scope. See [task operations](references/task-operations.md) before dispatch or resume.

### Rules

- **One fixed role per context.** The customer window loads only Communication; Communication starts the Planning, People Operations, Scheduler and Independent Acceptance contexts as separate subagents. The scheduler controls the project-wide task graph and authorization and is the sole dispatch gateway for worker roles; it starts a worker only after authorization, scope reservation, implementation confirmation, dependency and conflict checks pass. Communication never assigns, authorizes or starts a worker role. Workers do not assign peers. Each worker uses a separate context bound to its own role. See [scheduling](references/scheduler.md) and [bootstrap scheduling](references/bootstrap-workflow.md#dependency-aware-scheduling).
- **Role activation required before mutation.** Before creating or modifying any file, verify the current role. Built-in management roles operate from their reference default scopes without a project card; worker roles require an active card and boundary. Scheduling records belong to the scheduler's `docs/scheduling/` scope. Application code requires a worker role card and its boundary doc Section 1. Writing application code without an active worker role is a governance violation.
- **No role drift.** When a task crosses role boundaries (e.g., fixing a bug in one capability reveals a governance gap), hold the cross-scope mutation and return it to the scheduler for the responsible owner. The current context remains locked to its role; the other role acts in a separate authorized context.
- **Evidence records its producer and coverage.** Each role reports the actual candidate, tests and observed results. The test role may verify cross-role behavior through read-only source access and its own tests; this grants no production-write authority. A handoff alone does not invalidate evidence; changed inputs or dependencies do. Independent acceptance judges current role-produced evidence; the scheduler releases stages only from matching current pass conclusions; unit results do not replace required integrated verification.
- **Assembly and test roles follow the same activation rules.** Assembly prepares build/test configuration and verifies wiring/startup after its actual dependencies pass, without waiting for unrelated roles. It reads participating roles' `api-spec.md` before wiring; each file still obeys its layer. The fixed test role independently checks cross-role and complete-flow behavior. See [Assembly](references/built-in-assembly.md) and [Test role](references/test-role.md).

## Task Routing

Communication receives the customer request, confirms its understanding of the intent with the customer (gate 0), and only then starts the Planning context; Planning delivers the product proposal, implementation plan, research plan (as needed), architecture design and acceptance criteria. Communication obtains the customer's proposal confirmation (gate 1). Only then does the scheduler judge the team (keep, adjust boundaries, split, add or merge) by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表) and complete the team plan — which roles, who does what, each role's scope and write set — including the assignment when the roster stays unchanged. Communication obtains the customer's role-assignment confirmation (gate 2); role-assignment and boundary changes are confirmed here. When the confirmed plan requires new or changed roles, the scheduler writes the team plan to `docs/scheduling/`, and after gate 2 Communication starts the People Operations context; only then does People Operations write cards or the scheduler dispatch. Same-object, same-version, same-scope confirmation is reusable, but each gate confirms its own object and version. The scheduler then routes work to accepted roles, assesses each affected role's workload, and authorizes/reserves its exact scope before activation. Groups are classification only. A standalone single-role task still needs the customer-consent/configuration check and the applicable gates. Missing worker roles or ownership changes go to the scheduler, which decides and writes the team plan; People Operations executes it after the role-assignment confirmation.

### Routing Sources

The primary routing table is each role's `boundary.md` Section 1. Every file in the project belongs to exactly one role or is unowned. Use targeted source searches, stack traces, and integration contracts to trace dependencies; no code-atlas scan is required.

### Routing Process

1. **Extract file evidence.** From the bug report or task description, identify affected files, error locations, stack traces, or user-visible symptoms. Prefer concrete file paths over abstract descriptions.
2. **Look up the owning role.** Search all `角色卡/*/boundary.md` Section 1 tables for exact files or accepted directory coverage. Resolve ownership conflicts before dispatch; a broader directory grant does not override another owner.
   - **File found** → The scheduler assigns the owner and required scope, then starts that exact role only after authorization and reservation. The worker loads its own role card and follows [Role Binding and Handoff](#role-binding-and-handoff).
   - **File not covered by an exact or directory entry** → it is read-only by default. Report the gap and decide: add to an existing role's Section 1, create a new role, or mark as frozen.
   - **No file evidence** → start investigation from the highest relevant entry point, following the top-down trace in [Workflow](references/workflow.md). Trace relevant callers and dependencies with targeted source searches and contract inspection.
3. **Check cross-role impact.** Check the affected file's relevant callers and dependents in source and the agreed integration contracts. If contained within one role, route directly. If it crosses boundaries:
   - Split the task into independent sub-tasks, each routed to its owning role.
   - Or route the primary fix to the owning role and report cross-role dependencies as follow-up.

### Examples

| Bug report | File evidence | Owning role |
|---|---|---|
| "Order export fails with timeout" | `services/order/export.ts` | 订单服务 |
| "Login page 500 error" | `interface/http/auth.ts` | 用户认证 |
| "Database query returns wrong results" | `providers/database/query.py` | 数据存储 |
| UI crash, no file evidence | Start from the actual entry file → Interface → Pipeline → Service → Provider | Trace and route |

### When Routing Fails

If no worker role covers the file and worker roles have not been established, report the gap to the scheduler. The scheduler judges the team by the [five-dimension standard and decision table](references/scheduler.md#五维判断与决策表) (keep, adjust boundaries, split, add or merge), writes the team plan, obtains the customer's role-assignment confirmation (gate 2), and only then hands it to a separate [ANS People Operations context](#built-in-role-ans-team-formation) for [bootstrap](references/bootstrap-workflow.md) and definition writing. An already-bound context does not switch identities.

## Meeting

Project-wide and cross-group [meetings](references/meeting.md) are hosted by Communication when the customer or an end-to-end workflow decision is involved, otherwise by the scheduler, with the smallest relevant authorized set of roles. Routine tasks do not require meetings. The actual host writes minutes only in its own authorized docs scope, for example `docs/meetings/`. Each participant stays in its own fixed-role context; the host never acts out the other roles. Default to two rounds unless the customer specifies another limit. Record recommendations, unresolved issues, proposed follow-up owners and actual customer decisions separately. Meeting consensus does not grant write permissions or replace any customer gate (intent, proposal or role assignment), proposal confirmation or implementation authorization. This is a skill workflow, not a new CLI command or role.
