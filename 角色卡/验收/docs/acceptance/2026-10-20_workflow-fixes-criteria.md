## 必要完成条件

### WF-01：真实初始化和交接能检出必要文档权限遗漏

真实 `task_ops.py preflight-role --request -` 读取批准配置中完整 `roleDefinitions` 与实际 Section 1，无需 task ID、凭证或已有任务；在 Store／加锁之前分支，不创建任务、runtime、锁或日志。缺项／冲突退出2并指出具体角色、路径和原因；权限齐全退出0。启用登记的新配置在 `init` 复用同一检查，失败不得创建任务。技能规范将其放进形成／调整角色和实际交接路由，不仅提供一条没人调用的命令。

`requiredWorkDocuments` 是精确文件清单，仅核对权限，不授予权限。每个项目角色的 feature-map、memo、functional-description 为 core；有真实跨角色程序能力或装配接口者声明 `apiSpec=required` 并列出实际 api-spec，纯协作角色可有具体职责依据地声明不适用。实际 docs 按职责列出；无直接系统功能者不伪造功能页，未来日期文件仍可按已批准 docs 目录许可入选。文件未创建可报告 `exists=false`，不得把权限完整说成内容已完成。全角色完整性由团队组建交接实际九角色清单、统筹与验收核对；程序不声称自动发现未登记角色。

必须有昨天那类 core／本轮 docs 漏权拒绝、齐全通过、整根过宽、目录包含式重叠、穿越／symlink 保护的真实证据。既有 `test_directory_grant_does_not_cover_sibling_or_broad_root`、`test_overlapping_directory_and_file_ownership_is_rejected`、`test_directory_scope_rejects_traversal_and_symlinks` 回归保持，不能放松源码、common/test 原范围。

Provider／Service 的 abstract、public、impl、契约与相邻层规则保持原约束；本次不新增通用架构扫描器。库存 `test/integration/test_architecture.py` 两方法只验证当前生产源码无三元表达式及直接静态相邻层 public 导入；不证明缺失 abstract/public/impl／契约的机器拒绝，也不把合法正例当成此类负例。与本轮改动无关的通用结构检测不是新完成条件。

### WF-02：仅本角色获准工作文档的精确文件可进入任务

工具允许已在真实 Section 1 获准的本角色根工作文档，以及本角色有界 docs 授权所覆盖的具体文件，进入审核配置 `writeFiles` 和任务 `writeSet`。目录许可只决定文件是否有资格入选，实际任务仍逐文件列出；配置与任务不能写目录通配范围，也不能借目录许可自动增加任务外文件。任务范围只能缩小已确认边界。

所属角色根取完整 `roleDefinitions` 中真实 card／boundary 的共同父目录，二者存在且同父；拒绝重复、相互嵌套角色根及与 roles／acceptanceAuthority 不一致的登记，scheduler 亦须登记。不能用 `roleId` 拼目录或凭中英文目录名猜所有权。有限根工作文件为 feature-map、memo、functional-description 和适用 api-spec；其他允许工作文件是自身 docs 内的精确 Markdown。须有角色 ID 与目录名不同的合法正例，以及伪称自己角色的跨角色负例。没有登记的旧配置维持原范围语义，不自动获得角色文档写权；新能力需新审核配置和新任务。

下列路径仍不能进入普通执行者工作文件写集合：治理角色卡、boundary Markdown 与 YAML、changelog、其他角色资料、`.ans`、正式调度状态和配置中登记的治理文件。自定义文件名或位置不能使已登记治理文件逃过保护；把治理文件塞进工作 docs 目录也不能因此获得普通写权。只读依赖不因禁止写入而一概不可读取。

必须拒绝越出边界或任务清单、同文件／目录包含式跨角色所有权冲突、目录作为精确文件、非规范路径、目录穿越与 symlink 绕过。负例中给出的宽边界或错误登记不构成新授权。拒绝应能定位实际请求路径及原因；不能部分接受非法清单再声称全部获准。

### WF-03：查询者的无关 PATH 变化不替代执行环境

新检查证据使用 `environmentVersion: 2` 与工具生成的私密 `environmentSnapshot:{path,sha256}`。run-check 只捕获一次实际环境，并将其用于解析、固定实际 canonical 程序执行及检查前后身份核对；跟踪键和声明 env 按 D1 第5节限定，不采集完整 os.environ。原值只在工具生成的私密 runtime 快照中，目录0700、文件0600；Git 任务／报告／status 不含私密原值或明文 declaredEnvironment。

完成并经独立验收的同一候选，由执行角色普通终端查询或其他角色消费状态时，若只是调用者 PATH 写法不同，实际被检查的可执行程序路径及内容、声明环境、相关输入和证据都没有变化，`currentAcceptanceValid` 应保持有效，任务完成与依赖放行不因此丢失。status、verify 和依赖消费使用同一重核逻辑，不能出现只在 status 有效的两套判定。

正例须使用真实不同 PATH 和普通 `status` 调用，核实实际执行对象与内容未变；不能要求查询者先抄回旧执行端全量环境才能通过，也不能把查询端的 Python／环境身份直接当作原检查的执行身份。D1 定义如何独立核对执行环境，不由本标准指定存储格式。

允许范围仅限能够证明不影响执行对象的查询环境差异。重核按原快照的跟踪键／absent 语义、执行文件路径与字节、声明环境和相关 readSet；被检查程序的合法符号链接按声明路径解析到同一实际目标校验，项目内输入仍遵守 safe 拒绝 symlink。当前平台／Python 身份变化仍可保守失效，不承诺跨机器复用；间接工具／资源按批准精确 readSet 覆盖，不声称发现所有动态或未跟踪依赖。不得虚构、回填或篡改环境记录来得到通过。

### WF-04：真实相关变化仍使旧证据失效，旧证据不追认

对新版证据，应分别实际证明：被检查可执行程序的路径或内容变化、声明环境变化、相关配置或批准命令变化、候选源码／相关读取输入变化、检查日志或报告证据变化时，旧通过不再对当前对象有效，依赖与任务完成不能继续使用该旧通过。变化原因和需复核对象应可辨认。只证明 PATH 正例不足以完成本项。

执行途中对象或相关环境变化的既有防护仍有效。不能把已记录的失败、超时、缺证或候选变化当通过；不能用放宽断言、权限或日志校验满足本轮标准。对无法确认是否等价的情况可保守失效并说明原因，不要求新增第三种工具状态。

**仅没有 environmentVersion 字段的 legacy 证据走旧 environment 比较。** v2 快照缺失、改动、损坏或形状不符直接当前无效；未识别版本拒绝，不得回退 legacy 或查询者环境。昨天 hash-only 证据不能从哈希还原明细、自动补造快照或追认为新版结果；旧格式保持原语义，换 PATH 仍可能无效。昨天 revision93 在实际跟踪环境中六节点有效、`taskComplete=true`，与普通 root PATH 查询 false 的历史事实均保留。

只有现有状态机允许、仍 active 的 assignment 可重新 run-check。新实际检查环境产生真实新证据后，沿用既有 candidate／attempt 的 report 门禁并由独立验收重新 verify，不能沿用旧 acceptance；不新增通用 report—environment 绑定机制。verified 后 active=false 的节点不能原批次重跑或重开，应使用新审核任务。快照丢失亦不得猜原值恢复。

### WF-05：在库存项目的隔离验证中走通真实文档任务与保护负例

采用 D1 第7节 B：验证根为旧库存内 `validation/workflow-fixes-2026-10-20/`。按 D1 精确清单字节复制原20文件、九实际角色各七输入、原冻结P1/D1/R1/C1/T1、四API与最终快照；原配置仅为 `baseline-inputs/original-project.json`。原件／初始副本摘要相等后，副本治理仅按新验证职责补必要边界与 YAML，分别记录“复制基线”和“治理补权后的执行基线”，不能把获准副本改动判成原件不变或偷偷覆盖基线。不得复制旧任务 state、凭证、私密环境或失败日志到新任务。

源候选两文件字节复制到 `validation-tools/task_ops.py`、`validation-tools/coordination_store.py`，摘要须匹配已审核源候选，实际运行该副本且两文件纳入 readSet；本轮 workflow P1／D1／C1／QA 批准版本亦复制进 root 并绑定，不能拿旧库存方案冒充本轮需求。没有新增检查脚本，文档校验采用审核配置显式 `python -c`，环境负例仅用 D1 三个精确受控夹具。task ID 由实际计划选，不用旧 inventory-full-trial，不预造 token 或批准摘要。

两个必需节点为 `document`／provider-json（唯一 writeSet：`角色卡/provider-json/docs/change/2026-10-20_change_document-probe.md`）及依赖它的 `document-check`／test（唯一 writeSet：`角色卡/test/docs/change/2026-10-20_change_workflow-fixes-validation.md`）。后者 readSet 覆盖前者全部 writeSet/readSet，accept-plan 的 independentTests covers document。两个节点均走过派发、本人 ack、实际 run-check、本人 report complete 和隔离项目独立 acceptance 本人 verify；scheduler 只消费结论。随后普通 PATH 和跨角色状态／依赖消费核对。只调 roles_valid、模拟凭证或开发自报不能代替真实流程。

document-check 使用原六组检查入口在副本 cwd 新跑60方法：model7、provider7、service10、cli21、assembly6、integration9，不重复累加。其报告自身先写完并冻结，再正式运行六项 run-check／report／verify，避免后写报告改变 writeSet 候选；如有实际改动，重取受影响证据。详细输出留工具日志，后续结果引用不回写被冻结报告。库存60项不能代替源工具自身单元与独立 CLI 回归。

独立测试角色还须实际验证源 CLI 中跨角色／治理／目录保护与 WF-01 至 WF-04 边界；破坏性负例隔离。原库存批准、revision93任务、全部 runtime 日志／失败历史、20文件、角色定义和 observed 私密快照保持原字节。获准准备／收尾操作在副本 root 外只读取得原项目保全摘要；root 内检查只读复制 manifest 及 root 内载荷，不能越根，也不声称一直证明父根实时未变。新增范围单独列出；发现旧文件变化停止报告，不回写掩盖，不把旧历史通过当成本轮新回归通过。

### WF-06：当前产物、原始证据和角色职责可相互核对

实际改动位于各执行角色当前 Section 1 及本次获准精确范围内；三个问题均有必要工具改动、对应开发检查和固定测试的独立完整流程／回归证据。技能说明、工具指南和相关当前功能说明由原所有者同步为实际行为，不能把计划写成已实现。

开发、规范维护、固定测试、独立验收和统筹结论保持区分。独立测试报告应指向同一最终工具候选、批准输入、实际命令与环境、检查输出和真实失败历史；源码、规则或相关输入变更后重取受影响证据。凭证不得进入公开报告或仓库。调度者不能自行 `verify`，开发者自测不能替代固定测试，任何角色自报都不替代本角色独立判断。

验收结果须逐项说明版本与原始证据，采用“通过／返工／证据不足”。检查缺失、候选不符或无法确认时不判通过。安装、public 镜像、发布、推送及对旧库存内容的迁移不属于本轮完成条件。

`document` 的逐项 `pass` 只表示本表左列的阶段交接条件达到；`document-check` 及最终完整目标还须右列全部满足。独立验收据实给逐项及总“通过／返工／证据不足”，不在实施后临时把欠缺项改为“不适用”。全部必需节点须有当前有效独立通过，源修复最终结论还须源QA完整证据和原项目收尾保全；不能仅用副本任务的 taskComplete 宣称源修复全部完成。

## 可供审批状态及剩余交接

本标准已吸收 D1、两位 owner 和 QA-T1-draft-1 的本轮必要意见，**标准可供客户审批，非成果 pass**。没有待客户另选的新增功能或选装，也没有新增测试模块、架构扫描器、状态机重开或通用报告绑定要求。

当前 D1 所读正文仍有两项 owner 已明确的小修措辞和 QA Q1–Q4 待 PM 同步：legacy 仅无版本字段、v2坏快照直接无效；换环境须服从 active／verified状态机及既有report门禁；复制双基线、本轮批准输入根内承接、根外保全证明界限、报告先固定再正式检查。以上在本标准已经明确，PM按同一技术约束同步即可，不需为文档摘要相互变化再开审稿轮。

实际批准时应一并呈现 P1、D1最终正文、本 C1、QA验证设计及精确源／新根范围。客户确认并指令实施、治理落实精确副本权限、统筹固定实际配置／输入、可信端独立交付凭证后才可 init／accept-plan／派发。没有测试结果，没有成果验收结论，结果文件尚未创建。
