# 验证项目工程法案与角色备忘录指南

本设计检查新指南能否指导角色在真实项目状态下作出正确判断，并核对指南接入后相关入口、权限和产品文档是否连贯。目标依据是[已确认方案](../../../../doc/design/2026-10-10_design_project-plan-role-memo.md)和[项目管理评审](../../../../角色卡/项目管理/docs/design/2026-10-10_design_project-rules-memo-review.md)。本测试角色只维护本验证设计与报告；不会修改技能产品、其他角色资料或测试源码。

## 对象与依据

待核对的指南为仓库 `references/project-rules.md` 和 `references/role-memo.md`。产品事实还要对照 `SKILL.md`、`SKILL.zh.md`、`README.md`、角色模板与初始化、项目管理、测试、文档规则，以及本项目的 `角色卡/项目管理/docs/project-rules.md`、`docs/architecture.md` 和各角色卡、边界。规则的生效状态以文档明示状态和用户已确认依据为准；本项目现有法案是项目级实际例子，不能反推所有外部项目都采用同一组工程约束。

需要核对的新产品功能文档与历史记录路径来自技能规范角色边界：`角色卡/技能规范/docs/feature/project-rules-memo.md` 与 `角色卡/技能规范/docs/change/2026-10-10_change_project-rules-memo.md`。文件不存在时记作缺失或待交付，不能用指南本身代替功能说明，也不替规范角色创建或修复它们。

## 场景验证

对指南逐项做桌面推演。每个场景记录输入状态、角色应采取的动作、预期产物或判断、实际指南依据和结果。只在隔离临时目录生成最小测试夹具；夹具不得带入仓库，不编辑源码或他人资料。

| 场景 | 初始状态与触发 | 预期判断与行为 | 重点失败信号 |
| --- | --- | --- | --- |
| 已有已确认法案 | 项目中有明确生效状态、维护者和授权路径的法案；角色接到相关实现任务 | 所有角色读取同一实际文件；只应用相关条目，报告可引用规则编号和检查依据 | 角色复制一份法案、把草稿当生效规则，或从法案推导写权限 |
| 只有草稿或没有法案 | 项目管理法案标为 draft，或文件缺失；角色需要开始获授权的工作 | 如实报告状态/缺失；不把工作自动阻塞，不虚构项目要求；继续遵守通用规则及已确认约定；无文件时管理角色完成建卡和边界后再调查整理 | 将草稿当作全局强制规则、声称文件存在，或无依据地停止工作/编造规则 |
| 角色续接发现旧笔记 | 续接同一角色任务，memo 含旧线索、过期线索或未核实判断 | 先读取自己的 memo；区分事实、待核实和已解决线索，复核相关法案；删除过期内容或链接历史，不沿用失效判断 | memo 取代正式法案、续接不读 memo、把推测写成已确认事实，或把它变成第二份 changelog |
| 新发现影响多个角色 | 执行角色发现可能改变多个角色做法的工程要求 | 先记录事实和影响，交项目管理评审；管理角色按已有确认流程更新唯一法案并通知受影响角色；memo 只留下本角色线索 | 发现者自行把 memo 提升为规则、直接修改他人 memo/法案，或遗漏受影响角色 |
| GUI 线程规则的具体作用域 | 提案采用 GUI；示例描述事件回调、渲染循环、主线程回调中的同步阻塞 I/O/重计算 | 只有确认项目确用该线程模型、规则状态生效且作用范围被写明时才执行；实现办法说明异步 I/O 与后台计算、结果回主线程；检查实际调用位置和交互响应；仅 `async` 不足以证明重计算移出主线程 | 将示例推广为所有项目规则、没有范围或检查办法仍称可验证、运行未经证实的代码并声称通过 |

再检查角色会提出的歧义：项目管理尚未建立时谁负责法案、发现冲突时是否可顺手重构、没有自动检查器怎样报告、memo 是否授权修改文件、实质法案变更是否需要设计/change 历史与通知。答案必须能从指南和现有治理约定找到，不靠测试者补规则。

## 文档与权限核对

检查英文与中文技能入口、README 的使用流程是否指向新指南；角色模板和初始化资料是否让项目管理、开发、装配、测试等每个适用角色都能找到“当前法案”和“自己的 memo”，并能在开始/续接时按需读取。检查角色卡的必读列表是否有明确接入点，项目尚无法案时是否不制造先有鸡蛋要求。

逐一核对真实 Markdown 链接的目标存在、相对路径正确；尤其检查上述功能文档和变更记录是实际产品链接，不能只链接方案或管理评审。对没有直接产品功能的测试角色，feature-map 只说明无直接业务功能，并导航到真实法案、指南和受测功能入口，不复制流程。核对法案维护者为项目管理、memo 由各角色维护、指南由技能规范角色维护、角色卡/边界由 Governance 维护；任何文档均不得扩大 Section 1 权限。

核对项目主方案回答“做哪些目标、选择什么路线、怎样推进”，工程法案回答“项目角色怎样组织工程实现”，架构说明回答“当前组成、职责、模块关系和交接”，功能说明回答“用户触发后实际流程”。主方案及管理评审应互相链接；不能把项目目标塞入法案，也不能把技能指南任务画成已交付的业务架构或功能实现。若架构图承担本轮分工说明，核对它与功能任务、角色边界、评审状态一致。

## 实际验证步骤与报告口径

收到规范角色交付后，固定候选版本并记录仓库状态。先检查两份指南及入口/模板/产品文档，再按上表逐个推演；之后对相关 Markdown 链接、YAML front matter 和代码围栏做实际文件检查。链接检查应以仓库根目录解析相对链接，跳过外部 URL、锚点和代码围栏中的示例，并报告例外。YAML 检查说明所用解析器；如解析器缺失，改做有限手工检查并如实说明，不称完整 YAML 验证通过。代码围栏核对开闭与示例内容边界，不把 GUI 样例运行当成指南验证。

验证结果分为：文档/静态检查、场景推演、真实应用行为测试。前两项只有实际执行并记录输入和结果后才能报告；GUI 响应、线程调度、业务性能与实际用户流程不在本轮已安排的代码运行范围，除非后续明确安排对应系统实测。不要把 Markdown 链接有效或情境推演通过表述为运行时性能已验证。本设计已按首轮及维护者修正后的候选文档执行；各阶段结果、证据和状态区分记录在[最终验证记录](../change/2026-10-10_change_project-rules-memo-validation.md)。场景推演与静态文档检查不代表 GUI、线程调度或性能行为实测。
