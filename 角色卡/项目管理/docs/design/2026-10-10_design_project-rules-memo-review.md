# 增加一份共同工程法案，各角色记住自己的工作线索

用户已明确：项目法案是全局工程约束，例如主线程职责、代码组织和资源处理；随后要求“委派角色去开发这个”。本轮按[修订方案](../../../../doc/design/2026-10-10_design_project-plan-role-memo.md)实施技能文档更新。

## 评审结论

建议通过，实施范围已被本轮用户指令覆盖。新增 project-rules 指南与 role-memo 指南，并接入技能入口、初始化、角色模板、评审与测试说明。具体项目的工程约束仍按实际环境及已确认要求编写；GUI 线程例子只是写法示例，不能批量变成所有项目的强制规则。

这份评审由项目管理完成，不是替开发者转发方案。主要判断是：项目法案补充通用技能的项目细节，memo 帮助独立角色续接，现有功能、任务与历史文档保持各自用途，避免同一规则出现多个来源。没有新增后台程序或存储机制，也没有选装项。

## 实际分工

| 固定角色 | 本轮交付 | 边界依据 |
| --- | --- | --- |
| ANS Governance | 建立三个本轮角色卡与准确文档白名单 | 内置治理职责与用户本轮委派指令 |
| 项目管理 | 评审、本项目既有工程法案、架构说明和自己的备忘录 | 本角色 boundary.md |
| 技能规范 | 产品指南与模板更新，当前功能说明、修改历史及自己的 memo | 技能规范 boundary.md |
| 测试 | 独立检查链接、职责与规则衔接，使用隔离场景验证新指南的可用性 | 测试 boundary.md |

规范与测试均通过独立上下文承接，互不扮演对方。治理上下文继续只负责卡与边界；管理上下文保持管理身份。用户的授权限于这轮工作，不是永久自动派发授权。

当前角色文件是针对这轮任务的实际定义。以前六角色划分的其他能力仍是候选，未在本轮全部启用。产品通用指南说明各种项目怎样做；本项目法案只整理 ANS 已确认的约束。新法案文档不会扩大任何角色的改文件权限。

## 需要特别核对

- 所有角色读取同一份项目法案，草稿、已生效约束和建议分清。
- memo 记录有依据的事实与待办，不自行生成全局规则，不抄任务状态或完整历史。
- 初始化时项目管理尚未建立，不要求它先完成法案；权限建立后再整理和确认项目级工程要求。
- 角色在自己的上下文中修订内容，发现跨角色冲突交管理处理；现有独立角色、会议、方案评审规则继续有效。
- 这里只更新技能说明与本轮角色资料。检查文档正确不等于已经在真实业务运行环境证明所有约束有效。

## 当前状态

规范实现已交付，独立测试检查了五类情境及实际文档链接、围栏与元数据。首轮发现的评审 events 缺项及过期状态由各自作者修正，最终复核已确认关闭。详细结果见[独立测试记录](../../../测试/docs/change/2026-10-10_change_project-rules-memo-validation.md)。这是指南与资料验证，未实测 GUI 线程、应用行为或性能。用户随后授权更新 README 并发布到 GitLab/GitHub；实际发布结果以 Git 提交和远端核对为准，本节不把安装替换或服务器部署当成已经授权。

管理侧另外核对当前工作区 39 个改动文档，各有唯一的实际写入负责人，270 个本地链接和锚点有效。官方 skill-creator `quick_validate.py` 在当前 Python 中因缺少 PyYAML 没有成功运行；不能算作通过。文档元数据用独立测试记录中的 Ruby/Psych 解析；补查发现并修复了当前功能文件缺少必需头部的问题，测试角色已复核字段、唯一 ID 和功能/修改记录的双向关联，未留未关闭项。
