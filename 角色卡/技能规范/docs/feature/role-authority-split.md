# 沟通、策划、人事、统筹与独立验收

使用者把请求交给沟通后，沟通先把需求写盘到 `docs/communication/` 并交策划；策划写产品方案、架构设计、共有业务契约和可核对的完成标准；统筹据方案和架构判断团队，需要新招或拆分时把团队计划写入 `docs/scheduling/`，交人事（原团队组建/招募）按计划写/改 worker 角色卡和边界；客户经沟通确认方案并授权实施后，统筹再逐角色派发。文件真正的所有者实施，测试实际运行检查，独立验收按同一版策划方案判断是否达到事先约定。安排工作的人不能自己宣布验收通过；角色不能写自己的角色定义。项目管理只在统筹团队计划建立时承接已确认架构做实现设计和技术评审，不是默认架构所有者。

本页的 `implemented-unverified` 表示规范文本已同步，独立测试和验收尚待交付。任务程序的分权接口见[本轮设计](../../../项目管理/docs/design/2026-10-19_design_role-authority-split.md)与按实际代码核对的[任务操作指南](../../../../references/task-operations.md)；开发和独立测试原报告提供实际执行事实，最终结论由独立验收自己的报告给出。接口存在、文本交付与验收通过分别记录。

## 使用时怎样交接

| 使用者遇到什么 | 谁处理，交出什么 |
| --- | --- |
| 新项目缺角色，或已有角色范围不足 | 统筹判断团队并把团队计划写入 `docs/scheduling/`，内置 ANS 人事（原团队组建/招募）只按计划建立或调整 worker 角色卡和边界 |
| 新请求不清楚影响谁、要先做什么 | 方案和架构完成后，统筹调查受影响角色、工作量和依赖，直接逐角色安排 |
| 需要说明问题、用户目标、完整产品流程与范围 | 独立策划在自己的文档范围形成产品/需求方案、架构设计和共有业务契约，并写明可核对的完成标准 |
| 架构设计、抽象或共享代码需要改变 | 架构设计交策划；如统筹按团队计划建立了项目管理（技术架构）角色，由该角色在已确认架构下做实现设计、技术评审，并维护自身 shared 和对应测试；未建立时不虚构该角色 |
| 要知道实现是否真的运行 | 开发、装配和测试按各自职责做真实检查，交原始证据 |
| 要判断这次能否算完成 | 独立验收按同一版策划方案先明确标准，再核对当前版本与证据，判通过、返工或证据不足 |

```mermaid
flowchart TD
  input[用户把请求交给沟通] --> intake[沟通写盘 docs/communication/ 并交策划]
  intake --> planning[策划写产品方案、架构设计、共有契约与完成标准；已有同版方案复用]
  planning --> judge{统筹判断团队：现有角色和范围够吗}
  judge -->|够| consent
  judge -->|不够| formation[统筹把团队计划写入 docs/scheduling/，人事只按计划建卡或调边界]
  formation --> preflight[按实际登记和Section 1运行只读preflight-role]
  preflight --> complete{文档许可完整且无冲突吗}
  complete -->|否| formation
  complete -->|是| consent[沟通取得客户确认和实施授权；同版同范围授权复用]
  consent --> criteria[独立验收按同一版策划方案明确完成标准]
  criteria --> assign[统筹逐角色授权、范围预留并开独立固定上下文]
  assign --> work[所有者实施和自测；装配与测试运行所需检查]
  work --> evidence[原始报告直接回统筹，独立验收只读核对]
  evidence --> verdict{当前成果达到标准且证据有效吗}
  verdict -->|达到| pass[验收通过；统筹按依赖安排后续或交付]
  verdict -->|有明确差异| rework[验收返工；统筹安排原所有者修复和复测]
  verdict -->|无法判断| missing[验收证据不足；统筹安排补证，不记完成]
  rework --> assign
  missing --> work
```

每个上下文固定一个角色。人事承接原治理身份，不是新组长或 PM 附带职责；五个内置管理角色不需要项目卡和边界，worker 角色才需要在项目中落成具体卡与边界。`group` 只分类，不保留组长、组内职责或中间汇报层。统筹直接派发并收每个角色原始反馈；小任务不要求全部角色开会，也不要求一直并发运行所有角色。

## 文档权限先检查，再按任务精确选文件

建立或调整角色后，人事按团队计划提供完整 roleDefinitions 登记内容与权限定义；五个内置管理角色按各自参考文档和默认范围登记（包括不执行的统筹、策划与验收），不另建项目卡；若计划建立了项目管理角色，也一并按 worker 角色登记。已接受统筹在自身边界内落候选配置，原owner按真实职责核对requiredWorkDocuments。默认是自身feature-map、memo、functional-description；有实际对外程序/shared能力或装配接口才要求api-spec，否则明确有据不适用。没有系统功能或代码就直说；协作角色说明真实交接与文档位置，不虚构代码层。

新项目不需要先接受统筹定义：统筹是内置角色，由独立固定统筹上下文仅做配置准备；已有项目由原统筹写候选配置。配置具备后运行只读预检，齐全后再交接/派发其余实际工作；治理不取得配置写权。按此顺序运行[实际preflight-role入口](../../../../references/task-operations.md)，读真实card/boundary共同父目录与Section 1，不按roleId拼路径，不创建任务、runtime、锁或日志。返回具体角色、文件和问题；缺权由统筹写入团队计划、交人事修正并重查。尚未创建的文档可报告exists=false，不等于没有创建许可，也不意味着已写完。成功不代替客户批准、派发或验收。工具核登记，人事/统筹/验收另对照实际角色清单核完整性。

清单只检查许可，不授予写权。执行文件仍取自身有限根工作文件或有界docs、实际Section 1、审核配置精确writeFiles、节点精确writeSet的交集。目录许可不等于本次允许修改整个目录；未来日期文档不必全在初始化清单中。card/boundary/YAML/根changelog由治理独占，owner历史写自身docs/change或fix；其他角色、.ans与调度状态继续保护。统筹合法管理范围参与所有权核对，状态实际变化仍只通过task_ops。旧配置申请新增角色文档能力须新审核配置及新任务。

## 查询时核对原检查环境

新环境证据v2把最少原执行环境保存在私密runtime快照，任务只存摘要和执行身份。status、verify和依赖消费重核该快照、实际程序、候选/readSet和日志，查询者无关PATH变化不推翻相同实际对象。真实程序、批准环境/配置、源码资源或证据变化仍失效，快照缺坏也直接当前无效；不能回退查询者环境或补造快照。

没有environmentVersion的legacy仍保留原比较语义，不追认旧哈希。仍active的获准assignment可真实补检查并接受独立重新verify；verified批次要换环境须新审核任务，不新增状态或通用报告绑定系统。动态未声明外部依赖并未自动覆盖，必要变量和资源仍显式放check.env/readSet。字段、私密权限及局限以[任务操作指南](../../../../references/task-operations.md)为准。

## 可照做的请求

> 使用 $ans-governed-construction，调查保存草稿失败，先写方案。请按现有角色直接安排，明确怎样才算完成。

沟通先接单并写盘；后续新需求交策划写问题、目标、完整产品流程分支、输入输出、范围、选项、架构设计和共有契约。统筹据此判断团队，需要时把团队计划写入 `docs/scheduling/` 交人事按计划建卡或调边界；客户经沟通确认方案并授权实施后，相关所有者写自己的具体提案并按团队计划审核（如已建立项目管理角色，由它做实现设计和技术评审）。已有同版方案和授权直接复用，本轮原技术方案不补造成策划产物。独立验收按同一版策划方案明确必要成功/失败场景与证据，统筹再给具体角色授权和预留。失败或缺证据原样保留，由正确的角色补做；不用统筹换身份修代码或验收。

新项目由沟通接单交策划，统筹判断团队后按需交人事建立 worker 角色，再交接。旧项目须显式盘点角色、配置、活动任务和凭证并迁移；旧 PM 上下文不能默默变成统筹或验收，旧完成记录也不追认为独立验收通过。详情见[人事](../../../../references/team-formation.md)、[统筹](../../../../references/scheduler.md)、[策划职责](../../../../references/planning-role.md)、[按需建立的项目管理职责](../../../../references/project-role.md)及[独立验收](../../../../references/acceptance-role.md)。
