## 2. 判断结论

### 2.1 工作流判断：已不再是可以直接落地的单一规则修正

第一轮的单一缺陷快速通道，原则上可以在既有角色边界内由技能规范与人事直接完成规则文字修改。但第二轮把范围扩展为四类工作、五条转换、判定权、闸门、证据、验收与失效规则的完整流程模型，已构成技能产品/流程的方案级变更：

- 它改变的不只是一句“缺陷可以快”，而是四类工作的成立条件、判断归属、闸门顺序、转换授权、验收基线和证据失效规则；
- 其中“变更必须回到策划方案与闸门 1”“重构必须做结构设计/方案确认”“转换必须显式停止、记录、重新分类并取得对应客户授权”等规则，需要策划在方案中统一定义，不能由实施角色边写边定；
- 现行技能规则明文要求：新增产品/流程方案由策划写，客户在闸门 1 确认的那一版是实施方案和验收基线；统筹不写实施方案或调研方案；
- 因此，**正式团队计划与派发的前置条件是：沟通写盘意图并取得闸门 0 确认 → 策划写四类工作流程方案 → 同一策划角色独立只读复核 → 客户闸门 1 确认 → 统筹冻结正式团队计划 → 客户闸门 2 角色指派确认 → 客户实施授权**。

本文件第 3、4 节给出的是候选模型约束、候选分工和候选写集，供策划方案与客户确认使用，不是最终规则。

### 2.5 必须保持的不变量

1. 三道客户闸门（0 意图、1 方案、2 角色指派）仍然只由客户通过沟通确认；默认勾选、团队共识、方案已写完、工具成功和沉默都不算同意。
2. 五个内置管理角色不增不减；角色保持平级；组别只作分类。
3. 统筹是工作角色的唯一调度口；沟通不得直接给工作角色派活、授权或启动。客户原话中的“让沟通……让指定角色去修复”按沟通→统筹→指定角色执行；如果客户要求沟通直接派发，属于权限变更，须另行确认。
4. 一个上下文只能绑定一个角色，禁止切换；主上下文不得直接修改技能文件，技能改动必须由固定角色完成。
5. 角色/边界变化仍走闸门 2 和人事；任何角色都不能借本计划扩大自己的 Section 1。
6. 不修改任何程序权限、任务状态、验收凭证或已安装技能副本。
7. 验收基线、风险档位和证据失效仍按 `references/testing.md` 与 `references/acceptance-role.md` 的现行口径执行；四类工作的差异由策划方案细化，不另造第二套定义。

### 3.1 客户已固定的约束（不得省略）

| 编号 | 约束 |
| --- | --- |

| K2 | 新建走完整方案与闸门；不得用快速通道代替。 |
| K3 | 修复只对“已确认行为内的缺陷”走窄快速通道；不得借修复之名改变已确认行为或扩大范围。 |

| --- | --- | --- | --- |
| 新建 | 客户提出新的目标/行为/契约；现有已确认行为不包含它；通常需要新方案、架构、契约、文件或角色能力。 | 沟通确认意图（闸门 0）；策划写方案与架构；统筹判断团队；客户闸门 1/2。 | 若只是现有行为偏离，降为修复；若只是需求调整，降为变更；若只是内部结构问题，降为重构。 |
| 修复 | 已确认行为/契约存在，实际结果偏离；不新增行为、不改公开契约、不新增边界外文件；有唯一所有者（Section 1 可定位）；修复范围在该所有者边界内。 | 验收/客户/角色报告发现；所有者判断技术性质是否在已确认行为内；统筹判断归属与边界；沟通记录客户指令。 | 若需要改变已确认行为/契约/新路径，停止修复，转为变更或新建；若暴露结构问题，转为重构。 |
| 变更 | 原要求被判定不合理、不够或客户要求改变已确认行为；修复无法在已确认行为内解决。 | 所有者提出发现；策划判断是否属于需求/架构变更；统筹停止当前通道并记录转换；沟通取得客户授权；客户闸门 1。 | 若只是实现缺陷，回到修复；若结构无法承载，转为重构。 |
| 重构 | 现有结构难以承载已确认或拟变更的需求；需要内部结构设计；不得静默改变已确认外部行为。 | 策划/项目管理（技术架构，如已建立）判断结构承载性；统筹判断团队与依赖；客户确认结构设计/方案；涉及角色/边界时闸门 2 + 人事。 | 若只是局部缺陷，回到修复；若需求本身变化，回到变更；若形成新能力基础，后续按新建走完整流程。 |

**判断权边界（候选）：**

- 沟通只记录和转达客户意图，不判断技术性质，不判定“是不是缺陷”。
- 验收只判断当前成果是否满足确认标准；发现问题时报告触发事实，不改标准、不扩大需求、不自行重新分类。
- 统筹判断归属、路由、闸门适用性和团队计划；不判断产品/技术方案优劣。
- 策划判断原要求是否不合理、结构是否难以承载，并写对应方案；项目管理（如按计划建立）判断实现层结构可行性和技术契约。
- 客户确认闸门与转换授权；任何角色都不能代替客户同意。
- 不允许任何角色在同一任务里默默改变分类；转换必须按第 3.5 节显式执行。

### 3.3 流程与闸门（候选）

| 类型 | 必要流程 | 闸门 | 交付与授权 |
| --- | --- | --- | --- |
| 新建 | 沟通接单写盘 → 闸门 0 → 策划方案（产品/实施/调研/架构/契约/验收标准）→ 同一策划角色独立只读复核 → 闸门 1 → 统筹团队计划 → 闸门 2（角色/边界变化时）→ 客户实施授权 → 派发 → 证据 → 独立验收。 | 0 → 1 → 2（按需） | 方案版本、复核记录、团队计划、实施授权、变更包、验收结论。 |
| 修复 | 沟通记录缺陷与客户指令 → 统筹按 Section 1 确定所有者并检查边界/依赖 → 直接派发所有者 → 所有者在边界内修复并写修复记录/证据 → 独立验收按缺陷基线判断 → 通过则放行，失败则返工。 | **跳过闸门 1 和闸门 2**；保留闸门 0 的轻量意图确认/客户缺陷指令记录。 | 缺陷记录、所有者任务、修复记录、证据、验收结论；不改角色定义，除非重新分类为变更/新建。 |
| 变更 | 显式停止当前通道 → 记录触发事实 → 策划变更方案（产品/实施/调研/架构/契约/标准）→ 复核 → 闸门 1 → 统筹团队计划 → 闸门 2（角色/边界变化时）→ 实施授权 → 派发 → 验收。 | 0 → 1 → 2（按需） | 变更方案、复核记录、团队计划、实施授权、新基线、验收结论；旧行为证据失效。 |
| 重构 | 显式停止当前通道 → 记录触发事实 → 结构设计/方案（策划负责流程/产品结构；项目管理负责实现层结构，如已建立）→ 独立评审 → 客户方案确认 → 统筹团队计划 → 闸门 2（角色/边界变化时）→ 实施授权 → 派发 → 回归证明外部行为保持（除非方案明确改变）→ 验收。 | 方案确认（结构设计）+ 闸门 2（按需）；外部行为不变是默认约束。 | 结构方案、评审记录、团队计划、实施授权、回归证据、验收结论；受影响调用方证据失效。 |

**修复类窄通道的边界（候选）：**

- 只适用于“已确认行为内的缺陷”：预期行为已经存在并被客户确认（产品方案、既有契约、既有验收标准或客户明确的缺陷说明），不是新行为。
- 不新增公开契约、不新增边界外文件、不改变角色/边界、不改变验收标准。
- 修复记录写在该所有者已获授权的路径；如果该路径未在 Section 1 中（例如技能规范当前只有一份历史 `docs/fix/` 精确文件），必须由人事按计划增加精确路径，或改记在已授权文档中；不得直接写未授权路径。
- 修复失败两次、或修复中发现原要求不合理/结构问题，必须停止并重新分类，不能继续“修到通过”或扩大范围。
- 修复不要求策划方案、不要求团队计划、不要求闸门 2；但仍要求客户明确的缺陷指令/意图记录、所有者边界内写入、证据和独立验收（如已授权）。

### 3.4 验收基线、风险档位、返工/复验（候选）

| 类型 | 验收基线 | 风险档位 | 返工/复验 |
| --- | --- | --- | --- |
| 新建 | 客户在闸门 1 确认的同一版策划方案（产品方案 + 架构 + 契约 + 可验收标准）。 | 按 `references/testing.md` T0–T3；涉及治理/权限/共享抽象为 T3。 | 验收失败交原所有者；方案实质变化重开闸门 1；受影响证据失效。 |
| 修复 | 客户确认的缺陷意图/预期行为 + 已确认行为/契约 + 修复记录与证据；不是新的闸门 1 方案。 | T0–T3；纯文档修复可为 T0/T1；治理/权限修复为 T3。 | 同一所有者修复；复验受影响路径；同一候选、输入、依赖和命令的证据可复用；失败两次或发现需求/结构问题则重新分类。 |
| 变更 | 新闸门 1 确认的变更方案版本。 | 按 T0–T3；行为/契约变化通常 T2，治理/权限为 T3。 | 按新方案返工；旧行为证据失效；未受影响部分可复用。 |
| 重构 | 客户确认的结构方案 + 默认保持的已确认外部行为/契约。 | T2/T3；共享结构、跨角色或治理变化为 T3。 | 回归证明外部行为保持；隐藏缺陷按修复处理；范围扩大重新分类；受影响调用方证据失效。 |

**统一规则：**

- 风险档位不新增第二套定义，仍以 `references/testing.md` 的 T0–T3 为唯一口径；四类工作只做映射和补充说明。
- 转换时旧证据是否失效按“候选、输入、依赖、契约或确认版本是否改变”判断；受影响的证据必须重跑，不受影响的可复用。
- 独立验收只按客户确认的同一版方案/缺陷意图判断，不自造标准、不增加需求、不把返工说成通过。

### 3.5 转换规则（候选）

| 转换 | 触发事实 | 必须动作 | 授权与证据 |
| --- | --- | --- | --- |
| 新建 → 修复 | 验收发现交付成果不满足已确认标准。 | 停止“新建完成”结论；记录失败标准、证据和候选版本；重新分类为修复；若在已确认行为内走窄通道，否则转变更。 | 客户缺陷指令/闸门 0 记录；旧证据只对未受影响部分有效；修复证据覆盖失败标准。 |
| 修复 → 变更 | 修复中发现原要求本身不合理、不够或客户要求改变行为。 | 停止修复；记录触发事实；交策划写变更方案；重开闸门 1；不得继续按修复硬改。 | 客户通过闸门 1 确认新方案；旧修复候选和受影响证据失效。 |
| 变更 → 重构 | 变更方案发现现有结构难以承载。 | 停止变更实施；记录触发事实；做结构设计/方案并取得客户确认；涉及角色/边界走闸门 2 和人事。 | 客户确认结构方案；旧变更实施证据对重构路径失效。 |
| 重构 → 修复 | 重构过程中暴露隐藏缺陷。 | 停止重构；记录触发事实；重新分类为修复；仅在已确认行为内和已确认重构范围内走窄通道，否则转变更/新建。 | 客户缺陷指令；修复证据覆盖缺陷；不得借机扩大重构范围。 |
| 重构 → 新建 | 重构形成可扩展基础，支持新能力。 | 停止把重构当作新能力授权；按新建完整流程重新走闸门 0/1/2。 | 客户新建方案确认；重构确认不代替新建方案确认；复用已验证基线。 |

**转换通用规则：**

1. 每次转换必须显式停止当前通道，不能边做边换名。
2. 必须记录触发事实：发现了什么、依据哪条标准/证据、当前候选版本、为什么原分类不成立。
3. 必须重新分类，并按新类型取得对应客户授权（修复的缺陷指令、变更的闸门 1、重构的结构方案确认、角色/边界的闸门 2）。
4. 不允许沿用旧授权覆盖新范围；不允许在同一任务里默默扩大范围。
5. 转换记录写入沟通记录（客户授权）和统筹的 `docs/scheduling/` 记录（停止、分类、依赖和证据状态）；不写其他角色文档。
6. 旧证据按“候选、输入、依赖、契约、确认版本是否改变”判断失效；受影响的重新取证，不受影响的按 `references/testing.md` 复用。

### 6.3 最小可执行授权建议

按以下顺序，每一步都以客户明确同意为条件；任何一步缺失都停在该步，不提前派发：

1. **沟通写盘 + 闸门 0**：沟通在 `docs/communication/2026-11-03_communication_four-work-types.md` 写清四类工作、转换链、闸门、证据与不变量的意图理解，交客户确认。
2. **策划方案**：客户确认闸门 0 后，策划在 `角色卡/策划/docs/design/2026-11-03_design_four-work-types.md` 写方案；同一策划角色独立只读复核并写复核记录；作者逐项处置。
3. **闸门 1**：沟通把方案、复核记录和处置摘要交客户确认；客户明确确认方案版本。
4. **正式团队计划 + 闸门 2**：统筹把本计划冻结为正式团队计划（含精确写集、边界批次、依赖、验证和风险）；沟通交客户确认角色指派与写集。
5. **实施授权**：客户明确授权本轮文档与角色定义实施范围；不含代码、测试、站点发布或已安装技能副本。
6. **人事边界批次（如需）**：客户确认后，人事先补四个文档类型指南的精确路径（A13/A14），再执行角色定义批次（A1–A12）。
7. **技能规范实施**：在边界补齐和闸门 2 后，技能规范按确认写集实施 S1–S10；S11–S14 仅在边界补齐后实施。
8. **验证与验收**：技能规范和人事自检；统筹核对写集和一致性；如客户要求，独立验收按 B1/B2 判断；未要求则披露验收缺口。
9. **放行**：只有匹配当前候选的验收通过（或客户明确的例外放行）才记录完成；返工交原所有者。

### 6.4 如果客户坚持“不改任何角色边界”的替代方案

如果客户坚持第一轮的“不改任何角色边界”口径：

## 7. 依赖与执行顺序

```text
客户两轮原话（已转达）
  → 沟通写盘意图（C1）
  → 闸门 0 客户确认
  → 策划方案（P1）+ 独立只读复核（P2）+ 作者处置
  → 闸门 1 客户确认
  → 统筹冻结正式团队计划（本文件更新）
  → 闸门 2 客户确认角色指派与写集
  → 客户实施授权
  → 人事边界批次（A13/A14，如需）
  → 人事角色定义批次（A1–A12）
  → 技能规范共享文档批次（S1–S10）
  → 技能规范类型指南批次（S11–S14，仅在边界补齐后）
  → 验证/独立验收（B1/B2，如授权）
  → 统筹放行
```

- 人事和技能规范的写集不相交，可在边界批次完成后并行或顺序执行；同一文件不能同时有两个写入者。
- 未通过闸门 1 前不写正式团队计划、不派发；未通过闸门 2 前人事不写卡/改边界；未取得实施授权不开始实施。
- 转换发生在本轮实施过程中时，按第 3.5 节停止、记录、重新分类并重新取得授权；不沿用旧授权。
