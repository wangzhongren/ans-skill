01 / 能帮你什么

接手、修改和排查，都有依据。

适合需要持续维护、经常换对话或由多个 AI 接力的项目。

  1. 01

    下一轮，少从头解释

    功能说明和工作记录，让下一轮 AI 知道项目现在怎么运行、还有什么没做。

  2. 02

    只想改一处，先定范围

    先确认方案和改动范围，再按角色的文件边界修改。

  3. 03

    多个 AI 做事，知道找谁

    开发、测试、验收各有负责角色，出问题知道该找谁处理。

  4. 04

    过阵子再改，能查原因

    从功能说明回看设计和修复历史，知道当初为什么这样做。

02 / 一次协作

用一个草稿，说明角色怎样配合。

假设用户要保存尚未提交的工单。工单角色处理输入和保存流程，存储角色负责读写；各自维护自己的文件。以下只是协作示意，ANS 不是一个已经交付的工单应用。

Owner 01

工单角色

对保存过程负责：检查输入，组织步骤，处理业务结果。

  1. 接收输入
  2. 组织保存
  3. 检查规则
Owner 02

存储角色

对持久化负责：通过公开约定读写记录，返回实际结果。

  1. 接收记录
  2. 读写存储
  3. 返回结果

公开约定连接两个角色

工单 → 记录与保存请求；存储 → 成功结果或错误
Model：由指定所有者维护数据定义，供各层共享。修改共享约定后，重新核对受影响的调用者。
03 / 责任与代码

一个角色，可以跨多个代码层。

角色回答“谁对结果负责”；分层回答“代码怎样配合”。不是一层一个角色，也不要求每个功能在五层各建一个文件。

  1. Interface接收外部输入，返回结果
  2. Pipeline组织步骤与分支
  3. Service处理业务规则
  4. Provider访问文件、数据库或外部资源
  5. Model共享的数据定义与约束

职责清楚，交接才有着落。

团队组建定义角色和文件边界；统筹直接安排每个角色。策划说明用户目标，项目管理设计技术协作，开发者实现，测试角色运行检查，独立验收判断是否完成。

  • 上下文始终绑定一个角色，不在同一对话中来回换身份。
  • 跨角色阅读不会自动带来修改权限。
  • 测试通过与最终验收是两件事。

04 / 开始工作

先检查权限，再安排实际工作。

新的团队先建立角色；已有项目由原统筹准备配置。配置、边界和本次任务一起限制可写文件，预检不会自动替你扩权。

  1. 01

    定义角色

    团队组建写清职责与权限，准备完整登记内容。

  2. 02

    准备配置

    确认统筹角色，由独立固定的统筹上下文准备项目配置。

  3. 03

    只读预检

    发现漏权或冲突，交回对应所有者修正；不创建任务或运行日志。

  4. 04

    获准后开始

    预检齐全且已有有效授权，统筹再安排各角色工作。

07 / 常见问题

开始前，可能还想知道。

读文档，需要启动服务吗？

不需要。Markdown 和网页正文可直接阅读。运行权限预检与任务工具需要 Python 3.10+；业务项目可以使用其他语言。

角色看懂了别人的代码，就能顺手修吗？

不能。读取是为了理解；写入仍受角色边界、项目配置和本次任务限制。跨角色问题交统筹安排，由对应所有者修改。

有一个测试通过，就算整个任务完成吗？

不算。开发者负责自身检查，固定测试角色运行联调与回归；独立验收依据当前版本和原始证据判断通过、返工或证据不足。

在哪里查看五层和功能流程？

从 README 进入五层说明和角色卡。项目管理维护整体架构，各角色用功能导航链接当前功能说明、流程图和历史记录。

脚本被禁用，或者页面暂时打不开怎么办？

禁用 JavaScript 仍能阅读全部正文、打开链接并手动复制命令。页面暂时打不开时，可直接访问公开仓库 README、论文和许可证；页面不提供离线缓存或自动切换。
