02 / A collaboration

Follow one draft through two roles.

Imagine saving a ticket that has not been submitted. The ticket role handles input and the save workflow; the storage role reads and writes records. Each maintains its own files. This is an illustration, not a ticket application delivered by ANS.

Owner 01

Ticket role

Owns the save workflow: validate input, sequence work and handle business outcomes.

  1. Receive input
  2. Sequence save
  3. Apply rules
Owner 02

Storage role

Owns persistence: read and write records through an agreed public interface, then return the actual result.

  1. Receive record
  2. Read / write
  3. Return result

A public contract connects the roles

Ticket → record and save request; storage → success or error
Model: data definitions have one designated owner and are shared across layers. Changes to shared contracts require affected callers to be checked again.
03 / Roles & code

One role can span several code layers.

Roles answer “who owns the outcome?” Layers answer “how does the code work together?” There is no one-role-per-layer requirement, and every feature does not need a new file in all five layers.

  1. InterfaceReceive external input and return results
  2. PipelineSequence steps and branches
  3. ServiceApply business rules
  4. ProviderAccess files, databases or external resources
  5. ModelShare data definitions and constraints

Clear duties make handoffs concrete.

Five management roles work out of the box: Communication is the single customer interface and confirms the intent before taking the request to Planning; Planning defines user goals, the implementation plan, any research plan, the architecture design and shared contracts; the scheduler judges the team (keep, adjust boundaries, split, add or merge) by one standard after proposal confirmation, prepares the role assignment and manages each role's workflow; independent acceptance judges completion against the same planning version; People Operations writes or changes role cards and file boundaries only per the customer-confirmed team plan — the scheduler defines the needed capability and boundary, and People Operations adds the capability description and turns it into the card. A project-management role is created only when the scheduler judges that implementation needs a technical-architecture role.

  • Each context keeps one fixed role, including across resumed conversations.
  • The customer window loads only Communication; Communication starts Planning, People Operations, the scheduler and acceptance as separate subagents; worker roles go only through the scheduler.
  • Reading another role’s code does not grant write access.
  • Passing tests and final acceptance are separate facts.

04 / Start the work

Three customer gates, then the work.

Five management roles work out of the box. Communication confirms the intent first, the proposal second, and the scheduler applies one standard to judge the team (keep, adjust boundaries, split, add or merge) before the role-assignment gate. Each gate confirms its own object and version, and only explicit customer agreement passes it. Without the customer's agreement there is no recruiting, no card writing and no dispatch; default checkmarks, team consensus, a finished proposal and silence do not count. Configuration, boundaries and the task jointly limit writes; preflight does not expand permissions.

  1. 01

    Intent confirmation (gate 0)

    Communication records the request and writes down goals, scope, priorities, non-goals, authorized boundaries and known constraints. Planning starts only after the customer confirms the understanding.

  2. 02

    Proposal confirmation (gate 1)

    Planning writes the product proposal, implementation plan, research plan, architecture design and acceptance criteria; Communication presents it to the customer. Without confirmation, no team planning or recruiting starts.

  3. 03

    Role-assignment confirmation (gate 2)

    The scheduler names which roles, who does what, and each role's scope and write set; Communication presents it to the customer. Without agreement, no cards are written and no development is dispatched.

  4. 04

    People Operations, preflight, begin

    After the customer agrees, People Operations writes the cards per plan; the scheduler prepares configuration, runs read-only preflight, then authorizes and reserves each role.

07 / FAQ

A few things to know before you start.

Do I need a running service to read the docs?

No. Markdown and page content can be read directly. Permission preflight and task tools require Python 3.10+; your application may use another language.

Can a role fix another role’s code after understanding it?

No. Reading supports understanding. Writes still require permission from the role boundary, project configuration and current task. The scheduler routes cross-role issues to the relevant owner.

Does one passing test mean the task is complete?

No. Developers run their own checks, and the test role runs integration and regression checks. Independent acceptance evaluates the current version and original evidence: pass, rework or insufficient evidence.

Where can I find the layers and feature flows?

Start with the README links to architecture and role cards. Planning provides the product proposal, implementation plan, research plan and architecture design; an established project-management role maintains the implementation architecture. Each role’s feature map links current descriptions, flowcharts and history.

What if JavaScript is disabled or the page is unavailable?

With JavaScript disabled, all content, links and manually selectable commands remain available. If the page cannot be reached, visit the public repository README, paper or license directly. This page does not provide offline caching or automatic failover.
