# 四类文档怎么写：工单草稿示例

这里是**写作示例**，不是仓库里已经实现的工单功能，也不是测试通过的证据。四份文档使用同一个假设场景，方便比较各自的重点：

1. [设计：为什么先保存、再退出](design/2026-09-27_design_work-order-draft.md)
2. [新增：从打开工单到成功或失败的完整流程](feature/2026-09-27_feature_save-work-order-draft.md)
3. [修改：按钮在哪里改、前后有什么差别](change/2026-09-27_change_save-exit-feedback.md)
4. [修复：保存失败仍关页的问题](fix/2026-09-27_fix_close-after-save-failure.md)

读完后可以检查：设计能否帮开发者做决定；新增能否让人照着使用；修改能否让老用户知道哪里变了；修复能否让遇到同样问题的人找到原因。日期元数据在开头只为检索服务，正文不写公文式的“目标、范围、实施、验收”套话。

这次按反馈改了两句最容易写得生硬的话：

| 原来 | 现在 |
| --- | --- |
| 按钮会先等待保存结果 | 存上了才回列表；没存上就留在原页 |
| 尚未实施或测试 | 还没做，也没测 |

写完[设计文档](design/2026-09-27_design_work-order-draft.md)后，聊天里的交付说明可以这样写：

> 方案是先存草稿，存上了才退出；没存上就留在原页，原输入不丢。现在只写了设计，代码还没做、没测。[查看完整设计](design/2026-09-27_design_work-order-draft.md)。你对这个方案有什么地方想进一步了解吗？

分支不容易讲清时，也可以在聊天里画“点保存 → 成功才退出／失败留在原页”。先把文档给客户看；客户确认这份文档并说“按它修改”后，才开始改代码。上面的提问本身不算确认。
