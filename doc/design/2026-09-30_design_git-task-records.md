# 让任务记录跟着项目走

用户需要把项目放进 Git，在另一台机器拉取后仍能看到任务做到哪一步、为什么暂停、以前怎样修改。SQLite 作为唯一任务数据库做不到方便地比较和合并这些历史。

建议把每个任务保存为一份 **Git 跟踪的 Markdown 文件**：`docs/scheduling/<task-id>.md`。程序按固定格式写任务计划和事件；人可以直接读，Git 可以查看每次改了什么。角色卡、功能流程、设计与修复文档继续保持 Markdown，业务源码仍由 Git 管理。

## 文件长什么样

```text
项目根目录/
  docs/scheduling/
    repair-save-draft.md       # 保存草稿修复任务的计划与变化
    add-ticket-search.md      # 搜索功能任务的计划与变化
  .ans/project.json            # 仍保留一份经过审核的项目执行配置
```

每个任务文件由任务工具生成，包含四块：

1. **这次要做什么。**对应需求、已确认的方案、版本和参与角色。
2. **先后顺序。**每一步由谁负责、允许改哪些文件、需要哪些前置结果和检查。
3. **发生了什么。**按顺序写派发、接收反馈、测试、暂停、修改方案和验收等事件，带编号和实际时间。
4. **现在怎样。**从事件推导并展示当前步骤状态；这部分由程序生成，人不手改。

功能流程和方案继续链接角色已有的 `docs/feature/`、`docs/design/`、`docs/change/`、`docs/fix/`。任务文件记录**谁做了什么、何时做、验收证据**，不重复维护另一份功能说明。

## 为什么是一任务一份

两个不同任务各改自己的文件，Git 可以正常合并。一个任务在不同机器上同时被修改，Git 会提示冲突；任务工具必须停止写入，让项目管理角色核对哪个执行者仍在工作、哪些事件已经发生，再处理冲突。不能按时间戳盲选一个版本，也不能把两条“已完成”直接拼起来。

提交和拉取仍由用户决定。Git 只能同步**已经提交并推送**的任务记录；本地未提交的进度不会自动出现在另一台机器。需要马上让别人看到时，按项目原有 Git 流程提交并同步。

## 程序怎样安全使用 Markdown

任务工具只读取自己生成的、格式固定的任务区块，校验任务 ID、事件顺序、状态转换、角色边界、设计版本和证据哈希。自然语言说明供人阅读，不作为程序授权。每次有效操作先核对当前文件版本，再在文件锁下原子写入一个包含新增事件和最新状态的文件；中断时保留先前完整版本，不接受半写入文件。

当前的 `plan.json`、`state.json`、`events.jsonl` 和 `board.md` 分成多份，靠日志与快照互相核对。改成单个 Markdown 记录后，不能只换扩展名：必须重新定义工具可验证的结构和读取逻辑，保留现有的防重复反馈、版本核对、依赖暂停和检查证据要求。公开给用户的正文保持简洁；内部字段集中在清晰标记的固定区块，避免让人手填大量机器字段。

明文令牌不得写进 Git。任务工具继续只保存令牌校验值，真正的令牌由可信执行端保管。换机器时，**旧的“运行中”不能直接续跑**：先确认原执行者是否已停、核对当前代码和文档，创建新尝试并重新运行相关检查。原机器上的临时文件锁和完整测试输出不必作为项目历史同步；任务文件保留必要的检查命令、结果摘要、代码版本与证据引用。跨机器需要可复核结论时重新验证，不把旧机器上的通过状态无条件移交。

`.ans/project.json` 仍是一份项目级执行配置，不会每个任务生成一份。它包含已批准的角色、路径和检查命令；任务文件保存引用的配置哈希。AI 自己生成或修改配置，不等于获得客户批准。若后来连这唯一一份 JSON 也想改成别的格式，应单独处理它的审核和解析规则；本次先解决**每个任务反复产生多份 JSON**的问题。

## 哪些地方要改

1. **执行协作角色**修改 `scripts/coordination_store.py` 和 `scripts/task_ops.py`：建立、读取、校验和原子更新任务 Markdown；状态命令直接读它；请求可以通过标准输入提供，不要求额外建立请求 JSON 文件。
2. **云端与同步角色**修改 `dashboard/server.py`：从任务 Markdown 读取摘要和事件供已有任务页面显示。Dashboard 的云端账号、项目数据库及手动同步规则不因此改变。
3. **各维护角色**更新任务操作、调度、协调和 Dashboard 指南，写清现在的文件格式、Git 提交时机、换机器接手步骤。
4. **测试角色**独立验证：两个不同任务的提交与拉取、同任务分支冲突提示、旧设计反馈拒绝、暂停重做、证据过期和 Dashboard 展示。执行与云端角色分别维护自己的单元测试。

已有旧任务目录先保留可读，不能在新工具上线时自动删除。本次目标是**新任务**改用 Markdown；旧任务还要继续执行或迁移时，需先核对其现有计划、事件、授权和活动执行者，再单独处理。这个范围不会额外启动同步服务，也不改变业务源码或旧图谱工具。

## 完成后怎么检查

- 新任务只生成一份可随 Git 提交的任务 Markdown，不再产生该任务的 `plan.json`、`state.json`、`events.jsonl` 和默认 `board.md`。
- 两个人分别处理不同任务时，Git 能合并；同一任务发生实际冲突时工具停住，不能悄悄覆盖另一边。
- 授权、版本、重复反馈、任务依赖、失败测试、旧证据失效等现有行为仍可通过验证。
- 换机器后能看到已同步的计划和历史；运行中的步骤需重新核对和接手，不能把另一台机器的执行令牌当成本机有效。
- Dashboard 显示的任务状态和事件与任务文件一致；如页面未验证，就明确写“页面还没测”。

代码已按这份方案修改。每份任务文档上面是给人看的计划、步骤和变化记录；下面是工具写入的固定机器区块，包含有序且带哈希的事件及其当前状态。工具核对整份文件后才继续写；手改正文或 Git 合并冲突会阻止执行。运行时文件位于本地 `.ans/runtime/`，不跟着 Git 提交。

验证结果：完整工具回归 **157 项通过**；真实游戏引擎计时修复回放通过，产生 1 份任务 Markdown 和 22 条事件；不同任务的 Git 提交合并通过，同一任务的冲突被 Git 与任务工具拒绝。Dashboard 能读取新任务，并能只读展示旧 JSON 任务。另已验证：换到没有本地检查日志的副本后，依赖步骤不会继续派发；Windows 风格换行可以正常读取。

目前的限制：已有旧任务没有自动迁移；新机器若没有可信执行端保存的原令牌，就无法继续原来仍标“运行中”的批次。需要先核对原执行者是否停止，按授权新建任务并重做受影响的检查。没有做线上部署，也没有把新任务记录自动上传云端；本地 Dashboard 与已有手动同步的读取路径使用同一新格式。独立复制 `dashboard/` 的命令行启动已验证；新任务 Markdown 的本地读取需要完整技能目录中的 `scripts/`。
