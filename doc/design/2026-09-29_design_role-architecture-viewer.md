# 每个角色维护架构 JSON，程序生成本地架构页面

打开一个本地 HTML，就能先看角色如何配合，再选一个功能看数据怎样流动。点击其中的角色或模块，打开该角色的内部抽象图。内部图以稳定的概念、模块和公开约定为主干，功能点关联到对应抽象上；不把它画成文件清单或一串按钮操作。

每个角色维护自己的 `architecture.json`。绘图程序读取这些 JSON，生成一份项目页面。角色架构发生变化时更新自己的 JSON；项目角色在架构变更后或任务完成时汇总绘图并打开结果。程序只检查和渲染已有数据，不调查整个项目，也不替角色编造关系。

## 页面怎样看

1. **角色配合图。**节点是角色。连线说明使用对方提供的什么抽象或公开约定，例如“场景管理使用实体管理提供的 Entity 数据定义”。数据模型引用、能力调用分别标明，不能把引用数据画成调用对方服务。
2. **数据流向图。**选择一个功能，显示数据进入哪个抽象模块、交给哪个模块、怎样返回结果。每块标明所属角色，连线标明传递什么数据及实际条件。没有核实的分支显示待补，不猜测。
3. **内部抽象图。**点击角色进入该角色的思维导图；点击数据流中的模块，进入同一份内部图并定位到相应抽象。按“核心抽象 → 组成或使用的抽象 → 支撑的功能点”展开，可收起枝叶。

三种视图来自同一批角色 JSON。页面不另存一套手工关系。公开接口的完整字段、功能的详细步骤继续引用现有功能文档、Model 和正式契约。不再要求维护 content.json、context.sqlite3 等重复项目理解索引；旧数据和旧工具保留供用户明确需要时查看。

## 每个角色的 JSON 放什么

位置：`角色卡/<角色>/architecture.json`，英文项目跟随已有角色目录名称。角色 ID 必须与实际角色目录一致；节点 ID 在项目内唯一且保持稳定，例如 `场景管理:SceneManager`。其他角色只引用这个 ID，不复制一份相同定义。

| 内容 | 说明 |
| --- | --- |
| 角色和版本 | `schemaVersion`、`roleId`、`revision`、`updatedAt`、简短说明；更新本角色结构时增加版本 |
| 本角色的抽象 | `abstractions`：名称、含义、类型、所属五层、是否公开、源码或契约依据 |
| 抽象之间的关系 | `relations`：组成、管理、使用等关系；对外依赖指向提供方角色的公开节点或共享 Model |
| 关联功能 | `features`：功能 ID、用途、相关抽象 ID、功能文档或正式契约的依据 |
| 数据流片段 | `dataFlows`：所属功能、发出与接收的抽象节点、数据定义引用、条件和依据 |

JSON 保存画图所需的结构与引用，不复制所有源代码、接口字段或整份功能文档。代码和正式契约仍是事实依据。已有项目只补核实过的抽象；新项目的拟定内容明确标为“计划中”，不能画成已经实现。

下面是结构示意，不表示示例项目已经创建这些 JSON：

```json
{
  "schemaVersion": 1,
  "roleId": "场景管理",
  "revision": 1,
  "updatedAt": "2026-09-29",
  "summary": "管理场景的创建、切换和更新。",
  "abstractions": [
    {
      "id": "场景管理:SceneManager",
      "name": "场景管理约定",
      "kind": "contract",
      "layer": "service",
      "public": true,
      "description": "提供创建、查询、切换和更新场景的操作。",
      "sourceRefs": ["src/services/abstract/scene.ts"]
    },
    {
      "id": "场景管理:Scene",
      "name": "场景数据",
      "kind": "model",
      "layer": "model",
      "public": true,
      "description": "记录场景名称、状态和实体引用。",
      "sourceRefs": ["src/models/scene.ts"]
    }
  ],
  "relations": [
    {"from": "场景管理:SceneManager", "to": "场景管理:Scene", "kind": "manages"},
    {"from": "场景管理:Scene", "to": "实体管理:Entity", "kind": "uses-model"}
  ],
  "features": [],
  "dataFlows": []
}
```

使用方记录自己依赖谁；数据流中，一条传递关系由发出数据的角色记录，接收方记录它自己的后续处理。全局功能 ID 指向主要负责角色的功能定义，参与角色沿用这个 ID。这样同一条跨角色关系不会由两边各写一个版本。

共享定义只在所属角色 JSON 中定义一次。缺少角色 JSON、找不到引用节点或缺少数据流时，页面如实显示待补；不能用角色名称推断调用。重复节点归属或不合法的结构要先报告，不覆盖原页面。画图工具核对 JSON 的结构和引用；五层调用规则和语义仍由角色对照实际代码检查。

## 谁负责更新，谁负责生成

不新增画图师或其他内置角色。各角色负责事实，绘图程序负责把事实排成图，项目角色负责项目总览的生成和交付。

1. 各角色只更新自己已批准范围内的 JSON，对照代码和契约说明抽象与依赖。
2. 绘图程序读取各角色 JSON、角色 ID 和必要的引用信息，检查并生成 HTML；只写已批准的生成页面位置，不修改输入 JSON、业务源码或角色边界。
3. 项目角色在自己的生成文档范围内运行工具并打开结果。执行角色完成架构更新后通知项目角色重画，无需切换为新的绘图角色。
4. 同一项目的共用 HTML 由项目角色统一生成，避免多个执行角色互相覆盖。任务收尾时汇总一次；无需新增后台队列或常驻服务。

治理角色负责在角色模板和已批准的边界中明确各角色自己的 JSON 路径、项目角色的生成输出路径。没有这些写入范围时，不能因绘图需求自行扩权；具体业务项目的角色边界仍按原治理流程处理。

绘图直接由程序读 JSON 和排版，不需要 AI 子代理、额外模型调用或新角色调度。

## 文件和生成方式

```text
技能目录/
  assets/architecture-viewer/       可复用的 HTML、样式和页面脚本
  scripts/render_architecture.py   读取角色 JSON，生成页面
  references/role-architecture-viewer.md JSON 格式、更新与绘图说明

业务项目/
  角色卡/<角色>/architecture.json  每个角色维护的唯一图数据
  <已有文档根>/architecture/index.html  生成结果，不手工维护
```

模板放在技能中。绘图程序将当前 JSON 数据、样式和脚本嵌入生成 HTML，可以直接在本地浏览器打开，不依赖远程 CDN，也不需要另起后端。输出跟随项目已经确定的文档目录，例如已有 `doc/` 就复用它，不再新建一套 `docs/`。

模板重复使用，角色 JSON 是维护源；生成 HTML 是当次快照。页面标明生成时间和所用角色版本。刷新浏览器不会自动读取磁盘新 JSON；角色改完后由绘图程序重新生成，再打开最新文件。

## 什么时候更新

公开约定、模块职责、抽象组合、跨角色依赖、相关数据流或功能归属发生变化时，负责角色核对后更新自己的 JSON。纯措辞、排版或不影响这些关系的私有实现变动，不强制重画。

一次任务的交付顺序为：实现与验证 → 更新受影响角色的 JSON → 项目角色运行绘图程序 → 打开本地 HTML，聊天里给链接和短说明。确认过的绘图范围内可以直接刷新图，不要求客户为每次重画重复授权。新的选装或业务代码改动仍按已有方案确认规则处理。

## 这次改动与验证范围

实施时修改项目角色的交付说明、角色卡模板、相关边界和文档规则；新增本地模板、绘图工具和有实际行为断言的测试。保留现有旧图工具，避免把旧的文件调用图或运行步骤图混成这次的抽象图。

验证内容：多个角色 JSON 能组合；抽象引用保持唯一归属；角色配合、功能数据流和内部图能互相定位；缺失信息如实提示；修改 JSON 后重新生成可见变化；页面可本地打开、折叠、切换功能和返回总览；绘图不修改角色 JSON 或业务文件。用现有示例项目中核实过的抽象做验证数据，明确它是示例。

这版以本地架构 HTML 为默认入口，旧 Dashboard 与云端代码保留为可选工具，不默认启动。角色卡、启动流程和交付规则已移除强制维护 SQLite 项目理解索引的要求；既有数据没有删除。**没有额外选装项，也不新增角色。**

## 实施与验证结果

模板、绘图工具和 JSON 规则已实现。完整测试共 142 项通过，新增 13 项覆盖角色归属、跨角色引用、数据流、缺失信息、生成后输入文件不变、重复 ID 不覆盖旧图、文本安全嵌入、更新后重画等行为。客户端有 8 项内存 DOM 交互检查，覆盖三种视图、折叠、功能切换、角色引用跳转和模块定位；它不是浏览器视觉验收。

示例根据现有游戏引擎中核对过的约定构建，包含 4 个角色、13 个抽象、4 个功能点。示例 JSON 和生成 HTML 位于技能输出目录，原游戏项目的源码和角色文件没有修改。未记录的功能数据流显示待补。

浏览器自动化工具拒绝 file:// 地址，禁止直接打开本地 HTML；没有改用其他浏览器或服务绕过限制。生成文件已准备好，可以由客户在本机打开检查布局。当前状态为代码与测试完成、真实浏览器视觉验收待完成。

安装和发布按客户指示执行，不因为完成绘图工具就自动部署服务器。具体 JSON 和运行命令见[使用说明](../../references/role-architecture-viewer.md)。
