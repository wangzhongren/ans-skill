# 项目法案约束怎样写代码，备忘录帮助角色继续工作

通用技能是各项目共同采用的工作原则。具体项目还需要一份**全体角色共同遵守的工程法案**：线程怎样使用、代码怎样组织、哪些操作放在哪个位置、数据和资源怎样处理。

项目法案与“项目要做哪些功能、分几期实现”是两类内容。目标和实施路线沿用项目已有方案；本次新增的是 `project-rules.md` 和各角色的 `memo.md`。

## 项目法案：所有角色的工程约束

项目管理角色维护一份 `角色卡/<项目管理>/docs/project-rules.md`。它适用于整个项目，每个角色卡都指向同一份法案，不能各自复制出不同版本。文件路径进入项目管理已接受的文档边界；法案中的工程约束不自行扩大文件修改权限。

法案根据项目的实际运行环境、架构和已确认要求制定。例如：

| 约束方向 | 可以规定什么 |
| --- | --- |
| 线程与执行 | UI/渲染主线程允许做哪些工作；阻塞 I/O 或重计算如何交给后台，结果如何回到主线程 |
| 代码组织 | 本项目模块怎样拆分、文件放哪里、什么地方是公开入口、内部基础组件怎样复用 |
| 依赖与调用 | 项目中具体模块的调用关系，哪些依赖允许，哪些依赖会破坏既定设计 |
| 数据与状态 | 数据由谁维护，哪些状态可共享，什么操作需要事务或明确的同步方式 |
| 资源与生命周期 | 连接、文件、监听器、任务由谁创建和释放，停止或失败后如何收尾 |
| 错误处理 | 错误怎样返回、哪些情况交上层决定、本项目如何记录排查信息 |
| 检查方式 | 对已确认约束如何核对和测试，具体可用命令或行为检查在哪里 |

法案写的是适用于这个项目的具体约束。已有通用规则可以引用，不再抄一遍整个技能。没有实际依据的“万一”措施先作为建议，不自动写成全局强制要求。

## 一条法案怎样写清楚

每条写清四件事：**作用在哪、要求是什么、正确实现办法、怎样检查**。必要时用一句话说明原因。给规则一个稳定名称或编号，角色报告问题时可以直接引用。

下面是 GUI 项目的示意，只有项目确实采用这套线程模型并确认约束后才生效：

```markdown
### THREAD-01：主线程保持页面响应

适用位置：页面事件、渲染循环和主线程回调。

要求：不能在这些位置同步读写大文件、等待网络结果或执行会阻塞页面的重计算。

实现办法：I/O 使用项目约定的异步能力；重计算交给 Worker、后台线程或任务进程。完成后按约定把结果交回主线程更新页面。单纯给函数加 async，不会自动把重计算移到后台。

检查：核对本次改动的调用位置，运行相应交互和计算场景，观察输入响应与界面更新。具体测试链接到角色的实际测试说明。
```

代码组织约束也应具体到本项目，例如某组组件只能通过一个已确定的入口被其他角色调用，并指出入口路径、拆分原则和依据。不能只写“代码要规范”“保证高性能”这样的口号。

法案草稿与已生效版本明确区分。项目管理结合相关角色的实际情况拟定或修改约束，按已有评审和客户确认流程确定；实质变更要让受影响角色知道。发现旧代码与法案冲突时，写清冲突和影响，交项目管理安排处理；不能顺手重构整个项目，也不能为通过测试私自放松法案。

## 角色备忘录：记住下一次工作有用的事

每个项目角色，包括项目管理、开发、装配和测试，在自己的根目录维护 `memo.md`。它记录本角色掌握的重要事实、问题和继续工作的线索，不再定义另一套全局法案。

按实际内容使用四块：

1. **已确定的关键事。**本角色特别需要注意的工程法案或已确认决定，链接正式依据。
2. **工作中发现的事实。**真实行为、容易踩坑的位置、测试条件和排查入口。
3. **待解决问题。**阻塞、待核实的判断，以及需要哪个角色协作。
4. **下次从哪里继续。**最近工作位置、应先看哪份方案或任务、需要重新核对什么。

线索尽量写清日期、当前状态和来源。推测标“待核实”；已经解决的事项移除或标明，重要原因链接历史。不要抄完整聊天、源码或测试日志，也不要无限追加成第二份 changelog。

例如某角色可以在 memo 中提醒自己：“当前图片处理必须遵守 THREAD-01；还在核对现有回调是否运行在主线程。继续时先看对应功能和测试。”这只是提示，真正的约束仍在项目法案里。

每个角色更新自己的 memo，其他角色按需读取。新发现需要成为全局约束时，交项目管理修改正式法案；仅写进某个 memo 不会让其他角色自动承担新的规则。

## 各种文档分别回答什么

| 文档 | 回答的问题 |
| --- | --- |
| 通用技能 | 各项目共同采用什么组织和开发原则？ |
| 项目法案 | 这个项目所有角色怎样写代码、运行程序和处理资源？ |
| 项目方案 | 要实现哪些目标，选择什么路线，怎样推进？ |
| 架构说明 | 当前系统怎么组成，角色和模块怎么配合？ |
| 功能文档 | 某个功能当前怎样运行？ |
| design/change/fix 历史 | 那次为什么改、改了什么、验证结果怎样？ |
| 任务 Markdown | 谁在执行当前工作、到哪一步、发生过什么？ |
| 角色 memo | 本角色下次工作需要记住哪些事实和线索？ |

法案统一保存项目级工程约束，memo 保存与本角色有关的简短提醒和引用。具体流程和当前任务状态分别沿用现有文档，不在这里重写。

## 技能需要怎样调整

1. 项目管理模板增加项目法案的维护责任和路径；每个角色的必读资料增加当前法案与自己的 memo，开始或续接任务时核对本次相关内容。
2. 角色模板与初始化说明增加 `memo.md` 的用途和所属角色。治理处理相应文档权限；不能凭新增文档给自己扩权。
3. 项目管理角色建立并接受后，整理实际项目的工程约束。已有项目先区分现行做法、已确认要求与待解决冲突，不把想象中的约束说成客户已经批准。
4. 项目管理评审方案时检查法案符合性；各执行角色实现时采用相应方法；测试角色按实际约束验证。法案没有检查依据时如实说明，不捏造自动检查结果。
5. 任务交接、角色续接或出现重要新事实时，更新相关 memo。不是每个工具调用都记一条，私有实现的小改动也不要求所有角色重写备忘录。
6. 更新技能入口、README 和文档说明。项目法案的变化链接原有日期设计/修改文档；备忘录中的实际工作线索不需要逐条重新审批。

本次只新增项目工程法案和角色备忘录两个用途，不要求新增后台服务、JSON 或数据库。

## 当前状态

这份方案已按用户澄清修正：项目法案指全局工程约束，与项目目标和实施方案分开。用户随后明确要求委派角色开发本功能。

本轮由独立治理角色建立项目管理、技能规范、测试三个任务角色，技能规范已更新入口、指南和模板；项目管理整理 ANS 已确认工程选择，建立本项目法案及自己的 memo。各角色在自己的独立上下文写入获准文件。详情见[本轮评审与分工](../../角色卡/项目管理/docs/design/2026-10-10_design_project-rules-memo-review.md)。

独立测试角色完成了五类情境及实际文档检查，首轮发现的元数据与过期状态问题已由对应维护者修正；最终复核确认通过。具体结果见[独立验证报告](../../角色卡/测试/docs/change/2026-10-10_change_project-rules-memo-validation.md)。这些结果验证指南和资料衔接，没有实测真实业务项目的线程或性能。未自动向其他项目添加具体法案，也没有修改应用程序代码。
