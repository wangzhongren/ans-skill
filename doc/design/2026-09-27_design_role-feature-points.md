# 每个角色列出自己负责的系统功能点

打开角色卡时，现在能看到这个角色能改哪些文件，却不容易看出**系统的哪些功能点归它负责**。这里说的功能点是用户或外部系统实际能用的行为，比如“保存工单草稿”“提交工单”，不是“负责 Service 层”或“编写测试”这种角色职责。

每个角色在 `role-card.md` 列出自己负责的功能点，并链接到各自的说明。**一个功能点一份文档**，放在这个角色的 `features/` 目录。文档讲当前功能：它解决什么事，从哪里触发，输入什么，按什么顺序处理，遇到不同条件怎样走，成功或失败会发生什么，以及用到哪些接口和数据。写到读者不打开代码也能理解的程度；字段和分支仍要用真实代码或已确认的设计核对。

```text
角色卡/工单/
  role-card.md                负责的功能点：保存草稿、提交工单（链接到下方文件）
  boundary.md                 允许修改的文件
  features/
    save-draft.md             保存草稿当前怎样工作
    submit-ticket.md          提交工单当前怎样工作
  docs/feature/
    2026-09-27_feature_save-draft.md  当时新增保存草稿的记录
```

一个功能点只有一个**主要负责角色**和一份当前说明。需要其他角色配合时，在文档里写清交接和链接，但不在多个角色目录复制同一份内容。角色卡中的功能点列表是**归属索引，不是执行授权**；真正能改哪些文件，仍看已接受的 `boundary.md`。某个角色若没有直接负责的系统功能点，就写“暂无”，不要把调度、装配或文档工作硬凑成业务功能。

`features/<功能名>.md` 说明**现在怎么用、怎么运行**；带日期的 `docs/feature/`、`docs/change/` 和 `docs/fix/` 解释**某次为什么增加、改变或修复**；SQLite 项目理解提供可查询、可画图的流程、数据和接口索引。三者互相链接，变更后由负责角色核对一致。源码与正式接口契约仍是实际行为的依据；证据不足就写“待核实”，不能把设想当成已实现。

这次只修改技能的文档规则和模板，没有修改 Dashboard 或业务代码，也没有把旧项目里的功能点凭名称批量补成文档。当前 Dashboard 的同步扫描不会收集新 `features/` 文件，页面也不会展示它们；以后若要在云端查看，需要另写同步和页面改动方案，再按客户确认的方案实施。
