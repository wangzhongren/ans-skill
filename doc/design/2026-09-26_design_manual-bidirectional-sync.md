# 手动版本同步方案

这份设计对应[已实现的候选功能与验证记录](../feature/2026-09-26_feature_manual-versioned-sync.md)。当前业务服务器尚未部署新版。另有[云端直接成为正式数据的备选方案](2026-09-26_design_cloud-first-dashboard.md)，不能与本方案同时作为写入规则实施。

## 1. 要解决什么

原有 [`dashboard/sync.py`](../../dashboard/sync.py) 启动后立即上传，随后按间隔整份覆盖云端展示快照。它既不能按版本判断覆盖是否安全，也不能把云端新记录完整拉回本地。用户现在选择：**像 Git 一样，由用户决定何时同步**。本地仍用 Git 管源码，用现有角色文件、任务记录和项目理解 SQLite 开发；云端保留最近一次同步的 Dashboard 页面和版本历史。

同步范围是管理数据：角色卡、边界、任务展示、流程/数据/接口/定义、日期文档的原文与历史、云端角色消息和审批。**业务源码全文不上传**。同一个项目继续使用一个项目 Key；它只能证明项目身份，不能单独证明具体角色或授权写代码。

## 2. 版本与存储

不能让本地和云端各自把数字加一，再比较谁大：两边都从第 5 版改到第 6 版，也可能改出不同内容。因此项目版本只由服务器递增分配。本地 Git 忽略的 `.ans/project.sqlite3` 保存已经拉到的云端版本、完整快照、每次显式记录的角色/任务/项目理解/文档差异、待上传快照、消息游标和冲突。现有 `project-context/context.sqlite3` 在某些业务项目已纳入 Git，不能把频繁变化的游标和重试状态写进去。

云端仍按项目使用一份 `projects/<project-id>.sqlite3`；该库保存不可改写的整份同步版本、冲突候选和现有展示快照。全局 `dashboard.sqlite3` 保留账号、项目和 Key 哈希。后端的网页写操作经过一个有界的单线程队列；同一项目的版本检查、版本写入和展示快照更新在该项目库事务中完成。

**当前冲突单位是整份管理数据快照。**即使两台机器改了不同条目，也可能被判为冲突。这比错误地自动覆盖安全，但不是逐条自动合并。按条目合并需要独立设计、实现和测试，不能宣称现已具备。

## 3. 用户怎样操作

| 用户操作 | 本地与云端发生什么 |
| --- | --- |
| 完成一项管理数据修改后运行 `--record` | 捕获当前管理快照，按实体记录差异到本地 SQLite；不联网、不上传 |
| 运行 `--pull-only` | 分页拉云端版本及全部新增协作事件，保存在本地 SQLite；不上传 |
| 运行默认同步命令 | 先拉云端，再记录当前本地快照并上传待同步版本；无变化时不创建新版本 |
| 运行 `--status` | 只读本地配置、云端已知版本、待上传数量和冲突，不读取或显示 Key |
| 客户决定冲突后的取舍 | `--resolve <changeId> --choice local|cloud`；未决定前不覆盖云端当前版本 |

默认命令运行一次就退出；**角色启动、页面刷新和任务结束都不自动上传**。仅当用户明确选择后台模式时才使用 `--interval`。用户未运行同步命令时，云端页面保持上一次快照是预期行为。

新版完整同步内容另带受限 `artifacts`：角色卡、边界、角色说明和 `docs/`、`doc/` 中带日期的设计/功能/修改/修复文档与任务记录。云端展示快照仍去掉角色文档正文；原文保存在版本记录供历史查询。文件数、单文件大小和总请求大小都设上限，并拒绝越界路径；不扫描业务源码目录。上传前应检查文档不含 Key、密码和不适合当前云端用户查看的资料。

## 4. 接口和拉取

`GET /p/<项目ID>/api/changes?after=<云端版本>&limit=<页大小>` 分页返回这个版本之后的完整同步版本。服务端还提供 `POST /api/sync-v2`，要求上传基础版本和唯一 `changeId`；旧版本返回 `409`、保留候选，但不改当前快照。同一个 `changeId` 重试只返回原结果。现有旧 `/api/sync` 在项目切换到新版后被拒绝，避免再次无版本覆盖。

`GET /api/channel/changes?after=<事件序号>` 分页取消息、权限申请与决定，不受旧列表“最近 100 条”的限制。它们进入本地同步 SQLite 供查询；云端管理员的决定不会自动变成本地源码写入授权。`GET /api/design-docs` 可按文档相对路径和云端版本查询确切旧版原文；本地命令提供 `--design-list`、`--design-path`、`--design-revision`。

**拉到本地 SQLite 不等于自动改写工作区。**技能可用 `--remote-summary`、`--remote-artifact`、`--remote-context` 查看已拉取内容。如果本地角色文件或项目理解和云端版本不同，必须先核对 Git、任务和两版内容，再由对应角色在授权范围内更新文件；新版不会静默覆盖业务源码、角色文件或 `project-context/context.sqlite3`。这也是当前“拉取最新”的明确边界。

## 5. 冲突、恢复和客户提醒

当本地依据的云端版本已过期，服务器保留冲突候选并返回 `409`；本地 SQLite 记录冲突、停止该快照上传。云端 Dashboard 的“记录检查”显示冲突，并可查看发生差异的角色、文档或任务预览。活跃的 AI 应当告诉客户：本地依据版本、云端当前版本、哪些管理内容不同，以及需要选择保留本地、保留云端还是人工合并。同一冲突不应每次运行同步时重复提醒。

选择本地后，客户端以当前云端版本重新上传该候选；选择云端前，用户必须先让本地文件与已拉取的云端内容一致。两种选择都不能代替角色授权或代码测试。断网时待上传版本留在本地 SQLite；恢复连接后先拉版本，再按同一个 `changeId` 重试，避免重复写入。

服务器升级前备份全局库和各项目库；新客户端第一次读取版本时，将已有展示快照记为旧版基线。先停旧同步进程再使用新客户端。源码仍从 Git 恢复；仅有旧展示快照不足以重建所有本地文件。备份和恢复应同时核对云端版本链、文档原文与协作事件。

## 6. 当前实现边界与后续选择

当前本地 `--record` 会对**每次调用时可见**的管理快照做实体差异记录。两次记录之间产生又消失的中间文件版本无法事后复原；若要求每次原子写入都保留，角色/任务/项目理解的全部修改入口还须直接写统一变更日志。当前也没有把从云端拉取的角色或项目理解自动写回现有业务文件与旧项目理解 SQLite。上述两项属于后续迁移，不能以本版测试通过来声称已经完成。

本次验收聚焦现有能力：手动默认不启动定时器，`--record`/`--pull-only` 不上传，改过的管理文档在云端保留多个可查询版本，旧版本上传得到冲突且不覆盖，Dashboard 展示差异，超过 100 条协作事件能分页拉取，业务源码不进入同步内容。具体测试结果记在关联功能文档中。
