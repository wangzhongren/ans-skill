# 云端统一管理方案

> 这是待评审、待实施的**备选设计**：让云端成为正式数据。当前采用[由用户触发的本地与云端手动同步](2026-09-26_design_manual-bidirectional-sync.md)。两种路线不能同时作为写入规则实施；本文提到的云端主数据接口尚不存在。

## 1. 要解决什么问题

现在业务项目的角色卡、修改边界、项目理解 SQLite 和任务记录都在本地。云端 Dashboard 保存它们的展示副本；本地同步器定时上传整份快照。服务器收到快照后直接替换旧快照。另一台电脑若持有同一项目 Key 并上传同一项目，后上传的内容可能盖掉前一次内容。云端的消息和审批另存于服务器，已有命令可以读取，但没有一套完整的“从云端领角色、完成工作、交回结果”的流程。

目标是让多人和多个角色**共用一个云端工作台**。本地不再启动 Dashboard 页面，也不再维护第二份可独立修改的角色、任务和项目理解主数据。本地仍保留源码、测试工具、Git 和轻量命令行客户端。**本地写出的设计、功能、修改、修复文档必须上传云端**，云端保存每个版本，并提供接口让技能查询历史设计。后续 ANS 的**持久化管理数据统一存 SQLite**：云端是正式数据，本地 SQLite 只存缓存、草案和待提交请求，不再把 JSON/JSONL 文件作为另一套任务状态。

### 成功时应看到的行为

1. AI 开工前，从云端取得本次角色、允许修改的文件、任务和相关设计的**已确认版本**；没有有效角色或任务时不能开始写代码。
2. AI 在本地改代码、写日期文档、运行测试；提交时上传本次文档、项目理解的变化、测试结果和代码版本。云端先记录候选结果，验收后才标为当前结果。
3. 云端页面能看当前角色、流程、数据、接口、任务进度，也能打开一份设计文档的旧版本；技能可用同一套接口查询这些历史版本。
4. 两处同时修改同一条内容时，旧版本提交会被拒绝并指出冲突；任何一方都不能静默覆盖另一方。

### 不在本方案内

- 不把整个业务源码仓库或业务 SQLite 上传 Dashboard。源码的正式版本仍由 Git 管理。
- 不让云端服务器启动本地 AI、执行项目测试或直接写业务代码。
- 不给每个角色另发一把 Key；仍使用一个项目 Key。角色的可操作范围由已确认的任务和边界约束。
- 不把每次键盘保存都当成正式提交。开发中的进度可以实时上报，**设计和功能的当前版本必须等完整提交与验收**。

## 2. 哪份数据说了算

| 内容 | 主版本在哪里 | 本地保留什么 | 云端做什么 |
| --- | --- | --- | --- |
| 业务源码、测试 | Git 仓库 | 工作区与 Git 记录 | 保存关联的提交号、改动路径和测试证据；不接收源码树 |
| 角色卡、职责、文件边界 | 云端该项目的 SQLite | 按任务下载的临时副本及版本号 | 按 `role_id` 管理版本、文件归属、审批和下载 |
| 流程、数据、接口、定义 | 云端该项目的 SQLite | 本次任务需要的临时读取结果 | 按 `role_id` 和条目 ID 读写，保存修订记录 |
| 任务、派发、反馈、验收 | 云端该项目的 SQLite | 本次任务的分配凭据和待提交结果 | 检查跨角色依赖、版本、状态和审计事件 |
| 带日期的设计/功能/修改/修复文档 | 项目 Git 中的 Markdown 原稿 | 原文件，按现有目录和命名规则维护 | 该项目的 SQLite 保存正文、历史、所属角色和统一索引 |
| 角色消息、权限申请、管理员决定 | 云端该项目的 SQLite | 通过客户端读取或发送 | 延用现有协作收件箱，记录审计历史 |
| 本地缓存、角色草案、待提交请求 | 本地 `.ans/client.sqlite3`（非正式版本） | 断网重试所需的版本号、游标、草案与请求 | 正式版本仍由云端决定；客户端不能凭缓存自行扩大权限 |
| 项目 Key | 本机受保护的机密来源 | 系统机密管理器或环境变量；迁移期兼容旧配置 | 只保存 Key 哈希；按项目鉴权 |

这里的“云端统一”指**协作状态和查询入口统一**。设计文档仍是本地可审查、可随代码提交的 Markdown；云端存它的原文副本和各次版本，不允许在网页悄悄改一份不同的正文。若将来要在线编辑，必须另设计 Git 回写和冲突处理。

服务器保留**一份全局库 + 每项目一份 SQLite**。全局库只存账号、会话、项目登记和项目 Key 哈希；项目库包含该项目全部角色、任务、项目理解、文档历史、消息、审批和审计。角色数据通过 `role_id` 区分，跨角色任务也在同一个项目库里。页面从这些表生成视图，不再把整份快照当主数据。

### SQLite 存储边界

| 数据库 | 主要表或记录 | 作用 |
| --- | --- | --- |
| 云端 `dashboard.sqlite3` | 用户、会话、项目登记、项目 Key 哈希 | 跨项目身份和项目入口 |
| 云端 `projects/<project-id>.sqlite3` | 全部角色与边界版本、文件归属、流程/数据/接口/定义、任务、文档正文和历史、提交、消息、审批、审计 | 这个项目唯一的正式管理数据库；用 `role_id` 区分角色，文档原文存 `TEXT` |
| 本地 `.ans/client.sqlite3` | 项目地址/ID、已下载版本、角色草案、待提交队列、增量查询游标 | 方便本地执行和断线恢复；可以从云端重新建立，不能代替云端验收 |

项目库中的角色使用稳定的 `role_id`；角色改显示名不改 ID，停用时标记状态而不物理删除历史。文档索引记录 `documentId → role_id、当前版本`，历史设计查询只查这一份库。给常用的 `(role_id, topic_id)`、`(role_id, document_id)` 和任务 ID 建索引，不靠分库解决小规模并发问题。

项目理解的流程节点、字段和接口尽量沿用现有的结构化表；文档正文使用 `TEXT`，必要的可变证据可用经过校验的 JSON 字段，**不把整个项目重新塞进一条快照 JSON**。网络 API 仍可使用 JSON，这只是传输格式，不是第二套持久化文件。源码、测试和本地 Markdown 仍是普通文件：编译器与 Git 要直接读取它们；云端把上传的 Markdown 原文及其历史保存在对应 SQLite。

SQLite 适合这里的单机应用服务器和每项目分库，但[同一数据库同时只有一个写入者](https://www.sqlite.org/wal.html)。服务端使用本机磁盘、短事务、写入超时与有界查询；多个应用实例不能通过共享网络文件系统直接写同一 SQLite 文件。若以后写入量或多机部署超出这个前提，再评估数据库迁移；不提前维护两套存储实现。[SQLite 官方适用场景](https://www.sqlite.org/whentouse.html)也区分了应用服务器本机使用与多台机器直接访问同一数据库文件。

**不按角色分库。**一次提交涉及的任务、该角色流程和文档都在同一项目库内，可以用一笔 SQLite 事务保证一起成功或一起失败，不需要 `ATTACH` 多个角色库。全局账号/Key 库仍独立；日常项目提交不同时修改全局库。创建项目等少数跨全局库和项目文件的管理操作使用可重试的初始化步骤，并在启动时核对缺失文件，不把两个文件的创建误称为一笔事务。

### 一个写入队列就够了

当前预期写入量不大，后端使用**一个有上限的进程内队列 + 一个专用写入线程**，不引入 Redis 或独立消息队列。网页和 AI 的读请求可并行读取；所有修改用户/Key、角色、任务、文档、消息、审批和审计的请求都进入同一个写入入口，不能绕开队列直接改库。服务器只运行一个负责这些数据库的写入进程；第二个进程启动时应被状态目录锁拒绝，不能让两个实例各有一条队列。

HTTP 层先检查身份、请求大小和基本格式，再把命令放入队列。写入线程按顺序处理，**在对应项目库的事务内重新核对版本、角色和权限**，提交成功后才向请求方返回成功。队列只做排队，不能代替 SQLite 事务。事务里只进行有界数据库操作；源码扫描、网络请求、运行测试和 AI 生成都在入队前或事务外完成，避免一项慢工作堵住其他项目。

队列满时立即返回可重试的忙碌响应和等待建议，不丢弃请求；客户端保留 `.ans/client.sqlite3` 中同一请求 ID 稍后重试。服务崩溃时未提交的进程内队列会消失，因此服务端**不提前回复“已成功”**；客户端在超时后先按请求 ID 查询，再用原 ID 重试。若数据库已提交但响应丢失，幂等记录返回原结果。备份和迁移先停止接收新写入、排空队列，再处理整组数据库文件。

## 3. 本地怎样工作

本地只保留一个 `ans` 命令行入口，可由技能调用；它不启动 HTTP 页面。

```text
云端：已确认角色 + 任务 + 项目理解 + 设计历史
                  ↓ 下载并固定版本
本地：读取源码 → 修改代码与 Markdown → 测试 → 提交结果
                  ↓ 带原版本号上传
云端：检查范围和冲突 → 保存候选记录 → 验收后更新当前视图
```

1. **领任务**：`ans task start <task-id> --role <role-id>` 使用项目 Key 读取已确认角色卡、边界、任务和相关设计；真正领取还须有该任务的客户同意或已审核预授权。云端固定 `roleRevision`、`boundaryRevision`、`taskRevision` 和设计版本，并发给本次分配 ID、限此角色/任务使用的短期任务凭据。客户端将副本和版本号存入 Git 忽略的 `.ans/client.sqlite3`；它不是另一份主数据。下载角色不等于激活角色，项目 Key 本身也不能领取任意角色。
2. **本地开发**：AI 按下载的边界修改允许的源码和文档；本地检查实际改动路径、运行项目测试，记录输入、结果和代码 Git 提交号或候选差异哈希。云端 Dashboard 可收到“进行中”“遇到问题”等状态事件，但不会把未验收的说明显示为已生效行为。
3. **交回结果**：`ans task submit <task-id>` 上传本次**增量**，包括改动路径、测试证据、关联代码版本、项目理解条目变化，以及本次新增/修改的日期文档原文和 SHA-256。设计任务可以没有代码改动，先单独提交设计文档，再由后续角色按已确认的设计版本开发。
4. **验收**：服务器先核对任务、角色、边界、前置任务和版本；通过后保存一个候选提交。项目角色或已授权验收方依据实际代码与测试记录验收。只有验收通过，当前项目理解和当前设计版本才向所有人显示为“已生效”；被拒绝的候选和原因仍留在历史中。

提交 Dashboard **不等于**自动 `git commit`、`git push` 或发布程序。若只有本地未提交差异，云端记录为“候选，代码尚未提交”；不能声称服务器上的代码已包含该功能。后续按现有 Git 授权流程提交代码，并在验收前核对关联的 Git 版本。

### 新项目第一次接入

普通角色提案要求已有治理任务；空项目还没有任务和角色，因此需要**一次性初始化入口**，不能假装先有一个项目角色。

1. 管理员在云端创建项目 ID 和项目 Key；本地项目配置记录服务器地址、项目 ID 和 Key，检查 Git 根目录与项目 ID 的对应关系。Key 只证明项目身份，不赋予任何业务源码写权限。
2. 技能内置的 ANS Governance 调查项目，在本地编写初始角色/边界草案和日期设计文档。客户或可信宿主明确确认初始化范围后，由管理员操作提供一次性 `bootstrap` 票据；它只允许提交首批治理草案，不能执行普通开发任务，也不是需要长期配置的另一把项目 Key。
3. 云端检查初始文件归属没有重复、角色间依赖可以成立、设计文档已上传；客户/管理员审阅后发布首批角色和项目默认角色。初始化凭据随即失效，后续新增角色必须走正常治理任务和角色提案接口。
4. 项目角色用已确认版本创建任务，再按通常的领取、执行和验收流程工作。若初始化中断，云端保留草案状态，不发布一半角色；可用同一幂等请求继续。

### 本地新增角色

**必须保留本地创建入口，但创建的是草案，不是立即生效的角色。**首次接入按上面的 `bootstrap` 流程；此后只有技能内置的 ANS Governance 在已授权的治理任务下可以提出新角色。普通业务角色不能给自己新增文件权限。

1. 治理角色先调查代码归属，在本地写角色设计文档；角色卡、边界和职责说明的草案存在 `.ans/client.sqlite3` 的 `role_drafts` 中。命令行可导出临时 Markdown 供审阅，再把修改内容存回草案；临时导出文件不是可执行权限。角色设计文档按日期留在项目 Git 中。
2. 技能调用 `ans role propose --task <task-id> --draft <role-id>`。客户端读取 SQLite 草案和本地设计文档，附项目治理版本、幂等请求 ID、内容哈希上传云端。云端检查角色 ID 是否重复、文件归属是否与现有角色冲突、边界是否列出具体路径、设计文档是否齐全；只生成“待审核提案”。
3. 客户或已有授权的治理审批方在云端查看**具体角色卡、边界差异和设计文档**，批准或拒绝。项目 Key 可提交提案，不能批准自己的提案。批准后服务器发布新 `roleRevision` 和 `boundaryRevision`；若改变已有文件归属，相关在途任务暂停并要求重新领取版本。
4. 技能用 `ans role pull <role-id>` 下载**已批准版本**，再通过正常的任务派发与角色激活门禁使用它。单纯提出草案、下载角色或通过审核，都不自动授权当前 AI 写业务代码。

本地可用 `ans role proposal-status <proposal-id>` 查询审核结果。断网时草案留在本地，恢复后以同一幂等 ID 重试；若云端治理版本变化，返回 `409`，重新核对归属再提交。批准的角色由云端保存为主版本，本地草案可以归档，但不能反向覆盖云端版本。

### 设计文档必须上传

扫描范围是业务项目 `docs/design|feature|change|fix/`、现有项目采用的 `doc/` 同类目录，以及 `角色卡/<role>/docs/` 下的对应目录。只上传本次任务实际新增或修改的 Markdown，不扫描/上传完整仓库。每份文档沿用 `YYYY-MM-DD_<type>_<topic>.md` 和 YAML 元数据，`id` 在项目内稳定；同一 ID 的每次内容变更形成一个新版本，旧原文不改写。

服务器保存：项目、文档 ID、角色、类型、相对路径、标题、状态、原文、SHA-256、文档版本、关联任务、设计/需求版本、代码 Git 版本、上传时间、验收状态。文档换路径时沿用原 ID；两个不同文件不能占用同一 ID。缺少元数据的旧文档可作为“待整理旧文档”导入，并保留实际路径和哈希；不能编造创建日期或已验证状态。

云端页面既能看**当前设计**，也能按时间查看历史版本和它关联的任务/代码版本。流程、接口或角色任务可以引用 `documentId + documentVersion`，让 AI 知道当时依据的是哪一版设计；链接不能只指向会变化的“最新文档”。上传前检查路径仍在项目内、不是符号链接逃逸、内容为 UTF-8 Markdown，并对单文件与单次提交设大小上限；正文可能含项目内部信息，按项目的账号和 Key 权限访问，不放公开 URL。

文档改名仍沿用原 `id`，新版本记录新路径；删除则提交带原因的停用记录，不物理抹去旧版。当前云端策略是所有启用用户可查看全部项目，所以**上传前须确认文档可供这些用户阅读**，排除密码、Token、客户隐私和真实业务数据；需要更窄可见范围的项目，先改访问策略再开启文档全文上传。文档内容不会出现在无需它的普通列表响应中。

### 文档与代码怎样对应

每次功能提交记录 `repositoryId`、Git 提交号或候选差异哈希、改动路径，以及所依据的设计文档确切版本。云端展示源码位置时使用“仓库内相对路径 + Git 提交号 + 行号”；本地 AI 用这些信息打开本地源码，网页在配置了 Git 仓库地址时可打开该提交中的源文件。不能把本机绝对路径当云端链接，也不能把旧提交的行号指向当前代码。

服务器若没有只读 Git 访问，就不能自行证明提交号真的存在；这种提交保持候选状态，由验收方对照实际 Git 版本和测试结果确认。若一个设计改动影响了已派发任务，项目角色必须列出相关任务和依赖，云端将这些任务标为暂停/待重新领取；旧设计版本的反馈留在历史里，但不能验收为新版设计的完成结果。未受影响的任务不因全项目版本号变化而无故停下。

## 4. 云端接口草案

所有路径都接在现有 `/p/<project-id>/api/` 下，因此部署在 `/ans-dashboard` 等前缀时仍可工作。读请求需要项目 Key 或已登录用户；提交请求使用项目 Key，审批仍需管理员/可信宿主的独立授权。**同一项目 Key 只能证明“来自这个项目”，不能单凭它证明操作者真的是某个角色。**服务器必须再核对该角色当前任务、已确认边界和版本；本地执行器仍负责限制实际文件写入。

| 接口 | 目的 | 关键输入或返回 |
| --- | --- | --- |
| `GET /roles` | 列出可领取的已确认角色 | 角色 ID、名称、职责摘要、当前角色/边界版本 |
| `GET /roles/<role-id>/bundle` | 下载已确认角色 | 角色卡、边界、可写路径、所需设计 ID、各自版本和哈希 |
| `POST /bootstrap` | 空项目提交首批治理草案 | 一次性客户/可信宿主凭据、首批角色与边界、日期设计文档；不能直接获得业务代码权限 |
| `POST /role-proposals` | 本地提交新角色或角色边界变更草案 | 治理任务、草案正文与哈希、设计文档、基础治理版本、幂等 ID；只生成待审核记录 |
| `GET /role-proposals/<id>` | 查询提案和审核结果 | 草案、范围差异、冲突检查、状态、审批记录 |
| `POST /role-proposals/<id>/decision` | 审批并发布角色版本 | 独立的管理员/可信宿主授权、批准或拒绝理由；项目 Key 不可调用 |
| `GET /tasks/<task-id>/assignment?role=<role-id>` | 取得本次任务 | 目标、依赖、分配 ID、允许操作、固定的需求/设计/边界版本 |
| `POST /tasks/<task-id>/claim` | 在授权后领取任务 | 客户同意或已审核预授权的证明、角色与版本；返回限定本次分配的短期任务凭据 |
| `GET /context?role=<role-id>&category=<type>` | 查询项目理解 | 条目摘要、ID、当前版本；详情按现有 topic 接口读取 |
| `GET /design-docs?role=<id>&type=design&q=<词>&cursor=<值>` | 查历史设计清单 | 文档 ID、标题、日期、状态、最近版本、下一页游标；有界分页 |
| `GET /design-docs/<document-id>/versions` | 查看一份文档的版本史 | 每版号、哈希、关联任务、设计版本、代码版本、验收状态与时间 |
| `GET /design-docs/<document-id>/versions/<version>` | 取确切旧版正文 | Markdown 原文、SHA-256、元数据；只读、不可覆盖 |
| `POST /submissions` | 提交设计或功能结果 | 幂等请求 ID、分配 ID、所依据的版本、代码版本、改动路径、测试证据、项目理解增量及本地 Markdown 文件内容/哈希 |
| `GET /submissions/<id>` | 查询提交结果 | `candidate / accepted / rejected` 与原因、生成的文档/条目版本；版本冲突直接返回 `409` |
| `GET /changes?since=<cursor>` | 增量查询角色、任务和文档变化 | 有序变更与下一游标，供技能在下一次任务前更新理解 |
| `GET /export` | 管理员导出项目归档 | 带校验清单的角色、任务、项目理解和文档各版；不包含明文凭据 |

技能查询历史设计时，先用清单接口按角色、关键词或时间找到文档 ID，再用版本史和确切版本接口取原文。它应优先读取本次任务固定的设计版本，而不是拿“最新”覆盖当时的依据。返回结果带 `documentId`、版本、哈希和来源路径，AI 在结论中能说明自己依据哪一版；找不到时明确说未找到，不编造历史。本地命令行应提供对应的 `ans design list --role <id>`、`ans design history <document-id>` 和 `ans design get <document-id> --version <n>`；技能只需调用这些命令，不必自行拼接 URL 或接触 Key 原文。

一次设计文档提交的请求结构示意如下。实际接口必须校验字段、文档元数据和大小，不接受示意值直接进入生产数据：

```json
{
  "requestId": "task-42-design-1",
  "taskId": "task-42",
  "assignmentId": "assignment-7",
  "roleId": "project",
  "base": {"roleRevision": 3, "boundaryRevision": 5, "taskRevision": 2,
           "documents": {"order-review-design": 1}},
  "codeRevision": null,
  "changedPaths": ["docs/design/2026-09-26_design_order-review.md"],
  "documents": [{"documentId": "order-review-design", "path": "docs/design/2026-09-26_design_order-review.md",
                 "sha256": "<64 位十六进制摘要>", "content": "<完整 Markdown 原文>"}],
  "contextChanges": [],
  "testEvidence": []
}
```

服务器先以 `base` 检查本次工作依据的版本，再逐项校验任务凭据、角色和范围。`roleId` 是角色声明；项目 Key 本身不能证明身份，短期任务凭据只能证明请求关联到某次已授权分配，实际本地文件写入仍由执行器限制。设计文档可先进入候选状态；它被确认后才成为其他任务可固定引用的设计版本。功能提交则补充 `codeRevision`、实际改动路径、测试证据和项目理解增量。`409` 响应返回冲突对象及云端当前版本，不回显项目 Key、文档中不相关的内容或其他项目数据。

`POST /submissions` 只接受增量，不接受整份项目快照。服务端先检查请求，再交给唯一写入线程；写入线程重新校验当前版本，在对应项目库的一笔事务中写候选提交、文档不可变候选版本、项目理解候选变更、索引和审计事件；中途失败则整次不生效。验收时也经同一队列和项目库事务更新“当前版本”指针与任务状态。客户端超时重试同一个幂等 ID，只会拿到原结果，不会造出两份版本。角色或边界变更走单独的治理提案与确认流程，普通功能提交不能顺手扩大自身权限。

项目 Key 是本地唯一需要长期配置的 Key。短期任务凭据由服务器自动发放、客户端内部管理，无须用户另行创建；两者都放在请求头，不写入提交 JSON、文档或命令行参数，服务端日志也不得记录原文。SQLite 本身不加密机密，项目 Key 优先由系统机密管理器或环境变量提供；迁移期读取旧 `.ans-dashboard.local.json`，验证新来源后再清理旧配置。短期凭据到期或任务暂停后，必须重新按当前角色/设计版本领取，不能复用旧分配继续提交。

## 5. 冲突与失败怎么处理

角色、边界、任务、项目理解条目和文档“当前指针”各有独立版本。客户端提交它开工时读到的版本，服务器在事务内比较：

- **相同**：接受候选增量，并分配新版本。
- **不同**：返回 `409 Conflict`，列出冲突对象、客户端依据的版本和云端当前版本；不写入当前记录。AI 拉取新版本、比较本地改动，必要时修改代码/设计并重新测试，再以新版本提交。不同条目可并行提交，不因另一个角色改了无关条目而冲突。
- **重复请求**：同一幂等 ID 且内容相同，返回第一次结果；同 ID 内容不同，拒绝。
- **网络中断**：本地保留待提交文件和请求 ID，查询提交状态后重试；不因为没收到响应就假定失败或重新生成一个提交。
- **云端不可用**：可以只读调查本地源码和已下载的历史，但不能领取新角色/任务或宣称新结果已同步；正在进行的本地改动保留，恢复连接后重新核对版本。

文档原稿仍在 Git。若两个分支改了同一文档，先在 Git 合并正文，再提交云端；云端的 `409` 防止把旧文档标为当前版本。云端保存候选与被拒绝的历史，但不自动把任何一版反向写入本地 Git。

### 云端数据丢失时怎样恢复

云端成为角色、任务和项目理解的主版本后，备份是上线条件，不只是迁移时做一次。定期备份全局库和**每个项目的一份 SQLite**，使用 [SQLite 在线备份接口](https://www.sqlite.org/backup.html)；备份开始前排空写入队列，记录同一备份批次、架构版本、项目 ID、备份时间和校验和，避免全局项目登记与项目文件不一致。备份文件加密并限制管理员读取。按项目设定保留期，定期在隔离环境实际恢复一次，核对账号/Key 元数据、角色版本、任务历史、文档版本和项目理解的数量与哈希。恢复失败不能直接开放写入。

恢复旧备份会使服务器版本倒退。恢复后先暂停提交，对照本地 Git 文档、尚未确认的本地提交请求和最近审计记录，明确缺失的时间段，再以原幂等 ID 补交或人工处理；不能让旧客户端直接上传并把恢复后的内容盖掉。支持管理员按项目导出角色、项目理解、任务事件和文档原文/版本的可校验归档，供迁移或灾难恢复；导出不包含明文 Key、密码或会话。项目 Key 泄露时由管理员撤销并轮换，旧 Key 立即失效，不改变已存的文档和任务历史。

## 7. 迁移和发布顺序

1. **先备份**：停止旧同步器，备份云端完整状态目录/卷，以及业务项目的角色卡、`project-context/context.sqlite3`、任务 JSON/JSONL 记录和文档目录。记录项目 ID、各条目数量与哈希。已有云端消息和审批保留，不拿旧展示快照覆盖它们。
2. **先让云端能读**：在现有 `projects/<project-id>.sqlite3` 增加结构化表和只读 API；从**本地正式记录**一次性按 `role_id` 导入已确认角色、边界、项目理解、任务 JSON/JSONL 历史和带日期文档。迁移前复制旧项目库作备份，旧展示快照只用于对照，确认新表和页面正确后才停用全量快照写入。建立本地 `.ans/client.sqlite3`，把旧配置中的项目 ID/服务器地址与待提交状态迁入；Key 转到受保护的机密来源。检查角色数、各角色条目数、任务事件数、文档 ID/哈希及权限边界；导入失败从备份恢复并继续旧系统。
3. **再让云端能写**：增加首次接入、角色提案、版本检查、增量提交、审计和文档历史接口；本地客户端先在测试项目完成“初始化项目 → 本地提出新角色 → 云端批准 → 下载角色 → 设计文档上传 → 修改功能 → 测试 → 提交 → 验收 → 查询旧版设计”的闭环。测试同条目并发、断网重试、重复提交、越权路径、旧角色版本和设计修订后暂停任务。
4. **最后切换**：真实项目先选一个角色试运行。验收标准通过后，停止本地 Dashboard 页面和定时全量同步；更新技能规则与 README，改用云端页面及本地命令行客户端。保留旧数据备份和只读导出一段迁移期，不让新旧两条写入链路同时运行。

本设计文档本身也属于必须上传的本地设计文档：**文档上传接口上线后**，应由迁移程序按它的 `id`、路径、原文和哈希导入历史。当前系统没有该接口，不能声称此文件已经同步到了云端。

## 8. 验证与验收条件

这是设计阶段，下面的测试**计划执行，尚未运行**：

1. 一个项目两台客户端同时领取同一设计版本：先提交者成功，后提交者收到 `409`；云端当前设计不丢失，旧稿仍可查。
2. 设计角色先上传本地 Markdown，实施角色随后按固定 `documentId + version` 下载；即使之后设计修订，历史版本仍可完整取回并校验 SHA-256。
3. 功能提交包含代码版本、测试证据、文档和项目理解增量；任一条越界或校验失败时，整个提交不生效，页面不显示“已完成”。
4. 同一个请求超时重试只产生一次提交；模拟项目库事务中途失败时，任务、文档和项目理解要么一起生效、要么都不生效；服务器恢复后消息历史完整。
5. 旧项目迁移前后的角色数、项目理解条目数、任务事件数、文档哈希和已确认任务状态一致；旧同步器关闭后不再产生 JSON/JSONL 主状态或整份快照覆盖。
6. 网页和技能都能按角色/关键词找到历史设计，打开指定旧版本，并看到它对应的任务、代码版本和验收状态。
7. 本地新角色草案在批准前不能领任务或改业务代码；云端拒绝重复 ID、重复文件归属和旧治理版本。批准后可下载确定版本，受影响的旧任务不能继续使用过期边界。
8. 空项目能经一次性初始化创建首批角色，初始化凭据不能用于第二次普通开发；设计改版只暂停真正依赖旧设计的任务。
9. 网页源码链接指向对应 Git 提交中的仓库相对路径；不能错误打开本机绝对路径或把旧行号当成最新代码。
10. 从备份恢复到隔离环境后，可核对全局库、各项目库和文档哈希；缺少任一项目库或模拟服务器版本倒退时，不能开放写入或让旧客户端静默覆盖恢复数据。
11. 并发写请求按队列顺序提交；队列满时明确返回忙碌状态，客户端用原请求 ID 重试；写入线程崩溃后不存在“请求未入库却回复成功”的情况，第二个写入进程也不能同时启动。

完整实施时还需运行 Dashboard 单元/HTTP 测试、数据库迁移回归、浏览器流程验收和一个真实跨角色任务。设计文档本身只需检查元数据、链接、接口与迁移步骤的自洽性，不把计划中的测试写成已通过。
