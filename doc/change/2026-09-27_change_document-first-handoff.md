# 先交文档，再改代码

以前的规则强调“文档要写给人看”，却没说写完后怎么交给客户讨论。AI 可能只给一个文件链接，也可能刚写完方案就继续改业务代码，客户还没机会确认是不是他要的做法。

现在先把对应类型的文档写成草稿。在聊天里附链接，用几句话说明要解决什么、准备怎么做、还没做什么。流程或前后差别不好讲时，可以放一张小图或表；不必为了展示而硬画图。交付设计方案时问一句“这个方案有什么地方想进一步了解吗？”这只是邀请提问，不算确认。

客户确认这份文档，并明确授意“按它修改”后，才动业务代码或测试。已有的同一版本确认和实施指令继续有效，不让客户重复答应。等客户回复时仍可只读调查或完善文档；若方案实质改变，要先把改后的部分交客户看。这里改的是技能写文档和启动编码的顺序，没有改 Dashboard、业务源码或已有任务权限。

待检查：技能入口、角色卡、工作流和四类文档写法能否说同一套规则，相关链接能否打开，`git diff --check` 是否通过。此次只改文档规则，不需要运行业务代码测试。
