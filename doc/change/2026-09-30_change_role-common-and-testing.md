# 各角色的基础代码放哪里，跨角色的工作由谁安排

以前角色只能修改白名单里的具体源码文件。想把自己的代码拆成几个基础组件，也要先增加文件权限。项目管理角色又完全不能写代码，无法自己维护大家共用的组件。

现在合并工具函数和基础框架，统一放进 `src/common/`。各角色维护自己的子目录；项目管理角色维护 `shared/`、对应测试和共享组件说明。跨角色的需求、接入、问题修复和验收都由项目管理角色安排，治理角色继续负责权限变化。

## 一个完整例子

1. 工单角色在自己的 `common/order/` 中整理本次任务需要的校验工具，并运行对应单元测试。
2. 消息角色发现自己也需要相同的校验机制，向项目管理角色提出复用请求，不直接导入工单的私有目录。
3. 项目管理角色核对语义、输入输出及使用方，写明共享方案。用户确认文档并授意实施后，继续修改。
4. 如果需要新权限，由治理角色先提交边界调整。已有目录权限和同版任务授权继续有效，不为每个内部文件反复调整边界。
5. 项目管理角色编写 `common/shared/` 中的组件和测试，更新文档根下的 `architecture/shared-components.md`。
6. 项目管理角色安排工单、消息角色各自接入。它们修改自己的调用代码，清理已被替代的旧实现，并运行自己的测试。
7. 固定测试角色检查两个功能的实际流程和受影响功能。失败时报告复现步骤、实际与预期差别，由项目管理角色安排代码所属角色修复后复测。
8. 测试结果有效后，项目管理角色按已确认条件验收；各角色更新自己的架构 JSON，项目管理角色重新生成页面。

共享清单记录用途、代码入口、维护者、使用者、输入输出、调用示例、对应测试和修改影响。业务规则仍在五层内，common 不反向调用业务层，也不允许通过回调藏入越层流程。

## 范围与工具限制

用户已在本轮确认 common/shared 分工并要求修改，也明确选择了“开发角色负责单元测试，固定测试角色负责联调、完整流程和回归”。这次修改技能和必要的配套工具，不搬迁现有业务项目或 test 示例的代码，不自动更改它们的角色权限。没有新增选装项。

任务工具的配置 `writeFiles` 和单次任务 `writeSet` 仍记录具体文件。目录边界允许文件归属随内部组织生长，不表示运行中的任务可以任意增加文件。扩大已锁定任务的写入集合仍走原有任务配置和授权流程；不需要为了目录中每个新文件修改角色边界。

## 验证

1. `python3 -m unittest discover -s scripts/tests -q`：150 项通过。本轮新增 8 项测试，覆盖 common/测试目录内的新文件、任务范围仍受限制、目录越界与归属重叠、路径逃逸，以及共享节点的绘图归属和 Model 标签检查。
2. 首次完整运行有 10 项 HTTP 测试因沙箱不允许绑定本机端口而无法运行；获准使用本机临时端口后，完整重跑通过。没有连接部署服务器。
3. `node --check assets/architecture-viewer/app.js` 和 `git diff --check` 通过。149 个本地 Markdown 链接有效，技能 YAML 头部用 Ruby YAML 解析通过。
4. 官方 `quick_validate.py` 因当前 Python 缺少 PyYAML 没有运行成功，不能算通过。架构页沿用已有内存 DOM 交互测试，本轮没有做真实浏览器视觉检查。

这些结果验证的是技能配套工具。本轮没有用新分工开发一个真实业务功能，也没有修改已有业务项目的角色卡。仓库发布与本地技能更新另按用户的明确指令执行。
